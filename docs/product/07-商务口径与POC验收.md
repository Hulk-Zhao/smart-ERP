## 1. 计费单元的准确定义

### 1.1 定义（用枚举名，不用形容词）

计费单元 = **有效对账行（计费单元，= 行级 auto，含已自动归因的差异行）**，即同时满足下列全部条件的行（行，不是批次）：

| 条件 | 代码位置 | 判据 |
|---|---|---|
| 该行在供应商侧 | `apps/api/metering.py` `build_statement()`：`supplier_side = [line for line in all_lines if line.supplier_ref]` | `supplier_ref` 非空 |
| 引擎状态为 `LineStatus.MATCHED`（值 `"已匹配"`） | `apps/api/metering.py` `classify_billing_bucket()` | `status == LineStatus.MATCHED.value` |
| 匹配类型属于自动匹配 | `apps/recon/engine.py` 配对行赋值；`apps/recon/matching.py` | `match_type ∈ {EXACT, FUZZY, AGGREGATED}` |
| 未被标记为需人工 | `apps/recon/models.py` `MatchResultLine.needs_manual` | `needs_manual == False` |

正式口径（S2 底稿原文）：`status = 已匹配` 且 `match_type ∈ {exact, fuzzy, aggregated}` 且 `needs_manual = false`，**含已自动归因的差异行**（单价不一致、数量不符、税率口径、报废未扣、金额舍入容差）。

代码当前只判 `status == 已匹配`，没有再判 `match_type`；因为引擎只会给 `exact / fuzzy / aggregated` 三类配对行赋 `MATCHED`（`apps/recon/engine.py` 第 320–357、362–385 行），两者在现有实现下等价。**对外解释时按上面的完整定义说，不要只说「已匹配」。**

关于分母：整批「无法对账」（`BatchStatus.NO_CONCLUSION`，引擎未执行任何匹配）的批次，其行**不进有效对账行，也不进计费基数**。这不是「放行了但不计费」，而是引擎没有产出可对账的行；同一批次的 `expected_lines` 与逐行明细都为 0。

### 1.2 明确计入的几类行

| 行的形态 | 引擎状态 | 为什么计入 |
|---|---|---|
| 零差异直配 | `已匹配` | 引擎自动放行 |
| 已自动归因的差异行，仅限这四类：`UNIT_PRICE` 单价不一致、`QTY` 数量不符、`TAX` 税率口径、`SCRAP` 报废未扣 | `已匹配`（这四类归因置信度为 0.74–0.92，均 ≥ 0.70） | 「自动归因」本身就是交付结果；差异行仍需引擎判断与证据链 |
| 金额舍入容差行（`DiffType.ROUNDING_TOLERANCE`，默认单行 ≤ 0.05 元，**已自动放行、未生成差异单**） | `已匹配`（该差异置信度 0.95） | 已按容差自动放行；见 `apps/recon/attribution.py` 第 239–263 行 |
| 聚合匹配（拆单，`MatchType.AGGREGATED`，多张供应商行合计对应我方一行） | `已匹配` | 合计已闭合，引擎自动放行 |

两类容易被误认为「已自动归因、应计费」的差异，实际**不计费**：

- `DiffType.MISSING_DOC` 缺单：挂在 `供应商未匹配` / `我方未匹配` 行上，前者进 `other_unbillable`，后者不进供应商侧明细。
- `DiffType.UOM` 单位换算：置信度固定 0.40（低于 0.70），行状态为 `待人工`；且当前代码只定义了构造函数、引擎未调用，实际不会产出该差异。

### 1.3 明确不计入的行

| 引擎状态 | 枚举值 | 计量桶 | 对外原因码 |
|---|---|---|---|
| `LineStatus.NEEDS_REVIEW` | `待人工` | `dispute_hold` | `dispute_hold` |
| `LineStatus.AMBIGUOUS` | `匹配歧义` | `dispute_hold` | `dispute_hold` |
| `LineStatus.CANDIDATE_ONLY` | `候选待人工` | `dispute_hold` | `dispute_hold` |
| `LineStatus.UNMATCHED_SUPPLIER` | `供应商未匹配` | `other_unbillable` | `unmatched_supplier` |
| `LineStatus.DUPLICATE` | `重复计费` | `other_unbillable` | `duplicate_billing` |
| `LineStatus.UNPARSEABLE` | `不可解析` | `other_unbillable` | `unparseable` |

补充两点：

- `LineStatus.UNMATCHED_OURS`（`我方未匹配`）没有 `supplier_ref`，不进供应商侧计量明细；它是「我方有、供应商无」，本来就不该向客户计费。它体现在引擎的 `metrics.unmatched` 里，不影响 `expected_lines`（分母只数供应商行）。
- 合并开票（一张供应商行覆盖我方多行）被引擎判为 `NEEDS_REVIEW`，属 `dispute_hold`，不计费——因为拆分口径不唯一，必须人工确认。

### 1.4 为什么不用 clean 行做计费基数

1. **clean 不覆盖交付价值**：客户买单的是「引擎把这条差异判清楚了」，不是「这条差异不存在」。用 clean 计费，等于越难的对账越便宜，激励方向反了。
2. **clean 会随供应商质量波动，账单不可预测**：同一客户不同月份的零差异比例会变，客户无法做预算。合同需要一个**只随业务量变化、不随数据脏净变化**的基数。
3. **clean 与舍入容差冲突**：舍入容差行是引擎按规则自动放行的，但它 `diffs` 非空，不算 clean；如果按 clean 计费，这类已处理的行会白干。
4. **内部质量指标本来就不该兼作计费口径**：`docs/product/tech/recon-behavior-changes.md` §3.1 已明确「行级 clean 仅作内部质量指标，不作计费基数」。本文与之一致。

> 内部提醒：clean 比例当前只有自造夹具上的数字（B 类），**不得对外报任何 clean 比例**。

### 1.5 批次未放行，行照计

合同兜底句：**计费不以批次放行为前提。**

代码依据：`build_statement()` 只读逐行 `status` / `needs_manual`，**不读** `snapshot.status` 或 `snapshot.conclusive`（`apps/api/metering.py` `build_statement()`）。因此：

- 批次因存在争议行而整体为「待人工复核」时，其中已自动匹配的行仍然计费；
- 批次为「无法对账」（`BatchStatus.NO_CONCLUSION`）时，引擎不产出任何匹配行，自然没有可计费行——这是「没干活不计费」，不是「放行才计费」；
- UI 会在 `conclusive=false` 时提示「本计量表仅反映当前程序性事实」，但金额照常展示（`web/src/pages/MeteringPage.tsx` 第 329–333 行）。

### 1.6 舍入容差行：单行计入，整批超限部分不计

**口径（S2 底稿，权威）：**

- 单行舍入容差行计入：引擎已按容差自动放行、未生成差异单，属于有效产出。
- 整批舍入差累计超限（默认 1.00 元或供应商总额的 0.5%，即 `apps/recon/engine.py` 的 `ROUNDING_BATCH_RATE = 0.005`）而**转人工的那部分不计**。

**实现现状：**

- 引擎对舍入行生成 `DiffType.ROUNDING_TOLERANCE`，置信度 0.95，`needs_manual=false`，整行状态 `MATCHED`。
- 超限时引擎只设置 `metrics.rounding_escalated` 并把**批次**降为 `NEEDS_REVIEW`，**不改单行状态**；计量端只读行状态，因此这些行目前**仍会被计入**。
- 结论：口径要求「转人工部分不计」，代码尚未实现该剔除，属偏差 **D15**（见第 7 节）。
- **状态与使用限制：当前未实现——代码只降低批次状态并仍按行计费。在计量闭环补齐前，此条不得对外作书面承诺，也不得写进 POC 验收标准；对外只能说明「剔除逻辑尚未实现」。**
- 对外解释（单行层面）：舍入差是供应商按角取整产生的噪声，引擎按容差自动放行，属于已处理行。

## 2. 计量公式与算例

### 2.1 公式

```
应处理行数 expected_lines
  = 对账引擎 metrics.supplier_lines（供应商对账单行数）

行级 auto（有效对账行）
  = count(供应商侧行
          where status = LineStatus.MATCHED
            and match_type ∈ {EXACT, FUZZY, AGGREGATED}
            and needs_manual = false)
  （整批 NO_CONCLUSION 的批次不产出可对账行，自然为 0）

计费行数 billable_lines
  = 行级 auto
    − 已确认错放行行数（confirmed_wrong）
    − 客户原因不计费行数（customer_reason）
    − 整批舍入超限转人工的行（口径要求剔除，当前未实现，见 D15）
  （前两项回填入口未接线，按 0 扣减；第三项未实现，故 billable_lines = 行级 auto，是上界）

本期金额 period_amount
  = billable_lines × 单行单价（ERP_METERING_UNIT_PRICE，4 位小数）

累计金额 cumulative_amount
  = 已计金额（ERP_METERING_PRIOR_AMOUNT）+ 本期金额

封顶余额 cap_remaining
  = 封顶金额（ERP_METERING_CAP_AMOUNT）− 累计金额
```

四条约束：

1. **单价只从合同价目/配置读，不用默认价**：`require_contract_price=true` 且无可用价目时返回 503 `E-PRICE-MISSING`（**不是 200 带空价**）；`require_contract_price=false` 时回落环境变量，并在 `context.source` 标出取值来源（`contract` / `env`）；账单读取（计量表读取）给同一错误码。**合入状态**：该行为**已合入 main（`9502d83`）**：`apps/api/price_book.py` `require_contract_price()`、`apps/platform/contracts/errors.py` `PRICE_MISSING`、`apps/api/service.py` 的 `context.source`（`contract` / `env`）与 `unit_price_source` 均已存在。错误码可按目标口径对外承诺；§7-D18 随之关闭。
   计费单元不因单价来源变化：无论取合同价目还是回落配置，计费基数仍是有效对账行（= 行级 auto），见 §1.1。
2. **金额 4 位小数**：单价与金额均按 `0.0001` 量化。
3. **计数与逐行同源**：四类计数与逐行 `billing_bucket` 都由 `classify_billing_bucket()` 产出，禁止第二处重算。
4. **封顶只提示不阻断**：`cap_exceeded` 只是布尔标记，累计金额仍会继续增加；合同层面的封顶需要人工/商务在账单上执行（当前无自动阻断）。

### 2.3 算例（用真实枚举构造，不是报价）

> 单行单价假设 **2.00 元/行**，仅为算例假设，**不是报价**。真实单价写在合同附件。
> 批次：1 个期间、1 个供应商、7 条供应商行；容差取默认值（金额 0.01、舍入 0.05、整批舍入上限 1.00）。

| # | 供应商行 | 我方对应 | 引擎结论 | `LineStatus` | 差异类型 | `needs_manual` | 计量桶 | 计费 |
|---|---|---|---|---|---|---|---|---|
| 1 | PO-1，数量 10 × 单价 5.00 = 50.00 | 50.00 | 直配，无差异 | `已匹配` | 无 | false | `billable` | 计入 |
| 2 | PO-2，数量 10 × 单价 5.05 = 50.50 | 50.00 | 单价不一致 0.50 元，置信度 0.90 | `已匹配` | `UNIT_PRICE` | false | `billable` | 计入（已自动归因） |
| 3 | PO-3，数量 10 × 单价 5.00 = 50.04 | 50.00 | 金额差 0.04 元在舍入容差内，置信度 0.95 | `已匹配` | `ROUNDING_TOLERANCE` | false | `billable` | 计入（舍入容差） |
| 4 | PO-4，数量 10 × 单价 5.00 = 55.00 | 50.00 | 残留 5.00 元无法归入七类 | `待人工` | 无（进 `unattributed`） | true | `dispute_hold` | 不计 |
| 5 | ST-AMB，与两条我方行候选置信度差 < 0.10 | 两条候选 | 匹配歧义，只给候选不下结论 | `匹配歧义` | 无 | true | `dispute_hold` | 不计 |
| 6 | ST-X，供应商有、我方无 | 无 | 缺单 | `供应商未匹配` | `MISSING_DOC` | false | `other_unbillable` | 不计 |
| 7 | ST-DUP，与 PO-1 整行重复 | 无 | 重复计费 | `重复计费` | `DUPLICATE` | false | `other_unbillable` | 不计 |

计算过程：

```
应处理行数 expected_lines            = 7
自动放行行数 auto_released_lines     = 3   （#1 #2 #3，= 计费行数）
争议挂起行数 dispute_hold            = 2   （#4 #5）
其他不计费行数 other_unbillable      = 2   （#6 #7）
校验：3 + 2 + 2 = 7 = expected_lines = 供应商侧明细行数

行级 auto（有效对账行）              = 3
已确认错放行行数                     = 0（回填未接线，按 0）
客户原因不计费行数                   = 0（回填未接线，按 0）
计费行数 billable_lines              = 3

本期金额 = 3 × 2.00                  = 6.00 CNY
累计金额 = 0 + 6.00                  = 6.00 CNY
封顶余额 = 100.00 − 6.00             = 94.00 CNY（封顶仅为算例假设）
```

**这个批次最终是什么状态？** 存在人工行，批次为「待人工复核」（`auto_disposal_allowed=false`）。但 #1–#3 仍然计费 3 行——这就是 §1.5 的「批次未放行，行照计」。

**内部参考（不得对外）**：该批次的 clean 行只有 #1 一条，clean = 1/3；但计费行是 3。两者不是一个口径，clean 只用于内部质量观察。

### 2.4 反向减项算例（说明「合同口径」与「当前系统」的差距）

假设上例中：

- #2 事后被双方确认「引擎放行错了」→ 已确认错放行 1 行；
- #3 事后被确认是客户侧数据问题，按合同不计费 → 客户原因 1 行。

合同口径下：

```
计费行数 = 3 − 1 − 1 = 1
本期金额 = 1 × 2.00 = 2.00 CNY
```

**当前系统实际输出**：仍然是 3 行、6.00 元。因为 `confirmed_misrelease_lines` 与 `customer_reason_lines` 都是计费服务侧回填事件、当前尚未接线，`build_statement()` 只能按 0 扣减，并在 `calculation` 与 `billable_basis` 里写明「上界」。这不是算错，是**扣减链路还没接**。对外必须按 §4 的说法讲，不能把 2.00 说成系统已经能自动算出来的数。

## 3. 争议与反向减项

### 3.1 只扣两类，按行扣

| 减项 | 业务定义 | 谁提出 | 谁认账 | 当前系统 |
|---|---|---|---|---|
| **已确认错放行** | 引擎判为 `已匹配` 并已计费，复核确认该行结论错误（`confirmed_wrong`） | 客户财务或我方对账运营 | 双方复核人签字确认 | 无回填入口、无扣减；接口字段 `confirmed_misrelease_lines` 恒为 null |
| **客户原因** | 客户侧原因导致该行无效，按合同不计费（`customer_reason`） | 我方客户成功/商务 | 客户书面确认 + 确认人 | 无回填入口、无扣减；`customer_reason_lines` 恒为 null |

口径命名与职责边界（按 S2 底稿）：

- 对外/合同统一用 `confirmed_wrong`、`customer_reason` 这两个名字。
- 两者都是**计费服务侧的回填事件**（已批准的 schema 追加），`apps/recon` **不产出、也不应产出**；不是引擎漏了，而是职责边界本来就在计费侧。
- 系统现有字段名是 `confirmed_misrelease_lines` / `customer_reason_lines`，与对外名不同；客户按中文名找即可。
- 当前计费服务侧回填入口尚未接线，因此两个字段恒为 null、扣减为 0。

### 3.2 系统性错误不按行扣

以下情形**不逐行扣减**，而是走整批追溯：

- 引擎规则缺陷、主数据映射错误、单位换算错误等导致的成批错误；
- 同一原因批量产生、逐行确认已无意义的情形（是否构成「系统性」由双方在争议确认单上共同判定，**本文不设行数或金额阈值**）；
- 处理方式：保留原批次不动（库表只追加、不可改），用 `rerun_of` + `rerun_reason` 重跑生成**新批次**，以新批次重算；差额在次月账单以红字调整或贷记单冲抵。

代码依据：批次与行快照 append-only，数据库触发器兜底（`db/migrations/versions/0003_recon_persistence.py` 的 `recon_batch_append_only` / `recon_line_append_only`）；重跑必须同时给 `rerun_of` 与 `rerun_reason`，服务端生成新批次 ID，原批次永久不变（`apps/api/contract.py` §对账结果留存）。

### 3.3 怎么举证

争议必须以**行**为单位提出，并按下列材料举证：

| 材料 | 来源 | 是否已具备 |
|---|---|---|
| 批次 ID、行号 `line_no`、`supplier_code`、`our_ref`、`supplier_ref` | 计量表 JSON / CSV | 已具备 |
| 引擎状态 `status`、差异类型 `diff_types`、归属 `owner`、置信度 `confidence` | 同上 | 已具备 |
| 证据链 `evidence`（`system` + `doc_no` + `field`，可带 `coord`） | 同上 | 已具备（引擎产出，缺单行也有） |
| 逐行 CSV 与 `X-Content-SHA256` 摘要 | `GET .../statement?format=csv` | 已具备 |
| 「已确认错放行」的双方签字结论 | 线下争议确认单 | **未实现**：计费侧回填入口未接线，只能附件 |
| 「客户原因」的原因码、说明、确认人 | 线下确认单 + 商务台账 | **未实现**：计费侧回填入口未接线，只能附件 |
| 人工复核留痕（谁改的、改前改后） | 系统 | **未实现**：`human_modified` 恒为 null |

对外话术：**「每一行都能导出 CSV 并校验摘要，行级差异与证据链可查；但『确认错放行』和『客户原因』目前是线下确认、人工登记，系统还不会自动扣减。」**

### 3.4 谁认账、时限（建议条款，须商务/法务确认）

> 以下时限是**建议值**，仓库里没有任何合同模板或代码实现支撑；不得当作已生效条款对客户宣读。

| 环节 | 建议时限 | 责任人 |
|---|---|---|
| 客户对计量表提出书面争议 | 计量表出具后 10 个工作日内 | 客户财务 |
| 我方给出证据与复核意见 | 收到争议后 5 个工作日内 | 我方对账运营 |
| 双方对单行结论签字确认 | 证据交换后 5 个工作日内 | 双方复核人 |
| 未达成一致 → 升级 | 下一个工作日内升级至双方财务负责人 | 双方财务负责人 |
| 仍未一致 | 该行**暂不计费/暂挂**，不阻塞其他行结算；年度结算前必须清空 | 商务 |
| 扣减生效 | 次月账单红字调整或贷记单 | 商务/财务 |

原则：**争议只影响争议行，不冻结整批账单。** 这条与代码行为一致：计量表按行分类，争议行进 `dispute_hold`，同一批次的其他 auto 行照常计费。

### 3.5 赔付上限

- 合同口径：**赔付上限 = 年订阅额的 20%**。触发条件与计算方式以合同/法务文本为准，本文不扩展适用范围（未定）。
- 与「结果费封顶」不是一回事：`docs/product/05-商业模式与路线图.md` §1.2 的「结果费 ≤ 平台订阅 × 3」是**计费封顶**；20% 是**赔偿责任上限**。两个上限不得混用，也不得互相替代。
- **当前系统未实现任何赔付计算**：没有赔付单、没有 20% 校验、没有与订阅额关联的字段。该条只能作为合同条款，由商务/法务在合同与账单层面执行。

**三条禁止出现的说法**：

1. 「已实现外部写入」——含糊，会被理解成接了真实系统。应说「在本地模拟桩上跑通了写入与删除草稿」。
2. 「已接真实 U8 / 已对接客户 ERP」——不成立，对端是桩。
3. 「多系统写入」——只有 U8 制单（草稿）一类有写实现，WMS 无写实现、文件通道只读。

**与「自动补偿」的分界**：本节能演示的是**手动**补偿（`ERP_ROLLBACK_SYNC_ENABLED=1` 时、对执行中/补偿中工单、需 `fail_code`）；**自动**补偿（失败后进 `compensation_task`）仍无生产者，本版不演示、不承诺。

**补偿演示的强制讲述顺序（顺序不能改，缺一句就停）**：

1. 写入（预演 → POST 建草稿 → 回查）；
2. 手动补偿 → 删除草稿；
3. 打开 `/stub/reversals`，指给客户看这次冲销记录；
4. **紧接着必须说**：「这次冲销**没有写入 `ticket_event`**，审计链上查不到这一步，是下一步要补的缺口。」

不许让读者/观众自行得出「回滚已可审计」的结论：`/stub/reversals` 能证明的是**对端草稿被删除**，不能证明回滚进入了审计链。同步补偿路径不写 `ticket_event`、无租约与重试，这是已知限制（见 §7-D19）。

**反向禁区（内部同样适用）**：不得把「桩上能查到冲销」表述为「回滚可审计 / 回滚闭环已完成」。对外只能说「能核对冲销结果」，不能说「审计意义上的回滚闭环」。

### 5.2 客户要拿什么数据

- 供应商对账单：覆盖约定期间的全部行，含单据号、行号、物料、数量、单价、金额、税率。

- 上期已确认的对账结果：用于判断「引擎结论与人工结论是否一致」。
- 至少覆盖这些形态的样本（数量由协议约定，本文不预设）：零差异、单价差异、数量差异、舍入差、缺单、重复计费、匹配歧义、不可解析行。
- **数据交付方式（v0.9 续，仅内部）**：本期的对账输入是**请求内联 `dataset`**（或已登记数据集）。文件通道**未接线、当前不可用**：网关无对外读端点、api 未 ingest、`our_lines` 无来源，带 `statement_files` 只会得到 `DATA_MISSING`；CSV 解析能力只在分支、未接运行期。因此客户给的对账单需要我方先整理成行级数据集再跑，不能承诺「上传文件即对账」。演示与 POC 报告都不得写成「已接供应商系统 / 自动拉数 / 已支持对账单文件导入」。

### 5.3 跑几步

| 步 | 动作 | 接口 / 产物 | 观察点 |
|---|---|---|---|
| 1 | 数据体检与口径确认会 | 会议纪要 + 口径确认单 | 哪些行算、哪些不算，双方先签字 |
| 2 | 配置主数据、单价、封顶、上期累计 | 环境变量 / 配置 | 单价来源必须是配置，不是口头价 |
| 3 | 发起对账 | `POST /v1/recon/runs` | 201；返回 `batch_id`、`batch_status`、`metrics` |
| 4 | 看批次状态 | `GET /v1/recon/runs/{batch_id}` | 是否有 `missing_items`；是否「无法对账」 |
| 5 | 看差异 | `GET /v1/recon/runs/{batch_id}/diffs`（可按 `billing_bucket` 过滤） | 计数与列表是否一致 |
| 6 | 出计量表 | `GET /v1/metering/batches/{batch_id}/statement` | 四桶之和 = `expected_lines`；`data_gaps` 逐条可见 |
| 7 | 导出 CSV 并校验 | `...?format=csv` + `X-Content-SHA256` | 离线 sha256 一致 |
| 8 | 人工抽样复核 | 双方复核记录表 | 逐行判定「自动放行是否正确」 |
| 9 | 争议演练 | 线下确认单 | 模拟 1 行「已确认错放行」，走次月调整 |
| 10 | 出 POC 报告 | 报告 | 只写实测事实，不写未测量准确率 |

### 5.4 达到什么算通过

以下 6 条**全部满足**才算通过：

| # | 通过条件 | 判定方式 |
|---|---|---|
| P1 | 批次能出明确结论：`已对账` 或 `待人工复核`；若为 `无法对账`，必须给出可执行的 `missing_items` 清单（该情形按 §5.6 归为数据/前置问题，不算产品通过） | 接口返回 + 报告 |
| P2 | 口径自洽：`billable + dispute_hold + other_unbillable = expected_lines = 供应商侧明细行数`（`auto_released` 桶取消后的合计式；合入前为 `billable + auto_released + dispute_hold + other_unbillable`，其中 `auto_released` 恒 0） | 计量表 `line_accounting` + 逐行计数复核 |
| P3 | 可复算：`billable_lines × unit_price = period_amount`（4 位小数），CSV 摘要校验一致 | 手工复算 |
| P4 | 可追溯：每条 `billable` 行都有 `evidence`，或带可解释的自动归因 `diff_type` | 逐行抽查 |
| P5 | 抽样复核：自动放行行的错误率 ≤ **POC 协议书面约定的阈值** | 双方复核记录 |
| P6 | 对客户真实系统零外部写入：计量与对账链路连接器 `writes = 0`、`previews = 0`；演示环境的写路径若开启，只允许指向仓库内模拟桩，并以 `/stub/requests` 条数自证（W3 被拒时应无新增）。**一旦有请求指向任何真实客户系统，即判不通过**（见 §4.3） | 接口/审计记录 + 桩账本 |

关于 P5：**本文不给默认阈值。** 真实数据准确率当前「未测量」（见 §6.3），任何 95% / 97% / 99% 的数字都没有证据。POC 前由双方按样本量书面约定阈值；未约定则不把 P5 当作通过项，只做描述性统计。

### 5.6 不通过怎么办

| 情形 | 判定 | 处理 |
|---|---|---|
| 主数据缺失、行不可解析导致无法出结论，且 `missing_items` 指向数据/前置问题 | 不算产品不通过 | 限期修数后重跑；重跑生成新批次，不算新争议 |
| 双方对某类行是否计费口径不一致 | 不算产品不通过 | 停跑，先签补充口径；未签前该行不计费 |
| 计数与明细不一致、同一批次两次读取结果不同、批次无法出结论且无明确数据原因 | 产品缺陷 | 我方修复后免费重跑一次；仍不通过，客户可终止 POC |
| 抽样错误率超协议阈值 | 效果不达标 | 不进入计费；按 `docs/product/05-商业模式与路线图.md` §3.1 的约定执行（免费延期或退款，具体以合同为准） |
| 发生指向**客户真实系统**的外部写入 | 立即停 | 按安全事故流程处置；POC 直接判不通过。写在本地模拟桩上不算（桩账本可查、`X-Simulated-System` 头可验） |
