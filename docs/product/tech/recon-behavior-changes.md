## 0. 结论速览

这批改动里**没有可以按「仅类型新增」豁免的引擎改动**——六项全部改变对账输出。真正的「仅类型新增」只有枚举值与可选字段（见第 3 节），但它们会出现在 `to_dict()` 输出里，下游白名单需同步。

| # | 变更 | 性质 | 改变输出？ | 影响已承诺口径？ | 方向 |
|---|---|---|---|---|---|
| 1 | 解析降级：`unparseable` 行整批转人工、不抛异常 | 行为变更（P0） | 是 | **是，且是兑现承诺** | 异常出口 → 结构化降级 |
| 2 | 单位守门对直配层生效 | 行为变更（P0，收紧） | 是 | **是，属预期收紧（§5.5）** | 自动放行减少 |
| 3 | 重复计费键改为「同供应商+期间+单据号+物料」 | 行为变更（识别面扩大） | 是 | 是（更严） | 重复识别增加，**无回流** |
| 4 | 新增聚合匹配层（拆单/合并） | 行为变更（新增放行路径） | 是 | 是，计费口径已定（§5.2） | 自动放行增加（仅拆单） |
| 5 | 评分前先做单位换算 | 行为变更（识别能力） | 是 | 是（不扩大放行风险） | 误判减少 |
| 6 | 新增「金额舍入容差」类别 | 行为变更（新增放行类别） | 是 | 是，计费口径已定（§5.3） | 自动放行增加 |

**三问直答**

- (a) `unparseable` 行：**已实现「整批转人工、不向外抛」**。改动前是抛 `ValueError` 打断整批；改动后该行状态=`不可解析`、从匹配中摘出、整批 `待人工复核`，同单号同行号的对手行一并摘出（避免误报缺单），其余行照常对账，不静默当 0。
- (b) 单位守门 + 置信度封顶 0.65：**跨单位不再自动放行**。改动前直配层只看单据号，`100 BOX` 与 `100 PCS` 会以 1.00 自动放行；改动后必须命中主数据换算且换算后**数量与金额同时闭合**，否则 `min(score, 0.65)`，只给候选、原因码 `[UNCONVERTIBLE]`，走 `候选待人工`。
- (c) 重复计费键改四元组：**原本被判重复的单据不会被重新计入**。旧键（7 字段全等）命中的行，新实现第二维度仍按同一组字段判 `exact`。实测三套夹具「旧有新无」为空集（见 2.3）。

## 1. 逐条明细

### 1.1 解析降级：`unparseable` 整批转人工、不抛异常（P0-2）

| 项 | 内容 |
|---|---|
| 改动前 | `loader.build_request` 直接调 `to_decimal`，脏值抛 `ValueError`，调用方拿不到 `ReconResult`，整批对账失败 |
| 改动后 | 逐字段 `try/except`，记 `ParseIssue{ref, side, field, raw}`；该行（及同单号同行号对手行）从匹配中摘出；行状态 `不可解析`；`manual_line_count` 计入该行数；批次 `待人工复核`；其余行照常对账 |
| 输出差异 | 抛出异常 → 返回结构化结果；差异行数、待人工行数、批次状态全部随之变化 |
| 对外承诺口径 | **兑现既有承诺**，不新增口径：`unparseable` 行「整批转人工、不向外抛」是已对外承诺的行为。新增的是「对手行一并摘除」与「该行必进待人工计数」 |
| 风险 | 整批不可能再自动放行（只要有一行不可解析）；这是刻意的安全选择 |
| 证据 | 对抗集 `adv_unparseable` 2 行：auto 0/2，批次 `待人工复核`；训练集/留出集指标不变 |

### 1.2 单位守门对直配层生效（P0-1）

| 项 | 内容 |
|---|---|
| 改动前 | 直配只判 `同供应商 + 同单据号`，`same_line[0]` 直接取用，置信度 1.00；单位不参与判定 |
| 改动后 | 直配也要过 `unit_guard`：单位不同（仅忽略空白/大小写）必须命中主数据换算，且**换算后数量与金额同时闭合**；否则不直配，交模糊配生成候选，`_score` 中 `min(score, 0.65)` 封顶 → `候选待人工` |
| 输出差异 | `100 BOX` vs `100 PCS` 这类行：由 `已匹配 / exact / 1.00` → `候选待人工 / candidate / ≤0.65` |
| 对外承诺口径 | **影响**。自动放行率会下降、待人工上升，属口径收紧。这是安全修复（换算系数错一位会静默算错钱），需要在验收结论里明确写「该下降是预期，不是回归」 |
| 证据 | 对抗集 `adv_unit_mismatch` 1 行：auto 0/1，原因码含「单位不一致…[UNCONVERTIBLE]」；训练集 375 行 auto 无回归（375/375） |

### 1.3 重复计费键改为「同供应商+期间+单据号+物料」（含冲突列）

| 项 | 内容 |
|---|---|
| 改动前 | 7 字段全等去重：`(供应商, 期间, 物料, 单位, 数量, 单价, 金额)`；同单号下被改过一行（如单价 10→10.2）不会被识别，反而落成「缺单」 |
| 改动后 | 两个维度：① 同 `(供应商, 期间, 单据号, 物料)` 的第 2 行起一律判 `重复计费`，内容不同则标 `conflict` 并逐列写出冲突（如「单价 10.0000→10.2000」）；② 跨单据号的 7 字段全等仍判 `exact` |
| 输出差异 | 重复行变多；原本误判为「缺单」的行改为「重复计费」并附冲突列 |
| 对外承诺口径 | 影响，方向更严：不该付的钱被拦下，不涉及放宽 |
| 证据 | `duplicate_same_doc` 0/5 → 5/5；训练集重复行 **旧 5 → 新 10**；留出集 **旧 2 → 新 3**；对抗集 0 → 0 |

**关于 (c)「原本被判重复的单据是否会被重新计入」——不会，实测为空集：**

| 夹具 | 旧实现判重复行数 | 新实现判重复行数 | 旧有新无 |
|---|---|---|---|
| golden_500 | 5 | 10 | 空集 |
| golden_holdout | 2 | 3 | 空集 |
| golden_adversarial | 0 | 0 | 空集 |

口径说明：仅统计「可对账批次」（`metrics is not None`）。整批 `无法对账` 的批次两版都不进入匹配，不产生重复行，计入会得出假的「回流」。新增的 5 行（训练集）全部是旧实现漏掉的「同单号内被改动」的二次列示。

### 1.4 新增聚合匹配层（拆单 / 合并）

| 项 | 内容 |
|---|---|
| 改动前 | 只做一行对一行；拆单的第二行必然落成「供应商未匹配」 |
| 改动后 | 多对一（拆单）：同供应商+物料+期间+单位的合计与单行**数量与金额同时闭合** → 自动放行，`match_type=aggregated`、带 `aggregate_refs`；一对多（合并）：一律 `待人工`，拆分口径不唯一 |
| 输出差异 | 拆单场景由缺单 → 已匹配（aggregated）；合并场景新增待人工行 |
| 对外承诺口径 | 影响，已按 §5.2 定口径：计费以行为单元，批次未放行不影响该行计费；仅限「合计双闭合」且可区分直配与聚合 |
| 证据 | `split_invoice` 5/10 → 10/10；`merged_billing` 5/5 仍待人工 |

> 注：`split_invoice` 的 10 行行级 auto 为 1.00，但「批次闸门后放行」为 0——它们所在的 B08 同时含合并账单，整批被合并口径拉成 `待人工复核`。按 §5.2 已定口径，这 10 行**照计**，计费不以批次放行为前提。

### 1.5 评分前先做单位换算

| 项 | 内容 |
|---|---|
| 改动前 | 直接用供应商原始数量/单价算相似度，单位差异把分数压到 0.55 左右 → 恒为候选 |
| 改动后 | 先按主数据换算到我方单位口径再比（数量 ×factor、单价 ÷factor）；换算不可得按中性 0.50 降权，并在 `Candidate.reason` 区分「不可换算」与「相似度低」 |
| 输出差异 | `uom_conversion` 场景由候选 → 已匹配；候选原因文案变化 |
| 对外承诺口径 | 影响，但不放宽闸门：换算闭合才可 ≥0.70，不闭合走 1.2 的封顶 |
| 证据 | `uom_conversion` 10/20 → 20/20；训练集无回归 |

### 1.6 新增「金额舍入容差」类别

| 项 | 内容 |
|---|---|
| 改动前 | 金额差 0.01~0.05（按角取整）无类可归 → `unattributed` → 批次待人工 |
| 改动后 | 单行 ≤ `tolerance.rounding`（默认 0.05 元）且整批累计 ≤ `rounding_batch_limit`（默认 1.00 元）且累计占比 ≤ 0.005 时，记 `DiffType.ROUNDING_TOLERANCE`，**不生成差异单、不计入差异金额与差异率**，批次可自动放行；超限则 `rounding_escalated=true` → 待人工 |
| 输出差异 | 差异明细多一类；差异金额/差异率不再包含舍入差；批次由待人工 → 已对账 |
| 对外承诺口径 | **影响，已按 §5.3 定口径**：舍入容差行已放行、未生成差异单，但**计入有效对账行**；「不计入差异率」会改变对外披露的差异率口径 |
| 证据 | `rounding_diff` 0/20 → 20/20；B05 由待人工 → 已对账，理由写明「20 行金额舍入差 0.2170 元在容差内已放行」 |

## 2. 仅类型 / 枚举新增（不改变引擎判定逻辑）

以下不改变任何判定，但**会出现在 `to_dict()` 输出**中，属「向前兼容新增」；严格按字段白名单消费的下游（API Schema、报表、计费）必须同步，否则会报未知枚举值或丢字段。

| 新增 | 位置 | 影响下游 |
|---|---|---|
| `LineStatus.UNPARSEABLE = "不可解析"` | `models.py` | 新增状态值，`status` 白名单需加 |
| `DiffType.ROUNDING_TOLERANCE = "金额舍入容差"` | `models.py` | 新增差异类型，`type` 白名单需加 |
| `MatchType.AGGREGATED = "aggregated"` | `models.py` | 新增匹配类型 |
| `ParseIssue` | `models.py` | 请求侧新增 `parse_issues` |
| `Candidate.reason` | `models.py` | 序列化新增 `reason` |
| `MatchResultLine.aggregate_refs` | `models.py` | 序列化新增数组，默认 `[]` |
| `ReconMetrics.rounding_lines / rounding_amount / rounding_escalated` | `models.py` | 序列化新增三个指标 |
| `Tolerance.rounding / rounding_batch_limit` | `models.py` | 入参可选，默认 0.05 / 1.00 |

注意：`DiffType` 的七类归因口径未变，`ROUNDING_TOLERANCE` 是**容差调整类**，不属于七类，也不计入归因准确率。

## 3. 自动放行率（金标准集实测）

### 3.1 口径定义

| 口径 | 定义 |
|---|---|
| 批次级 | `batch_status=已对账` 且 `metrics.auto_disposal_allowed=true` |
| 行级 auto | `status=已匹配` 且 `match_type∈{exact, fuzzy, aggregated}` 且 `needs_manual=false`（含已自动归因的差异行） |
| 行级 clean | 行级 auto 且 `diffs` 为空（真正零差异）；**仅作内部质量指标，不作计费基数** |
| 对账行总量 | 从分母中剔除整批 `无法对账` 的行（引擎未做任何匹配）；**计费基数为其中的行级 auto（§5.1）** |
| 批次闸门后 | 行级 auto 且所在批次已自动放行；仅作对照，**不作计费口径（§5.2）** |

### 3.2 汇总

### 3.4 取数纪律

- 三组夹具**全部为自造、与标注同源**，任何一组都不构成泛化证据，**均禁止对外引用**。其中对抗集的 `7/10` 是 10 条构造样本的**自动放行率**，只证明「该放行/该转人工」的判定成立，不能当准确率、不能当产能承诺；对外统一回答「**真实数据准确率尚未测量**」。
- 训练集数字尤其不得引用（夹具与标注同源，满分无意义）。
- 留出集是从冻结夹具按单据组切出的子集，逐行规则确定，任何子集判定相同，**不能替代真实新数据**；它只能证明规则没有按单据过拟合。

- 上述数字全部来自当前代码实测（`1d759af`），未做四舍五入美化，分母用「标注期望行」，不用引擎实际产出行。

## 5. 计费口径（已定）

### 5.1 有效对账行 = 行级 auto，含已自动归因的差异行

- **定义**：`status=已匹配` 且 `match_type∈{exact, fuzzy, aggregated}` 且 `needs_manual=false`；包含 `price_diff` / `rounding_diff` / `tax_basis_diff` / `tax_rate_diff` / `scrap_not_deducted` 等「有差异但已被自动归因」的行。统计分母为对账行总量（剔除整批 `无法对账` 的行）。
- **决定理由**：这些行是引擎的实际产出——配对、比价、归因、证据链齐全，人工接手成本已被消除；clean 为 0 只说明「这批业务本来就有差异」，不代表没干活。
- **明确不采纳**：**不以 clean 作为计费基数**。clean 仅作内部质量指标（衡量输入干净度与识别稳健性），不进入合同。
- 对应数字（受 §3.2 禁令约束，仅内部核对）：训练集 375/400 = 0.9375、留出集 163/172 = 0.9477、对抗集 7/10 = 0.7000；clean 口径分别为 0.7150 / 0.7965 / 0.6000。

### 5.2 批次未放行但行已自动匹配的，照计

- 计费单元是**行**，不是批次。批次 `待人工复核` 只表示该批仍有未决项，不影响其中已自动匹配行的计费。
- 典型例：`split_invoice` 10 行——所在 B08 因同批含合并账单整批转人工，这 10 行**照计**。
- **合同兜底句（原样写入合同/计费附件）：「计费不以批次放行为前提。」**
- 对应数字：训练集 375 行（批次闸门口径 310 行，+65）、留出集 163 行（原 147，+16）、对抗集 7 行（不变）。

### 5.3 舍入容差行计费

- `DiffType.ROUNDING_TOLERANCE` 行已自动放行、未生成差异单，**计入有效对账行**。
- 理由：该类行已完成配对与金额校验，差额落在按角取整的物理误差内，结论与 clean 行等价，仅多一条可审计的容差留痕。
- 对应数字：训练集 `rounding_diff` 20 行、留出集 4 行计费；若整批累计超 1 元或占比超 0.5%，`rounding_escalated` 转人工，不计费。

### 5.4 反向减项

- 只认两类，**按行扣减**：`confirmed_wrong`（自动放行结论经复核确认错误）、`customer_reason`（客户侧原因导致该行无效）。
- **系统性错误不逐行扣减**，走整体追溯（整批重跑 / 退费），避免逐行扣减掩盖系统性问题。
- **实现状态（如实说明）**：`apps/recon/` 当前不产出这两个标记，`models.py` 中无对应字段；它们属于复核/结算流程的回填字段，需由计费服务侧实现，不在本次代码范围。
