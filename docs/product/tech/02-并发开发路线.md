## 1. 契约先行：冻结什么，什么时候冻结

### 1.1 为什么必须先行（不冻结会发生什么）

| 不冻结的后果 | 在本项目里的具体表现 |
|---|---|
| 数据模型各自演进 | 对账引擎按 `qty` 写、连接器按 `quantity` 供，集成时全量重命名；统一模型是 5 个主对象的公共底座（02 §2.2），改动波及全部流 |
| 工单契约后补 | 运行时用 `state=3`，前端按 `state="执行中"` 渲染，审计表用另一个枚举；状态机是 PRD §5.0 固定的 12 态，必须一次对齐 |
| 等级语义漂移 | 连接器声明 W2、场景声明 W1、运行时按 W2 执行 → 直接违反 G-03/FR-1406，且这类 bug 在功能测试里看不出来 |
| 错误码不统一 | 前端「Agent 失败」态要按 F1–F8 给不同下一步（PRD §6.3），错误码各写各的会让 7 个页面各做一套映射 |
| 目录不分 | 两条流同时改 `apps/api/main.py`、`db/migrations/`、`shared/canonical/`，每天都要人工解冲突 |

### 1.3 冻结后的变更纪律

| 变更类型 | 允许窗口 | 流程 | 代价 |
|---|---|---|---|
| 新增可选字段 / 新增错误码 | 随时 | 提 PR，Owner + 集成负责人任一审 | 低（消费方可忽略） |
| 新增必填字段 / 改语义 | 每周一次「契约窗口」（周三） | RFC：动机 / 影响流 / 兼容方案 / 迁移步骤 / 回滚方案 | 中（所有消费方当天适配） |
| 破坏性变更（删字段、改枚举、改等级） | 仅阶段边界 | RFC + 全部 Owner 签字；或用 `v2` 并存（NFR-D-05） | 高，需重排里程碑 |

判定标准只有一条：**消费方不改代码能否正确运行**。不能 → 属于第二/三类。

## 2. 工作流拆分

八条流（S0–S7）+ **一条部署横切流 S8**。每条流都是「一个人能从头讲到尾」的垂直切片，交付物可独立验收（不需要等其它流合并就能证明自己对了）。

### 2.0 全流共享的目录约定

```
repo/
  core/            S0 独占（policy / kernel / config / tenancy）
  core/runtime/    S3 独占
  core/audit/      S4 独占
  core/iam/        S4 独占
  shared/          S1 独占（canonical model）
  connectors/      S1 独占（sdk + 各厂商实现）
  domain/recon/    S2 独占
  domain/metrics/  S2 独占
  domain/docparse/ S5 独占
  agents/          S3 独占（AG-1/AG-2 执行器）
  apps/api/main.py, deps.py, routers/__init__.py   S0 独占
  apps/api/routers/<stream>.py                    各流独占自己的路由文件
  web/             S6 独占
  integrations/im/ S6 独占
  observability/   S7 独占（埋点规范、看板定义、告警规则）
  deploy/smart-erp/  S8 独占（docker-compose + profile + .env.example + db/00-provision.sql + 运维手册）
  scripts/         S8 独占（release.sh / bundle.sh / preflight.sh / backup-restore.sh）
  projects/smart-ERP/docker/  S8 独占（4 个 Dockerfile 与 .dockerignore）
  .github/workflows/smart-erp.yml  S8 独占（其余 workflow 归 S0）
  db/migrations/   S0 合并权，各流只提文件
  contracts/       冻结物，只按 §1.3 变更
  tests/           contract(各流) / golden(S2/S3) / fault(S3/S4) / e2e(S7) / deploy(S8)
```

> `deploy/` 拆成两半：**容器与发布归 S8**，**可观测配置（Grafana dashboard JSON、告警规则、OTel collector 配置）归 S7**，物理上分别是 `deploy/smart-erp/` 与 `observability/`，互不改对方目录。

### 2.1 S0 平台底座（Kernel & Policy）

| 项 | 内容 |
|---|---|
| **范围** | FastAPI 骨架、配置与多租户、认证（OIDC+本地）、`ScopeGuard`、RLS、`WriteGateway` 与等级取严、`ActionRegistry`（签名校验）、审批满足性判定、SoD 策略、配置变更审计、迁移链维护、CI/代码生成、契约测试框架与 fake 服务 |
| **独占目录** | `core/policy/`、`core/kernel/`、`apps/api/main.py`、`apps/api/deps.py`、`db/migrations/`（合并权）、`contracts/openapi.json`（生成物）、`.github/` |
| **依赖** | 无（唯一无上游的流） |
| **可独立验收** | ① `pytest tests/policy` 覆盖：W3 注册被拒、取严公式、字段 scope、自审被拒（DB CHECK）、无补偿 W1 被拒；② `import-linter` 契约通过（连接器 transport 不可被外部导入）；③ 一条 `curl` 能跑通登录→建工单→fake 预演→审批→fake 写入→审计；④ 迁移链 `alembic upgrade head` 在空库与旧库均可 |
| **风险** | 它是最强依赖，一旦延期全组停摆 → 阶段 0 只做**最小可运行**，不做完整体 |

**S8 的位置说明**：它不是「最后才做的打包流」，而是**从 W1 就开始供给环境的横切流**——G0 的判据「一条命令起栈」必须由 S8 交付；之后每个里程碑的云上/客户侧演示都由 S8 执行发布。把 S8 画在底部只表示「其它流依赖它的产物」，不表示时间顺序。

**必须串行的六段（它们不是人力问题，是物理约束）**：

| 串行段 | 原因 | 谁等谁 |
|---|---|---|
| 契约冻结（C1–C5/C10/C11/C12/C14/C15）→ 任何业务代码 | 契约未定，业务代码写两遍 | S1/S2/S3/S4 等 S0 的 G0 |
| 迁移链 | 单库单线性链，两个迁移同时合并必然冲突 | 全部流等 S0 的合并窗口 |
| `WriteGateway` → 任何写路径 | 写路径唯一出口，早于它写的代码都要重写 | S3/S4 等 S0 的 `core/policy` |
| 埋点规范 → S3 第一行业务代码 | 事后补 trace 会把状态机代码翻一遍 | S3 等 S7 的 OTel 规范（W2 末给） |
| **镜像 tag → 任何一次云上演示** | 演示必须能指名「跑的是哪个 sha」；tag 不可变是回滚的前提 | 全部流等 S8 的 tag 登记（§4.7） |
| **共用实例开通（C14）→ 第一次连真库** | `erp_app`/`erp` schema/`vector` 扩展由实例 owner 执行，属外部依赖 | S0/S8 等外部窗口（01 §1A.7.1） |

**可以真并行的证据**：S2 与 S1、S3、S4、S5 之间只通过 Canonical 对象与结论结构耦合，输入是「样本夹具」；S6 与所有后端只通过 OpenAPI 耦合；S5 与 S1 只通过 `read()` 耦合。这三条是首批可以立刻开跑的。

### 4.3 接口变更流程（RFC）

```
1. 在 contracts/rfc/NNNN-<slug>.md 写：动机 / 影响的流 / 兼容方案 / 迁移步骤 / 回滚方案
2. 关联 PR 只改 contracts/（不改实现），先让消费方看到「将要变什么」
3. 48 小时内无异议 → 合入契约；同时在 contracts/CHANGELOG 记录版本
4. 实现 PR 引用 RFC 编号；实现期间旧字段保留（双写/兼容读）
5. 兼容窗口结束（≥1 个契约窗口）后删除旧字段
```

红线：**任何流不得在自己的实现里「先按新契约写」，再回头要求契约改**。契约是先行条件，不是事后追认。

### 4.4 共享模型与迁移的特别约定

| 问题 | 约定 |
|---|---|
| 两个人同时加枚举值 | 枚举值只允许追加到末尾，禁止重排（影响 DB 存储与前端映射）；追加需在 PR 描述里列出「新增值 + 使用方」 |
| 两个人同时加索引 | 索引命名 `<table>_<cols>_idx`，S0 在合并窗口查重并合并为一个迁移 |
| 两个人同时改同一张表 | 由 S0 拆分：先合「加列（可空）」迁移，再各自合「用列」的代码；禁止在同一个迁移里既改表又改数据 |
| 数据回填 | 一律独立迁移脚本 `backfill_xxx.py`，可重入、可中断、带进度日志；不放在 schema 迁移里 |
| 测试数据 | 样本夹具放 `tests/fixtures/<stream>/`，各流独占子目录；共享金标准放 `tests/golden/` 由 S2 维护 |
| **共用实例上的迁移** | 一律**显式写 schema 前缀**（`op.create_table("t", ..., schema="erp")`）；`env.py` 设 `include_schemas=False` + `version_table_schema="erp"` + `version_table="alembic_version_erp"`；`ALTER TABLE` 前先 `SET lock_timeout='3s'`；CI 断言「非 `erp` schema 对象变化 = 0」；加锁 >1s 的变更走 §4.8 窗口审批 |
| **方言约束（PG15）** | 禁止 PG16 独有语法（`any_value()`、`json_arrayagg/json_objectagg`、`pg_stat_io`、`random_normal()`、`MERGE ... RETURNING`）；CI 用 `postgres:15-alpine` 跑迁移，误用即失败 |

### 4.5 分支与 PR 策略

| 项 | 规则 | 理由 |

| PR 大小 | ≤400 行有效变更（不含生成物/迁移） | 超过则评审质量断崖 |
| 评审 | 至少 1 名**非本流** reviewer（跨流视角）+ 独占文件 Owner | 防「自己流的假设变成别人的 bug」 |
| 主干保护 | CI 全绿才可合：lint / mypy / pytest / **import-linter** / **contract-diff**（OpenAPI 与 schema 破坏性检测）/ 迁移链可升可降 | 契约破坏在 CI 就拦，不靠人眼 |
| 每日 | 1 次 15 分钟集成同步（只讲：契约变更、阻塞、联调环境占用） | 并行流之间唯一的同步成本 |

### 4.6 compose / CI / Dockerfile 的归属与申请

**谁能改**：只有 **S8 owner** 能改 `deploy/smart-erp/`、`scripts/`、`projects/smart-ERP/docker/`、`.github/workflows/smart-erp.yml`。其他人一律提 PR 由 S8 合，且 PR 必须说明「为什么要动部署面」——和改他人业务目录同一条规则（§4.1）。

| 需求 | 流程 | 时限 |
|---|---|---|
| 业务流需要一个新的环境变量 | 提 PR 改 `.env.example` + `contracts/config.schema.json`（C11），写明必填/默认/敏感/是否启动期只读 → S8 审 → 同步在 compose 的 `env_file` 生效。**这是唯一路径，运行时无入口**：79 键中 78 个 `phase=startup`，进程只读一次，HTTP 写进去不会改变任何行为 | 1 个工作日 |
| 业务流需要一个新的镜像层内依赖 | 提 PR 改 `docker/<comp>.Dockerfile` 的依赖清单；**禁止**在业务代码里 `pip install` 运行时依赖 | 1 个工作日 |
| 需要开放一个新容器/端口 | 走 §4.7 的端口申请；新容器同时要更新内存预算表（01 §1A.3）与 `compose config` 快照 | 需 S8 + 集成负责人双批 |
| 需要新增 profile | 只允许 `demo/full/ops/self-db/cache/obs` 之外的 profile 经 RFC 批准；profile 数量是**复杂度预算**，不是越多越灵活 | RFC（§4.3） |
| CI 需要新增检查项 | 只在 `smart-erp.yml` 加 job；**不允许**动 `hogo-qa.yml`（属 hulkai 既有资产） | 1 个工作日 |

**CI 必须通过的部署类检查**（写进 `smart-erp.yml`，失败即不可合并）：

1. `docker compose --profile demo config` 能被解析，且**不含** `pg`/`redis`/`doc`/`minio`；
2. 缺少任一必填 `ERP_*` 变量时，`config` 必须失败并指出变量名（证明 C11 的 `:?` 生效）；
3. 4 个 Dockerfile 均可构建（PR 阶段只构建 `app` 与 `web` 控制时长，`doc` 在 nightly 构建）；
4. 镜像内不存在编译期依赖（`gcc`/`build-essential`）与非 root 之外的运行用户；
5. `contracts/release/` 的 tag 规则与 `compose` 里 `${ERP_IMAGE_TAG:?}` 一致（字符串级校验，防有人改回 `latest`）。

### 4.7 镜像 tag 与端口申请（唯一登记处）

**镜像 tag 规则**（C12）：`ERP_IMAGE_TAG` = 完整 40 位 git sha，一次性写入 `deploy/smart-erp/RELEASES.md`（**谁发布谁登记**）：

| 字段 | 内容 |
|---|---|
| tag | 完整 git sha |
| 构建机 | 谁在哪台机器构建（本地/CI） |
| 产物 | `erp-images-<sha>.tar.gz` + `sha256sum.txt` 的校验值 |
| 部署环境 | 本机 / 云上 demo / 客户 X |
| 回滚目标 | 上一个 sha |
| 时间 | 部署时间（含时区） |

- **tag 一经发布不可复用**（禁止「同一个 sha 重新构建覆盖」——构建不可复现会让回滚失去意义）；
- 未登记的 tag 不允许出现在任何演示环境；
- 不建镜像仓库的代价是「服务器上必须保留上一版镜像」，因此要求**至少保留最近 2 个 sha 的镜像**，清理前先确认回滚目标。

**端口登记表**（`deploy/smart-erp/PORTS.md`，申请制）：

| 端口 | 归属 | 状态 |
|---|---|---|
| 8010 | `erp_api` | 已分配（仅香港反代源 IP） |
| 8088 → 8080 | `erp_web` | 已分配（仅香港反代源 IP） |
| 8012 | `erp_gw` | 已分配（`expose` only） |
| 8004 / 8085 / 8080 / 8788 / 9010 / 9011 | hulkai 既有（mfg / APS） | **禁止复用** |
| 80 / 443 | hk-web Nginx + certbot | **禁止复用** |

申请流程：填「用途 / 需要宿主端口还是仅内网 / 谁访问 / 是否长期」→ S8 查表确认不冲突 → 更新 `PORTS.md` 与 `compose` → 同步 01 §1A.4 的端口表。**端口冲突是并入类事故里最难排查的一类**（表现为「另一个服务偶发 502」），所以宁可申请慢一天。

### 4.8 共用 PG 实例的迁移与变更审批

**为什么单列**：迁移一旦作用在共用实例上，影响面超出本项目（APS 与 mfg 同实例）。所以它的审批链比普通 PR 长，这**不是流程冗余**，是把「我们改坏了别人的库」的成本前移。

| 变更类型 | 审批 | 窗口 | 前置 |
|---|---|---|---|
| 新增表/列/索引（`erp` schema 内，加锁 <1s） | ERP 负责人 | 随时（合并窗口内） | CI 的「非 `erp` 对象变化为 0」断言通过 |
| `ALTER TABLE` 可能加锁 >1s（含 `CREATE INDEX` 非并发） | ERP 负责人 + **实例 owner** | **周二/周四 21:00–22:00** | 先在等量数据副本上测耗时；给出回滚语句 |
| 大表索引（必须 `CONCURRENTLY`） | 同上 | 同上 | 拆两个版本：先建索引（`CONCURRENTLY`、独立迁移），后启用 |
| 需要新扩展（如 `pgvector` 升级） | ERP 负责人 + 实例 owner + **APS 负责人** | 同上，且避开 APS 发布日 | 实例 owner 在维护窗口执行；我们只提交 `db/00-provision.sql` |
| 需要改 role/权限/连接数上限 | 同上 | 同上 | 同时更新 C14 与 01 §1A.7.1 |
| 触碰 `erp` 之外的对象 | **禁止** | — | 直接拒绝，不存在审批路径 |

**禁止窗口**（写进 `deploy/smart-erp/README.md`）：每月最后 3 天（月结）、APS 发布当天与次日、ERP 自身影子运行/灰度期。**窗口冲突时以实例 owner 的排期为准**（我们是共用的新住户，不是主人）。

**没批准怎么办**：迁移 PR 挂 `blocked:db-window` 标签，代码可先合入但不部署；**不允许**绕过窗口在业务高峰跑迁移（这是「先污染后治理」的起点）。

## 6. 并行度评估

### 6.1 合理上限

| 指标 | 建议值 | 依据 |
|---|---|---|
| 阶段 1 并行流数 | **6 条业务流**（S1–S6）+ S0 半投入兼任集成负责人 + **S8 以横切方式半投入**（不计入「并行业务流」上限） | 超过 6 条**业务**流时，跨流契约变更与迁移冲突成为串行瓶颈（见 6.2）。S8 不同：它不产出业务功能、独占目录与业务流零重叠，且它的产出（镜像/compose）是所有流的公共前置——把它算进上限会得出「部署别做了」这种荒谬结论 |
| 工程师人数 | **7–10 人**（+1 相对 v0.1） | 每业务流最低 1.5 人：6×1.5 ≈ 9；S8 需要 0.5–1 人（W1–W2 半投入、W3 起视客户包进度加到 1 人）。若不增人，则由 S0 负责人兼任 S8 owner（**可行但会拖慢 G0**，因为 S0 在 W1–W2 是最忙的） |
| 单流人数 | 1–2 人 | 3 人以上在同一流内会重新产生目录冲突（等于把流内再拆一次，需要新的 ownership 表） |
| 集成负责人 | 1 人（专职，不写业务） | 负责契约窗口、迁移合并、联调环境排期、G 门验收；**新增职责：审核共用实例迁移窗口（§4.8）与端口/tag 登记（§4.7）** |

**并行度上限有没有变？结论：业务并行上限不变（仍是 6 条），但总人力从 7–9 抬到 7–10。** 原因：

1. **S8 不消耗「契约对齐带宽」**——它不与其他流共享 `contracts/` 的语义变更（只消费 C11–C15，且这 5 份由 S8 自己持有），所以不触发 §6.2 的「契约变更会议」瓶颈；
2. **但 S8 消耗「发布与窗口带宽」**——每次发布要占服务器、占迁移窗口（周二/周四 21:00–22:00）、占 hulkai 侧的 Nginx 变更排期。这条带宽是**新增的串行资源**，与「并行流数」不是一个维度；
3. 因此正确的做法不是「少开一条业务流」，而是**给 S8 配 0.5–1 人 + 把发布节奏固定为每周一次**（避免每天发版挤占窗口）。若强行把人压回 7 人且不设 S8 owner，实际后果是「每个流各自写一份 compose 片段」，这正是 §4.6 要防的事。

按 05 §5 的团队假设（后端与连接器 4、Agent/算法 4、前端 2、产品 2、实施 3）对照：**后端 4 人对应 S0+S1+S3+S4（每人一流）**，Agent/算法 4 人对应 S2（2 人）+ S5（1 人）+ S3 协作（1 人），前端 2 人对应 S6，S7 由 1 名后端兼。**S8 在这套编制里没有天然归属**，两个可选落法：①后端 4 人中指定 1 人 W1–W2 全力做 S8（S0 同时减少范围，推到 W3 补齐）；②实施/运维侧出 1 人（更贴近真实发布与客户交付，但需提前补 Python/Docker 能力）。**默认取 ①，因为 G0 的「一条命令起栈」是硬门。**

### 6.2 超过上限会发生什么（不是「慢一点」，是「开始返工」）

| 瓶颈 | 触发阈值 | 表现 | 缓解 |
|---|---|---|---|
| 契约变更会议 | 契约变更 >2 次/周 | 每次变更要 6 个 Owner 对齐，半天没了；且消费方刚写完就改 | 冻结门 + 每周固定窗口；只允许「新增可选」随时提 |
| 迁移链串行 | 同时待合并迁移 >3 个 | 每天 rebase 重编号，且容易产生「顺序依赖」隐性 bug | 每日两个合并窗口 + S0 拆分为「加列」与「用列」两次提交 |
| 联调环境争抢 | 客户测试账套 1 套 | 连接器/运行时/对账三条流互相覆盖测试数据 | 本地 fake + 每家客户一套专属账套 + 时间片预约（阶段 2 才需要） |
| 单体边界侵蚀 | `import-linter` 例外申请 >3 个/周 | 「临时 import 一下」，三个月后无法拆分 | 例外必须写明拆除日期；超过 2 周未拆则升级为架构债 |
| 评审带宽 | PR 平均等待 >1 个工作日 | 分支变长 → 冲突变大 → 等待更久（正反馈） | PR ≤400 行 + 每日固定评审时段 + 跨流 reviewer 轮值 |
| **部署面争抢（新增）** | `deploy/smart-erp/` 的 PR 涉及 >1 条流 / 周，或同一周内 2 次发布 | compose 变更互相覆盖、端口/变量名冲突、线上回到「谁最后改谁生效」 | §4.6 的申请制 + 每周固定一次发布窗口 + `compose config` 快照 CI 断言 |
| **共用库窗口争抢（新增）** | 同一窗口排了 >1 个加锁迁移，或与 APS 发布撞期 | 迁移被推迟 → 代码等库 → 后续流全部排队 | §4.8 的窗口表提前一周排；单窗口只允许 1 个加锁迁移 |

### 6.3 该看哪些指标来判断「并行是否健康」

| 指标 | 健康值 | 采集方式 |
|---|---|---|
| `main` 红时长占比 | <5% | CI 记录 |
| PR 从提交到合并中位数 | <1 个工作日 | 仓库统计 |
| 契约变更次数/周 | ≤2 | `contracts/CHANGELOG` |
| 迁移冲突次数/周 | ≤1 | 合并记录 |
| 跨流例外申请（import-linter / ownership） | ≤2/周，且无长期未拆 | PR 标签统计 |
| **部署失败率**（`up -d` 后未达 healthy 或触发回滚） | ≤10%，且每次有 RCA | `RELEASES.md` + 发布记录 |
| **回滚耗时** | ≤3 分钟（切上一 sha） | 演练记录 |
| **demo 栈常驻内存** | ≤1.5G（触发线 T1/T2 见 01 §1A.10） | `docker stats` 采样 |
| 集成检查点按期达成 | G0/G1/G2/G3 各 1 次，不延期 | 里程碑评审 |

**结论**：本项目是「契约敏感型」而非「人力密集型」。把并行度从 6 条提到 10 条，产出不会线性增加，因为瓶颈从「写代码」变成了「对齐契约与迁移」。宁可少开一条流，也不要在 G0 未达标时开跑。
