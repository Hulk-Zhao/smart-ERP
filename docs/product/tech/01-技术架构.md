## 1. 总体形态

### 1.1 结论

**模块化单体（Modular Monolith）+ Docker 容器组（4 个自有镜像 / full 最多 10 个容器）+ 单库单事务边界；云端并入 hulkai 同一台服务器、同一个入口域名下。**

- 一个代码仓（落在 hulkai 的 `projects/smart-ERP/`）、4 个镜像、最多 10 个容器；**不是**微服务，**不是**单体大应用。
- 边界按「开发流」划（见 [02-并发开发路线](./02-并发开发路线.md) §2），目录级 ownership，跨流只走 `contracts/` 与 `core/` 的冻结接口。
- 只有两处必须容器级隔离：**连接器网关**（安全沙箱，NFR-S-03）与**文档解析**（CPU/内存尖峰，NFR-P-03）；`scheduler` 必须单实例（FR-101/FR-1602）。
- 交付形态由「私有化 16C/64G 单机」改为**双形态同构**：客户私有化 = 一套 `full` profile；云端演示/自用 = 并入 hulkai 的 `demo` profile。两者镜像与 compose 文件完全相同，只差 profile 与 `.env`（NFR-D-01/03）。

### 1.2 服务（进程）划分与容器映射

| 容器 | entrypoint / 职责 | 镜像 | 副本 | 为什么单独一个容器 |
|---|---|---|---|---|
| `erp_api` | 控制面 REST + BFF：7 个界面、审批、工单查询、导出、连接器配置 | `smart-erp/app` | 2（full）/ 1（demo） | 与长任务隔离，避免月结批量把界面拖死（NFR-P-05 首屏 ≤1.5s） |
| `erp_worker` | 工单运行时：状态推进、LLM 判断、Saga 编排（demo 中把 io 类任务合并进来） | `smart-erp/app` | 2–4 | LLM 调用耗时长且不可控（NFR-P-04 ≤30s），不能占 API 事件循环 |
| `erp_worker_io` | 连接器读/预演/写的**编排侧**、批量取数、导出（仅 full） | `smart-erp/app` | 1–2 | 与 LLM 任务争抢 CPU/连接池会互相拖慢（NFR-P-02 ≤90min） |
| `erp_doc` | 文档解析流水线（pdfium 文本层 + 坐标；Phase 2 加 OCR 版面分析） | `smart-erp/doc` | 1（仅 full） | 内存/CPU 尖峰大（开启 OCR 后 PaddleOCR 常驻 1.5–2.5GB），崩了不影响工单（NFR-P-03） |
| `erp_scheduler` | 月末 D-3、每日 06:00、补偿重投、熔断巡检、哈希链校验 | `smart-erp/app` | 1（强制单实例） | 必须单点，否则重复触发批次（FR-101 幂等是兜底不是设计） |
| `erp_gw` | **出站唯一出口**：MCP Server + 策略执行点 + 限流 + 拦截记录 | `smart-erp/connector-gw` | 1 | NFR-S-03 要求只读根文件系统/资源限额；它是唯一持有目标系统凭据的容器（NFR-S-05） |
| `erp_web` | React 产物 + 自有 Nginx（SPA fallback、`/erp/` 基路径） | `smart-erp/web` | 1 | 需要 SPA fallback 与子路径重写；纯静态 alias 做不到（见 §1A.4） |

**数据库与缓存不再作为我们的容器**（v0.3 决策）：

| 依赖 | 形态 | 说明 |
|---|---|---|
| PostgreSQL **15** | **复用 hulkai 现有实例**（APS 的 PG15，内网 expose 5432） | 我们只建自己的 database/role/schema，详见 §1A.7 |
| Redis | **demo 不用**；full/私有化可选 `cache` profile | 队列改走 PG，缓存非必需，详见 §1A.7.3 |
| 对象存储 | demo 用宿主卷 + `LocalObjectStore`；full 用 MinIO（WORM） | 见 §1A.3 |

**镜像共 4 个（自有）**：`smart-erp/app`（api/worker/scheduler 共用，靠命令行区分）、`smart-erp/connector-gw`（独立，最小攻击面）、`smart-erp/doc`（含 OCR 模型，体积大、更新频率低）、`smart-erp/web`（多阶段构建产物）。理由：私有化交付只需分发 3 个 tar 包（doc 单列），升级是整体版本号（NFR-D-03），不需要处理多镜像版本矩阵。

> 变更说明：v0.1 的「6 类进程 + 共享一镜像」在 Docker 下仍成立，但拆出了 `erp-web`（原文档假设前端以静态文件托管），并把 `worker-doc` 更名为 `erp_doc`。`worker-agent` / `worker-io` 在 demo profile 合并为一个 `erp_worker`，full profile 才拆开——**合并只发生在编排层，代码与队列不变**。

### 1.3 进程模型与并发模型

| 层 | 模型 | 约束 |
|---|---|---|
| Web / 编排 | `asyncio` + `uvloop`，全链路 async | 事件循环内**禁止**同步 HTTP/DB/文件 IO（CI 用 `blockbuster` 类断言拦截） |
| 阻塞型调用（厂商 SDK、图片处理、PDF） | `asyncio.to_thread` + 有界信号量（每连接器独立配额） | 线程池大小 = 连接器并发上限，防止把 ERP 打挂（FR-109 默认并发 4、FR-1205 限流余量 <20% 自动降并发） |
| 批处理（对账匹配、导出） | 按「供应商 × 期间」分片，每片一个任务 | 分片键 = 幂等键前缀，天然去重（FR-109、G-02） |
| 事务 | 一工单一步一事务，**绝不跨外部调用持有长事务** | 步骤状态用「意图 → 结果」两次提交写（见 §3.1.4） |

**为什么不在事件循环里用同步 SQLAlchemy**：月结期间 100 批次并发取数，同步驱动会把线程池占满，表现为「界面卡、API 超时」；这是单机容器最容易踩的坑。

## 1A. 部署形态（v0.2 重写：Docker + 并入 hulkai）

### 1A.1 前提的变化：哪些结论仍成立，哪些作废

| v0.1 前提 | v0.2 处置 | 理由 |
|---|---|---|
| 「私有化 16C/64G/1TB 单机」是唯一交付形态 | **作废**，改为双形态：客户私有化（full）+ 云端（demo） | 云端落点是 hulkai 现有广州机：**4C4G / 60G SSD / 5Mbps / 129.204.108.45（Ubuntu）** |
| 「三处独立进程」 | **保留**（`erp_gw`、`erp_doc`、`erp_scheduler`），但独立的是**容器**而非主机进程 | 隔离诉求（NFR-S-03、NFR-P-03、FR-101）与部署方式无关；容器化后隔离成本更低 |
| 「单库单事务」 | **保留** | 工单/审计/幂等必须同库；与容器数量无关 |
| 「一套镜像 + 一个 compose」 | **保留并强化** | 合并进 hulkai 后更需要「一份 compose 两处跑」，只靠 profile 与 `.env` 区分 |
| 「离线包 = 镜像 tar + wheels」 | **保留**，并扩展为云端与私有化**同一条链路**：构建机 `docker save` → tar → `docker load` → `compose up -d`（服务器不编译，§1A.2/§1A.10） | 客户内网无外网，必须离线；云端 2 核要留给业务而不是编译 |

**现机实测余量（决策依据）**：CPU 1.48%、内存 1620MB/4GB、系统盘 15.9G/60G → 可用内存约 **2.3–2.4G**，可用磁盘约 **44G**，带宽 **5Mbps**。

**结论：第一版在现机落「演示精简档」，只起 5 个容器，常驻内存预算 1.17G（上限 1.5G）；数据库复用现有 PG15，full 形态只在客户私有化交付。** 三档口径：

| 档位 | 规格 | 承载 | 判定条件 |
|---|---|---|---|
| **现机精简（v1 上线）** | 4C4G / 60G / 5Mbps | `demo` profile 5 容器：api + worker（agent+io 合并）+ scheduler + gw + web；PG 共用、无 Redis、docparse 关闭、无 MinIO | 现机可用内存 ≥2.3G；容器预算 **1200m**（见 §1A.3）；共用实例剩余连接 ≥60 |
| **客户最小** | 8C32G / 500GB | `full`：自带 PG15（独立实例）、拆 io worker、开 doc、开 MinIO（WORM） | 接入真实客户；或客户不接受共用实例 |
| **客户推荐** | 16C64G / 1TB+ | `full` + 本地小模型（4bit 7B/14B） | 要求本地推理、或 3 家以上客户共享实例 |

> 「16C/64G 前提在 Docker 下怎么落」的答案：**同一套 compose，靠 profile 裁剪 + 显式 memory limit + 复用外部 PG，可以在 4C4G 上跑演示、在 8C32G/16C64G 上跑生产**；差异只在 profile、限额与是否自带中间件，不在镜像或代码。

**磁盘与带宽同样要算进第一版**（60G 盘、5Mbps 是硬约束）：

| 项 | 估算 | 处置 |
|---|---|---|
| 镜像（app/gw/web） | ≈0.63G | 不再拉 pg/redis 镜像；doc 镜像默认不拉（当前 ≈0.35G，估算值，未实测，待基础设施流回填；开 OCR 后 1.5–2.5G）；`docker builder prune` 限 2G |
| PG 数据（演示 90 天量级，落在共用实例） | 2–3G（实例盘增量） | 分区 + 每日 `pg_dump -n erp`（压缩后 <200M/月） |
| 审计快照（无 MinIO，本地卷） | 5–10G | 前后像只存 diff + 压缩快照，90 天滚动清理；正式 WORM 等 full 档 |
| 日志（json-file 10m×3 ×5 服务） | ≤0.15G | 统一 json-file 轮转（对齐 hulkai） |
| 出网带宽 | 5Mbps ≈ 0.6MB/s | 首屏静态资源 gzip 后 ≤500KB；影像上传/导出全部异步 + 断点续传；镜像包 0.6G ≈ 8–10 分钟传输（见 §1A.2） |

### 1A.2 镜像划分与构建策略

| 镜像 | 基础镜像 | 构建方式 | 瘦身手段 | 大小目标 |
|---|---|---|---|---|
| `smart-erp/app` | runtime `python:3.12-slim-bookworm`；builder 同版本 | **多阶段** | builder 装 `build-essential` 编 wheel → runtime 只 `pip install --no-cache-dir --only-binary` 拷 wheel；`--no-install-recommends`；删 `__pycache__/*.dist-info` 外无用文件 | **<220MB** |
| `smart-erp/connector-gw` | 同上 | 多阶段 | 只装 SDK + 连接器依赖；**不装** PG 客户端、不装 OCR、不装 numpy/pandas | **<180MB** |

**构建放在哪做（2C 机器上现场 build 会抢 CPU，这是本次的关键取舍）**：

| 方式 | 服务器 CPU/内存代价 | 传输量（5Mbps） | 额外风险 | 适用 |
|---|---|---|---|---|
| 服务器现场 `docker compose build` | 2 核被占 3–6 分钟，峰值内存 +1.5G → **直接压到 mfg/APS 的余量，可能触发 5xx** | 0 | 需外网拉 pip/npm 源，5Mbps 下依赖解析易超时；层缓存占磁盘 | 仅热修单文件、且非高峰 |
| **本地/CI 构建 → `docker save` → scp → `docker load`**（**采用**） | 仅 `load`（<30 秒，解压写盘） | app 0.22G + gw 0.18G + web 0.06G，gzip 后约 **0.18–0.25G** ≈ **5–7 分钟** | 需保证构建机与服务器架构一致（amd64）；tar 包要 sha256 校验 | 常规发布（每周） |
| 只改前端 | 0 | ≈0.02G | — | 文案/样式热更 |

约定：**服务器不编译**。`scripts/release.sh` 在构建机执行 `build → save → gzip → scp → ssh load → compose up -d`；`ERP_IMAGE_TAG` 为完整 git sha，回滚就是 `ERP_IMAGE_TAG=<上一 sha> docker compose up -d`（镜像还在本机，无需重传）。

构建约定（全部沿用 hulkai 现行习惯，不发明新体系）：

| 项 | 约定 | 来源 |
|---|---|---|
| 镜像源 | `ARG PIP_INDEX_URL=https://mirrors.cloud.tencent.com/pypi/simple`，可 `--build-arg` 覆盖 | hulkai `gz-api` compose 已有 |
| 依赖层缓存 | 先 `COPY pyproject.toml` + `pip install .`，再 `COPY src`（hulkai 是 `COPY src` 后安装，我们改成先依赖后源码，减少重建） | 改进项 |

### 1A.3 compose 拓扑（单文件 + profile）

`deploy/smart-erp/docker-compose.yml`，顶层 `name: smart-erp`（与 `hulkai-web` / `hulkai-gz-api` 平级，互不干扰）。**第一版只起 5 个容器**（PG 复用外部实例，无 Redis）：

| `worker` | demo（合并队列） | `smart-erp/app` | `python -m core.runtime.worker --queues agent,io --concurrency 4`（asyncio 任务 + 信号量，非 fork） | — | **512m** | 1.5 |
| `scheduler` | demo/full | `smart-erp/app` | `python -m core.runtime.scheduler`；`pg_advisory_lock` 保证单实例；**不执行迁移** | — | **96m** | 0.2 |
| `gw` | demo/full | `smart-erp/connector-gw` | `read_only: true`；`tmpfs: /tmp`；出网仅目标 ERP | `8012`（仅内网） | **160m** | 0.3 |
| `web` | demo/full | `smart-erp/web` | 自有 nginx；`base=/demo/smart-erp/`；gzip + 长缓存 | `8088:8080`（仅香港反代） | **48m** | 0.1 |
| **合计** | | | | | **1200m（1.17G）** | **2.9 核** |

> 预算对账：384+512+96+160+48 = **1200 MiB**，距 1.5G 上限余 **300MiB**；距现机可用内存（约 2.3G）余 **1.1G**，留给共用 PG 的数据增长、APS 与 Docker 自身。**不使用 `memswap_limit` 放水**：4G 机器上 swap 抖动会让 P95 失控，宁可 OOM 重启单个容器（有重启策略与告警）也不要整机假死。

`full` profile 在此之上增加（仅客户私有化或 8C32G 以上）：`worker-io`（1G）、`doc`（3G，`start_period: 300s`）、`minio`（512m，Object Lock）、`pg`（`profiles: [self-db]`，仅当客户不接受共用实例）、可选 `cache`（redis 128m，`noeviction`+AOF）、`obs`（otel 256m / prometheus 512m / grafana 256m）。

**开发与 CI 仍需要完整中间件**：`docker-compose.dev.yml` 提供 `pg`（`postgres:15-alpine`）与 `cache`（redis）两个服务，`profiles: [dev]`，只在本机与 CI 启用；云端与生产禁止叠加该文件（CI 断言 `docker compose --profile demo config` 中无 `pg`/`redis`）。

**demo 档为什么敢去掉 MinIO**：对象存储被 `ObjectStore` 接口抽象（`put/get/presign`），demo 注入 `LocalObjectStore`（宿主卷 `erp_objects`，只追加命名 + 每次写生成 sha256 清单）；审计不可篡改性由**哈希链 + 锚点**保证（FR-1307 仍可校验；锚点是某时刻固化的链尾边界，不是按自然日切分），只是缺少「存储层 WORM」这一层（NFR-C-01 的合规要件）。因此：**demo 可以给客户看流程，不能作为合规审计交付**——这句话要写进演示话术与合同边界。

四处与 hulkai 现状的差异（评审时说明，不是疏漏）：

1. **队列不用 Redis**：hulkai 的 mfg redis 是 `--save "" --maxmemory 256mb --maxmemory-policy allkeys-lru` 的纯缓存；`allkeys-lru` 会静默淘汰我们的任务键。我们把队列改为 PG 表 + `SKIP LOCKED`（§1A.7.3），Redis 在 demo 中直接不部署。
2. **中间件不发布端口**：照抄 APS 的 `expose` + `docker-compose.dev.expose.yml`（绑 `127.0.0.1`）模式；我们只是**连**内网 5432，不暴露新端口。
3. **迁移不在 entrypoint**：hulkai 的 mfg 在 entrypoint 里做「种子复制」；我们用一次性 `migrate` 服务（`profiles: [ops]`，`erp_migrator` 凭据）在发布序列里单独执行（§1A.6），且 DDL 只作用于 `erp` schema。
4. **服务器不编译**：hulkai 是 `up -d --build`；我们改为 `docker load` 预构建镜像（§1A.2），避免 2 核机器上构建把 mfg/APS 拖垮。

### 1A.4 网络、端口与路由

**网络**（两张网 + 显式挂载矩阵，不用默认 bridge 以免与 hulkai 其他栈串味）：

| 网络 | 定义 | 成员 | 作用 |
|---|---|---|---|
| `smart-erp-net` | 本 compose 自建（`name: smart-erp_net`） | api, worker, scheduler, gw, web | 栈内互访；web→api、worker→gw |
| `hulkai-gz-api_default` | **外部网络**：`external: true`，即 APS 栈的默认网络（PG 只在该网内 `expose: 5432`） | **仅** api, worker, scheduler | 连共用 PG15；gw/web **不挂**（最小权限：网关不需要 DB，前端不需要 DB） |

```
external: hulkai-gz-api_default   ← 只读依赖（不改 hulkai 任何文件）
        │
   [ api ]──[ worker ]──[ scheduler ]        ← 3 个容器双网
        │
   smart-erp-net
        ├── [ gw ]（只出网到目标 ERP，不触 DB）
        └── [ web ]（只反代 api）
```

- 这是**零改动 hulkai** 的接法（不用给它加端口映射），代价是耦合了它的网络名：compose 的 `name: hulkai-gz-api` → 网络 `hulkai-gz-api_default`。缓解：网络名走 `ERP_DB_NETWORK` 变量；启动前 preflight 解析 `ERP_DB_HOST` 并 `SELECT 1`，失败直接退出并打印「外部网络不存在或 PG 未就绪」，而不是无限重启。
- 若该网络被 APS 重命名/迁移，属于**外部变更**，需按 §1A.7.2 的迁移窗口与 §1A.8 R4 的升级窗口协商；不接受临时硬编码兜底。

**端口分配**（已核对 hulkai 现占用）：

| 用途 | 端口 | 暴露范围 |
|---|---|---|
| `erp_api` | 8010 | 仅香港反代（广州安全组限源 IP） |
| `erp_web` | 8088 → 容器 8080 | 仅香港反代（同上） |
| `erp_gw` | 8012 | `expose` only，栈内可达，不发布 |
| PG | 5432 | **不发布**（APS 内网 expose，我们加入其网络访问） |
| Redis | — | demo 无 Redis；full 的 `cache` 也不发布 |

**路由**（香港 Nginx 是唯一入口，沿用其 `envsubst` 模板机制）：

```
https://hulkai.xyz/erp/api/...        → 广州 129.204.108.45:8010（rewrite 去前缀，后端 root_path=/erp/api）
https://hulkai.xyz/demo/smart-erp/... → 广州 129.204.108.45:8088（rewrite 去前缀）
```

- 演练：每月一次「空库恢复 + 哈希链校验」，纳入 M5 验收；恢复目标库为**新建的 `smart_erp_restore`**，严禁 `psql` 指向共用实例的现有库做覆盖式恢复。

### 1A.6 健康检查、资源限额与启动顺序

| 服务 | 探针 | 参数 | 说明 |
|---|---|---|---|
| `api` | `GET /healthz`（存活）、`GET /readyz`（`SELECT 1` + 对象存储可写） | interval 15s, timeout 5s, start_period 60s | `/readyz` 失败即摘流；`/healthz` 不查依赖，避免共用实例抖动引发重启风暴 |

### 1A.7 共用 PostgreSQL 实例的隔离设计

**结论：共用实例可以，但必须做到「库、角色、schema、版本表、扩展、权限、连接数、迁移窗口」八项全隔离；我们不碰任何其他项目的对象。**

#### 1A.7.1 隔离手段（开通脚本一次执行，之后只读复用）

| 维度 | 做法 | 防的是什么 |
|---|---|---|
| 实例 | 复用 APS 的 PG**15**（`hulkai-gz-api` 网络内 `expose: 5432`） | 不新增 PG 容器（省 300m+ 内存与一个要备份的组件） |
| 数据库 | 独立 database `smart_erp` | 跨库查询在 PG 里写不出来（无 dblink/FDW 时装不出来），天然隔离 |
| 角色 | `erp_app`（LOGIN，`NOSUPERUSER NOCREATEDB NOCREATEROLE`，`CONNECTION LIMIT 20`）；`erp_migrator`（仅 `erp` schema 的 DDL 权） | 应用无权建库建角色；迁移与应用权限分离 |
| schema | 全部对象在 `erp`；`ALTER ROLE erp_app SET search_path = erp`；`REVOKE ALL ON SCHEMA public FROM erp_app` | 杜绝「忘了带 schema 落到 public」污染 APS |
| 版本表 | Alembic `version_table='alembic_version_erp'`、`version_table_schema='erp'` | 不与 APS 的 Flyway/迁移表冲突 |
| 扩展 | `pg_trgm`、`pgcrypto`（trusted，库 owner 可建）、`vector`（**非 trusted，需实例 owner 执行**）统一 `SCHEMA erp` | 扩展建在别人 schema 会导致升级冲突 |
| 权限 | `erp_app`：`erp.*` 的 SELECT/INSERT/UPDATE/DELETE；审计表**只** INSERT/SELECT（`REVOKE UPDATE, DELETE`）；无 TRUNCATE、无 DDL | 越权改审计、误清表 |
| 超时 | `ALTER ROLE erp_app SET statement_timeout='30s'`、`lock_timeout='3s'`、`idle_in_transaction_session_timeout='60s'` | 我们的慢查询/长事务**不能**拖住 APS 的连接与锁 |

一次性开通（由实例 owner 执行，属**外部依赖项**，不是我们的迁移）：

```sql
CREATE ROLE erp_app LOGIN PASSWORD :'erp_app_pwd' NOSUPERUSER NOCREATEDB NOCREATEROLE CONNECTION LIMIT 20;
CREATE ROLE erp_migrator LOGIN PASSWORD :'erp_mig_pwd' NOSUPERUSER NOCREATEDB NOCREATEROLE CONNECTION LIMIT 4;
CREATE DATABASE smart_erp OWNER erp_migrator;
\c smart_erp
CREATE SCHEMA IF NOT EXISTS erp AUTHORIZATION erp_migrator;
-- 以下三条扩展需 SUPERUSER（pg_trgm/pgcrypto 为 trusted 可由 db owner 建；vector 非 trusted）
CREATE EXTENSION IF NOT EXISTS vector  SCHEMA erp;
CREATE EXTENSION IF NOT EXISTS pg_trgm SCHEMA erp;
CREATE EXTENSION IF NOT EXISTS pgcrypto SCHEMA erp;
ALTER ROLE erp_app SET search_path = erp;
GRANT USAGE ON SCHEMA erp TO erp_app;
-- 只收回「我们自己」对 public 的权限；不动 PUBLIC 的默认权限（否则会影响到 APS 等其他项目）
REVOKE ALL ON SCHEMA public FROM erp_app;
-- 由 erp_migrator 建表后，默认权限自动授予 erp_app
ALTER DEFAULT PRIVILEGES FOR ROLE erp_migrator IN SCHEMA erp
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO erp_app;
```

> 扩展与 role 创建**必须**由实例 owner 做，我们不假设自己拿得到 SUPERUSER；这也是「共用实例」的第一个硬约束：**没有这一步，应用起不来**（preflight 会明确报 `missing extension vector`，而不是随机 500）。

#### 1A.7.2 迁移隔离与窗口

| 规则 | 内容 |
|---|---|
| 迁移只动 `erp` | `include_schemas=False`、`target_metadata` 只含我方模型；CI 断言：`alembic upgrade head` 前后，`pg_class` 中非 `erp` schema 的对象数量变化为 **0** |
| 版本链独立 | 独立 `alembic_version_erp`；禁止任何跨项目共享迁移文件 |
| 锁不扩散 | 迁移会话先 `SET lock_timeout='3s'`；`ALTER TABLE` 拿不到锁就失败退出（重试一次），绝不让 APS 等我们 |
| 大表索引 | 仅 `CREATE INDEX CONCURRENTLY`（须 `transaction_per_migration=False` 的独立迁移），拆「建索引」与「用索引」两个版本 |
| 失败即停 | 单迁移单事务；失败则 `migrate` 服务非 0 退出，发布中止、整栈不更新，告警 P0（常驻容器保持上一版本） |
| 窗口 | 默认 **周二/周四 21:00–22:00**；避开月末最后 3 天与 APS 发布日；窗口外只允许「新增可空列」这类加锁 <1s 的迁移 |
| 批准 | 迁移 PR 需 **ERP 负责人 + 实例 owner** 双方 approve（流程与窗口见 02 文档 §4.8） |

#### 1A.7.3 Redis 与队列的取舍（为什么不共用 Redis）

| 方案 | 做法 | 优点 | 致命问题 / 代价 | 结论 |
|---|---|---|---|---|
| A. 共用现有 Redis（逻辑库 + 前缀） | `SELECT 3` + `ERP_` 前缀 | 零新增 | **淘汰策略是实例级的，逻辑库不隔离**：现有实例是 `--save "" --maxmemory 256mb --maxmemory-policy allkeys-lru`，内存一紧就会静默淘汰我们的队列键 → 任务消失（违反 I-1）；且无持久化，重启全丢 | 否决 |
| B. 自建 Redis 容器 | 80–128m，`noeviction` + AOF | 语义正确 | 多一个有状态组件要备份/升级；4G 机器上仍是白给的内存；仍要自己处理 at-least-once 与死信 | 仅 full/私有化可选 |
| **C. 队列进 PG** | `job_queue` 表 + `FOR UPDATE SKIP LOCKED` + `LISTEN/NOTIFY` 唤醒 | ① 入队与业务写**同事务**，彻底消除 dual-write；② 死信/重投/退避就是 `UPDATE`，运维可在页面直接重放；③ 少一个有状态依赖；④ 备份天然覆盖队列 | 需自研 worker 循环（约 300 行）；无 Celery 生态（flower 等）；轮询有微小空转（NOTIFY + 1s 兜底）；给共用实例增加写压力 | **采用** |

```sql
CREATE TABLE erp.job_queue (
  id bigserial PRIMARY KEY,
  queue text NOT NULL,                 -- agent | io | notify
  kind text NOT NULL,
  payload jsonb NOT NULL,
  state text NOT NULL DEFAULT 'queued',-- queued|running|succeeded|failed|dead
  priority smallint NOT NULL DEFAULT 0,
  run_at timestamptz NOT NULL DEFAULT now(),
  attempts smallint NOT NULL DEFAULT 0,
  max_attempts smallint NOT NULL DEFAULT 3,
  lease_owner text, lease_expires_at timestamptz,
  last_error text, created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX job_queue_pick_idx ON erp.job_queue (queue, priority DESC, run_at)
  WHERE state = 'queued';
```

取任务（单条 SQL，天然并发安全）：

```sql
UPDATE erp.job_queue j SET state='running', lease_owner=$1,
       lease_expires_at=now()+interval '60 seconds', attempts=j.attempts+1
WHERE j.id = (SELECT id FROM erp.job_queue
              WHERE state='queued' AND queue=ANY($2) AND run_at<=now()
              ORDER BY priority DESC, run_at
              LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING j.*;
```

写压力核算：演示量级每日 <1 万任务 × 4 次 UPDATE ≈ 4 万行更新/日，对 PG15 可忽略；正式档按月结 2 万行写入 + 100 批次，仍远低于实例承受能力。

**Redis 的最终定位**：demo 不部署；full 可选 `cache` 服务，只允许存**可丢失**数据（页面缓存、SSE 广播、限流令牌桶加速），且必须自建实例 `--maxmemory-policy noeviction --appendonly yes`。**关键状态（队列、工单、审计、幂等、熔断状态）永不放 Redis**。

限流与熔断在没有 Redis 时如何实现：
- 限流令牌桶落 `erp.rate_bucket(key, tokens, updated_at)`，`UPDATE ... RETURNING` 原子扣减（连接器并发 4，QPS 极低，足够）；
- 熔断计数落 `erp.breaker_metric(scene, window_start, fail, total)`，scheduler 每 60 秒聚合判定写 `breaker_state`；
- 两者都是**可重建**数据，量大时可迁到缓存而不改变语义。

#### 1A.7.4 共用实例的 DDL/DML 红线

1. 任何 SQL **不得**出现无 schema 限定的对象名（连接串带 `options=-c search_path=erp` 兜底）。
2. 禁止 `CREATE DATABASE`/`DROP DATABASE`/`CREATE ROLE`/`ALTER SYSTEM`（应用角色本就无权限，仍写进评审清单）。
3. 禁止 `TRUNCATE`、禁止无 `WHERE` 的 `UPDATE/DELETE`（CI 静态扫描 + 代码评审）。
4. 禁止对我们不拥有的表做任何写操作（`erp` 之外的表一律只读，且 v1 不需要读）。
5. 单条查询必须带 `LIMIT` 或 keyset 分页；导出走 worker + 分批，避免长事务占住连接与锁。

### 1A.8 共用实例带来的新风险（逐条给缓解）

| # | 风险 | 具体表现 | 缓解措施 | 残余风险（如实承认） |
|---|---|---|---|---|
| R1 | **实例级故障影响面** | PG 挂 → APS 与我们同时不可用；我们无法独立恢复 | 与 APS 同值班群；`/readyz` 快速摘流（30s 内）；前端显示「依赖服务不可用」而非白屏；不在我们的容器里做任何 PG 自愈重启 | 共享故障域，v1 无法消除；要独立 SLA 只能走 full 档自带实例 |
| R2 | **备份/恢复责任** | 谁的备份策略覆盖我们？现有 hulkai 无 PG 备份脚本 | 我方每日 `pg_dump -n erp` + 月度归档 + 每月恢复演练（恢复到独立库）；备份文件落在 `erp_objects` 并异地同步 | 无 PITR，RPO 最差 24h；合同/演示话术**不得**承诺分钟级 RPO |
| R3 | **连接数上限** | 实例 `max_connections` 默认 100，APS 已占一部分；我们峰值 ~20 | role 级 `CONNECTION LIMIT 20`；容器池 `pool_size 4 + max_overflow 4`；超限直接 503 并告警；每周核对 `pg_stat_activity` 按 role 计数 | 若 APS 扩容，需重新分配预算（走变更流程） |
| R4 | **升级窗口协商** | PG 小版本重启、APS 发布、我们的迁移三者互相踩 | 固定窗口（周二/周四 21:00–22:00）；迁移 ≤1 个版本/次；`lock_timeout=3s` 保证不阻塞对方；窗口表在 `deploy/smart-erp/README` 维护 | 紧急迁移需临时协商，可能延后到次日 |
| R5 | **慢查询相互影响** | 我们的 10 万条导出把 IO 打满，APS 报表变慢 | 应用侧 `statement_timeout=30s`；导出在 worker 分批 + `LIMIT`；重查询只允许低峰；`EXPLAIN` 门禁（禁止 Seq Scan 大表）；应用侧慢查询日志 >1s 打 WARN 并带 `role/scene` | 共用磁盘 IO，极端情况仍会互相影响 |
| R6 | **磁盘被我们撑爆**（共用数据盘） | 审计数据无节制增长导致整个实例写失败 | 保留策略（demo 90 天、正式 3 年分档）；每日磁盘水位 <80% 告警；分区表可整分区 `DROP`（不需要 DELETE） | 需实例 owner 提供磁盘监控权限/告警转发 |
| R7 | **对象被误删** | 有人 `DROP SCHEMA erp CASCADE` 或 `DROP DATABASE` | 应用角色无 DDL；DDL 仅在 `erp_migrator` 且走迁移；每周探针校验 role/schema/扩展存在；备份可恢复 | 有 DBA 权限的人仍可能误操作（属治理范畴） |

### 1A.9 与 hulkai 的合并边界

**结论：能做「独立自洽 + 可选挂载」，不要做「深度融入」。**

| 部分 | 归属 | 具体 |
|---|---|---|
| **自洽（不改 hulkai 即可跑）** | 我们独占 | `projects/smart-ERP/{api,web,contracts,db,tests}`、`deploy/smart-erp/{docker-compose.yml,docker-compose.dev.yml,.env.example,README.md}`、`.github/workflows/smart-erp.yml`、离线打包脚本 |
| **必须挂到 hulkai 服务组** | 需改 hulkai（后续任务） | ① `deploy/hk-web/nginx/templates/default.conf.template` 增 2 个 location；② 香港 `.env` 增 `ERP_BACKEND_URL`；③ 广州安全组放行 8010 给香港 IP；④ 根 `README.md` 路由表 + `site/public/demo/index.html` 加卡；⑤ `deploy/hk-web/docker-compose.yml` 无需改（走反代，不起容器） |
| **明确不接管** | hulkai 现有 | `/api/*`（mfg）、certbot/证书、域名变量、APS 栈、hogo、`site/public` 静态站 |

**命名空间约定**（全部加前缀，避免与 `mfg_*` / `hulkai_*` / `aps_*` 混淆）：

| 维度 | 规则 | 示例 |
|---|---|---|
| compose project | `name: smart-erp` | 容器/网络/卷自动带 `smart-erp_` 前缀，再叠加显式 `container_name` |
| 容器名 | `erp_<role>` | `erp_api`、`erp_gw` |
| 卷名 | `erp_<purpose>`（显式 `name:` 固定，防 compose 重命名丢数据，hulkai 有先例）；**无 `pgdata`/`redisdata`** | `erp_objects`、`erp_logs` |
| 镜像 | `smart-erp/<comp>:<tag>` | `smart-erp/app:abc1234` |
| 环境变量 | `ERP_` 前缀 | `ERP_DB_PASSWORD`、`ERP_LLM_API_KEY`、`ERP_IMAGE_TAG` |
| 路由 | `/erp/`、`/demo/smart-erp/` | — |
| 日志 | `docker compose logs erp_api` / json-file 20m×5 | 对齐 hulkai |

**环境变量约定**：密钥只放 `deploy/smart-erp/.env`（不入库，`.gitignore` 已屏蔽 `.env`/`.env.*`，保留 `.env.example`）；compose 用 `env_file: .env` + 行内 `${ERP_X:-默认}`；**不引入** docker secrets / Vault（hulkai 没有，自建会破坏「一条命令起栈」）。敏感值的默认值一律留空并在启动时 `:?` 强制报错（学 APS 的 `POSTGRES_PASSWORD:?` 写法），不写死在 compose 里。

### 1A.10 云部署形态、扩容触发线与升级

**形态结论：单机 compose，不引入多节点、不引入 k8s、不建镜像仓库。** 广州机跑容器，香港机只做入口（Nginx + certbot 完全复用 hulkai，不新增证书）；数据库**不在同机起容器**，共用 APS 的 PG15 实例（§1A.7）。

| 项 | 结论 | 理由 |
|---|---|---|
| 单机 compose vs 多节点 | **单机 compose**（广州一台），香港只做入口 | 目标负载（月结 100 批次）、团队规模与 hulkai 现状都支撑不了 k8s；多节点要到 SaaS 阶段 |
| 数据库 | **共用 hulkai 现有 PG15 实例**（独立 database/role/schema，§1A.7）；客户私有化 = 独立实例（`full`，可用 `self-db` profile 自带容器） | 省掉一个 PG 容器的 ~256–512m 常驻与一份备份体系；`vector` 扩展由实例 owner 一次性开通 |
| 缓存 | **demo 不部署 Redis**；`full` 可选 `cache` profile（`noeviction` + AOF，仅存可丢失数据） | 队列已进 PG（§1A.7.3），demo 没有必须用 Redis 的场景 |
| 镜像来源 | **本地/CI 构建 → `docker save` → scp → `docker load`**；tag = 完整 git sha（`ERP_IMAGE_TAG`）；**不建镜像仓库** | 2 核服务器现场 build 会抢 mfg/APS 的 CPU（§1A.2），且 5Mbps 拉依赖易超时；tar 走同一条链路，5–7 分钟 |
| 升级方式 | 服务器上 `docker load` 新 tar → `ERP_IMAGE_TAG=<新 sha> docker compose up -d`；**服务器不编译** | 与 hulkai「停机上更」一致；单机无法真滚动 |
| 缩短停机 | 先起新 `api`/`web` 容器再切换（蓝绿，Nginx upstream 或反代端口切换），`worker`/`scheduler` 直接替换 | 迁移先行（expand→migrate→contract），旧容器在窗口内仍可跑；中断主要来自迁移而非重启 |
| 回滚 | `ERP_IMAGE_TAG=<上一 sha> docker compose up -d`（镜像仍在本机，无需重传）；迁移只增不删，contract 延后一个版本 | NFR-D-03 一键回滚；**回滚不需要网络，这一点在 5Mbps 现场很关键** |
| 证书/域名 | 完全复用 hulkai（certbot 容器 + `PUBLIC_DOMAIN` + `envsubst` 模板），不新增证书 | 同域部署的最大收益 |
| 观测 | 默认 json-file（10m×3）+ `/healthz` `/readyz`；`obs` profile 可选（Prometheus/Grafana/Loki，仅客户私有化） | hulkai 无观测栈，不在 4G 机上强行引入 |
| CD | **无 CD**（现状人工发布）；我们只加 CI（构建 + 测试 + 镜像 tar 产物），不改 hulkai 发布模型 | 避免「两套发布」；CI 只产出 artifact，不直连生产 |

**发布序列（写死，避免口头约定）**：

```
构建机                    服务器（129.204.108.45）                 香港
1  build×3 镜像      →   4  docker load < erp-images-<sha>.tar.gz
2  docker save+gzip  →   5  ERP_IMAGE_TAG=<sha> compose up -d      （Nginx 无需改动）
3  scp（5–7 分钟）       6  scheduler 跑 alembic upgrade head（独立步骤，非 entrypoint）
                          7  curl /readyz 逐容器确认 → 摘旧容器
```

> 迁移**不放在 entrypoint** 里（与 hulkai 的 mfg 做法不同）：共用实例上必须由带 `erp_migrator` 凭据的独立步骤执行，且迁移窗口受 §1A.7.2 约束。

#### 扩容触发线（任一命中即启动评估，不是"视情况"）

| # | 触发条件（连续 24h 或连续 3 次采样） | 判定依据 | 动作 |
|---|---|---|---|
| T1 | 现机可用内存 < 400MiB，或容器 `erp_worker` 峰值 > 512m 持续 30 分钟 | `docker stats` / `/readyz` 上报 | 先关 `obs`、降 `worker` 并发；仍不缓解 → 档位 2 |
| T2 | 宿主机内存使用率**持续 >85%**（现机即 >3.4G/4G），或发生 OOM kill | `dmesg` + `docker events` | 立即扩档；不允许靠 swap/降 limit 硬扛 |
| T3 | **接入真实客户**（有外部租户数据、或需要 SLA 承诺） | 商务/合同状态 | 必须切档位 2，且不再共用实例（R1/R2 影响面无法对外承诺） |
| T4 | **并发对账压测**：50 并发工单 P95 > 30s，或单期 10 万行匹配 > 90min（NFR-P-02） | 压测报告 | 先拆 `worker-io` 回独立容器；仍超 → 档位 2 |
| T5 | **开启 docparse 或 full 全量 worker**（开 OCR 后 `doc` 需 1.5–2.5G） | compose profile 变更申请 | 现机**不允许**开启，必须切档位 2 |
| T6 | 共用实例连接数占用 > 70%（`SELECT count(*)/max_conn`），或 `erp_app` 频繁触顶 20 | PG 侧采样 | 先降 `pool_size`；再与实例 owner 协商上限；档位 2 |
| T7 | 系统盘 > 80%（>48G），或 PG 侧 `smart_erp` 库 > 10G | `df -h`、`pg_database_size` | 先清审计快照/日志；再扩盘或迁档位 2 |
| T8 | API P95 > 1.5s 或首屏 > 3s 连续 1 周（NFR-P-05） | `readyz` 指标 / 手工采样 | 先查慢查询与索引；无效则扩 CPU 档 |

#### 三档 sizing 与切换动作

| 档位 | 规格 | 判定 | 切换动作（可执行清单） |
|---|---|---|---|
| **档位 1：现机精简**（当前） | 4C4G / 60G / 5Mbps，5 容器 1200m，PG 共用，无 Redis | 默认；满足 T1–T8 均未命中 | — |
| **档位 2：客户最小** | 8C32G / 500G SSD / ≥20Mbps，`full`：自带 PG（`self-db` 或独立实例）、拆 `worker-io`、开 `doc`、开 MinIO | T3/T4/T5 命中，或 T1/T2/T6/T7 缓解后仍复发 | ①新建 `.env.prod`（`ERP_DB_HOST` 指向自带实例，连接串不再跨栈）②`pg_dump -n erp` 迁移到新实例，`alembic_version_erp` 版本号对齐 ③镜像复用（同一 tar），只改 profile 与限额 ④切 Nginx upstream 到新机，旧机保留 7 天做回滚 ⑤共用实例侧只做 `DROP DATABASE`（需 owner 批准） |

### 1A.12 为什么不是微服务（成本账，v0.3 更新）

| 方案 | 省下的 | 多付的 | 结论 |
|---|---|---|---|
| 微服务（工单/审计/对账/连接各自服务） | 独立扩缩、故障隔离 | ① 工单状态 + 审计影像 + 幂等记录**必须同库同事务**，拆开就要引入分布式事务或对账补偿，把 PRD 要解决的问题变成基础设施问题；② 广州机 4C4G 连 8 个 JVM/进程的连接池都放不下；③ 客户 IT 与 hulkai 现有运维习惯都不支持（NFR-D-02） | 否决 |
| 纯单体（一个容器干完） | 最简单，compose 只 1 个服务 | ① LLM 长调用阻塞界面；② 连接器与业务同容器，凭据面与出网面无法收敛（NFR-S-03/05）；③ 文档解析尖峰拖垮工单；④ 无 `internal` 网络隔离 | 否决 |
| **模块化单体 + 4 镜像 / demo 5 容器（full ≤10）+ profile 裁剪** | 单事务、单镜像集、可在 4C4G~16C64G 三档运行 | 需要靠 import-linter / CODEOWNERS / compose ownership 维持纪律 | **采用** |

## 2. 语言与框架选型

| 领域 | 选型 | 版本基线 | 一句话「为什么不是另一个」 |
|---|---|---|---|
| 语言 | **Python 3.12** | 3.12.x | 不用 3.13：OCR/图像/厂商 SDK 的 wheel 覆盖在私有化离线环境里仍是风险（NFR-D-03）；3.12 已有足够性能改进（NFR-P-02 靠架构分片而非语言特性解决） |
| Web 框架 | **FastAPI + Starlette + Pydantic v2** | fastapi ≥0.115 | 不用 Django：我们要的是「OpenAPI 即契约」，Django 的 ORM/Admin 优势在这里用不上，且其同步模型与批量并发冲突；不用 Flask：需要手写 schema 生成，契约先行无从落地（见 02 §1） |
| ASGI 运行 | **uvicorn + uvloop**，`gunicorn` 仅作进程管理（Linux） | — | 不用 hypercorn：uvloop 在限流/长连接场景实测更稳；Windows 开发机单进程 uvicorn 即可 |
| ORM / 迁移 | **SQLAlchemy 2.0（async, typed）+ Alembic** | 2.0.x | 不用 Django ORM：无法脱离 Django；不用 SQLModel：分区表、`WITH`、窗口函数、`ON CONFLICT`、行级安全等审计与对账必需能力表达力不足；报表与台账走手写 SQL |
| 数据库 | **PostgreSQL 15**（与 hulkai 现有 APS 实例共用，版本随实例） | **15.x**（≥15.4） | 不用 MySQL：需要 `jsonb`、部分唯一索引、RLS、`SKIP LOCKED`、声明式分区、`pg_trgm`，这些直接支撑工单队列、审计、模糊检索（FR-1106 ≤2s）；OQ-07 已定默认 PG。**版本口径统一为 15**：与共用实例一致，**禁止使用 PG16 独有语法/特性**（`any_value()`、`json_arrayagg()`/`json_objectagg()` 的 16 新增重载、`pg_stat_io`、`random_normal()`、`MERGE ... RETURNING` 等）；CI 用 `postgres:15-alpine` 跑迁移与集成测试，一旦误用 16 语法会在 CI 暴露。升级到 16 属于**独立变更**（需实例 owner 与全部共用方同步），不在本项目范围 |

### 2.1 Agent 编排：自研状态机 vs 现成框架

### 2.2 PDF 依赖选型与许可证约束（决策记录）

**为什么不能用标准库**（实测，不是推测）：用 `zlib` + 手写 tokenizer 解析一份 Identity-H 编码的中文 PDF，内容流里只能取到 `<00010002>` 这类字形码（glyph id），还原不出文字——Identity-H 的字符编码是「字体内部索引」，必须经 ToUnicode CMap 反查；而标准库既没有 CMap 解析，也没有交叉引用流（xref stream，PDF 1.5+ 压缩对象）解析。要自己补齐至少四块：**交叉引用流/对象流解析、内容流算子解释（`Tj/TJ/Td/Tm/CTM`）、ToUnicode CMap 与 CID 字体映射、加密（RC4/AES-128/AES-256）**。这四块加起来是一个 PDF 渲染内核的工作量，不是「几百行工具函数」。

**三个候选对比**（结论以许可证为第一约束，性能为第二）：

| 候选 | 许可证 | 体积 | 能力 | 结论 |
|---|---|---|---|---|
| **PyMuPDF**（`fitz`） | **AGPL-3.0**（商业授权需付费） | wheel ≈15–20MB | 最全（文本/坐标/渲染/OCR 桥接），性能最好 | **否决**：闭源商用分发触发 AGPL 传染，要么开源我方代码、要么买商业授权；私有化交付还要把这个义务转嫁给客户，尽调与合同法务都过不去 |
| **`pypdfium2`** | **BSD-3-Clause + Apache-2.0**（PDFium 内核，Chromium 同源） | **wheel 3.83 MiB** | 文本层 + 字符级 bbox + 页面渲染（供后续 OCR/缩略图），覆盖 FR-402 的坐标回链需求 | **采用**：许可证干净、体积小、wheel 自带二进制可**离线预装**（客户内网无外网也能装）；PDFium 的中文 CMap 支持成熟 |
| **`pdfminer.six`** | **MIT** | 纯 Python，≈5MB | 文本抽取可用，坐标粒度较粗、速度慢（约为 pdfium 的 1/5–1/10），无渲染 | **兜底**：当目标平台没有匹配的 `pypdfium2` 预编译 wheel（如非 x86_64/arm64 或极老 glibc）时降级使用；只保证「能出文字 + 行级坐标」，不承诺字符级 bbox |

**产品级约束（写进 `pyproject.toml` 与镜像构建，不是口头约定）**：

| 约束 | 落地方式 | 理由 |
|---|---|---|
| 核心安装**零 PDF 依赖** | 依赖声明为可选 extra：`smart-erp[pdf]`；核心包 `pip install smart-erp` 不拉 `pypdfium2`/`pdfminer.six` | 连接器网关镜像（`smart-erp/connector-gw`）与只跑工单的运行环境不需要 PDF 能力，少一个二进制依赖 = 少一个 CVE 面与许可证面 |

**硬规则（依赖准入）**：**后续任何第三方依赖的引入，必须先过许可证评估；AGPL / SSPL 默认否决**，例外必须由产品负责人 + 法务书面确认，并在本文档记录理由与替代方案。CI 增加一条 `pip-licenses` 检查：出现 AGPL/SSPL 即构建失败（白名单显式维护在 `contracts/deps/license-allowlist.txt`）。这条规则的动机不是洁癖——私有化交付意味着**许可证义务会随二进制一起交到客户手里**。

## 3. 关键机制设计（评审重点）

### 3.1 工单状态机与 Saga 补偿的持久化实现

#### 3.1.1 状态与迁移表（唯一真源）

状态严格取自 PRD §5.0 与 §6.2，**不新增、不改名**：

```
计划中 ──preview_ok──> 待审批 ──approved──> 执行中 ──all_ok──> 校验中 ──verified──> 已完成
   │                      │                  │                    └─mismatch──> 补偿中
   │                      └─rejected──> 已驳回  ├─step_failed──> 补偿中
   ├─preview_failed──> 已终止(零写入)          └─external_effective──> 已锁定
   └─deviation>5%──> 待确认(人工)
补偿中 ──all_compensated──> 已回滚 / ──any_failed──> 需人工处置
```

代码里只允许存在一张迁移表，任何推进都必须经过它：

```python
# core/runtime/transitions.py —— 唯一允许改状态的入口
TRANSITIONS: dict[State, frozenset[State]] = {
    State.PLANNED:       {State.PENDING_APPROVAL, State.TERMINATED, State.NEEDS_REVIEW},
    State.NEEDS_REVIEW:  {State.PENDING_APPROVAL, State.TERMINATED},
    State.PENDING_APPROVAL: {State.EXECUTING, State.REJECTED, State.TERMINATED},
    State.EXECUTING:     {State.VERIFYING, State.COMPENSATING, State.LOCKED},
    State.VERIFYING:     {State.COMPLETED, State.COMPENSATING},
    State.COMPENSATING:  {State.ROLLED_BACK, State.MANUAL_REQUIRED},
}
```

DB 层再加一道：`ticket_event` 上有 `CHECK (from_state, to_state)` 白名单的触发器（或由 `transition()` 函数封装 + 单元测试遍历全表），保证「不改代码就无法产生非法边」。

**为什么用「事件表 + 投影表」**：

| 表 | 角色 | 写入方式 | 用途 |
|---|---|---|---|
| `ticket_event` | **真源**（append-only，哈希链） | 只 INSERT | 审计、回放、争议举证（NFR-O-03、NFR-C-02） |
| `ticket` | **投影**（当前状态、影响面、金额、锁） | UPSERT，带 `version` 乐观锁 | 列表/检索 ≤2s（FR-1106、NFR-P-06） |
| `ticket_step` | 步骤级真源（每步一行的状态机） | 状态字段 UPDATE（受控） | 断点续跑、补偿依据（FR-109、FR-1105） |

投影可在任意时刻由事件表重建（`rebuild_ticket(id)` 工具），所以投影损坏不是数据丢失。

#### 3.1.2 核心 DDL（关键约束即设计）

```sql
CREATE TABLE ticket (
  id            uuid PRIMARY KEY,
  tenant_id     uuid NOT NULL,
```

要点：
- **`UNIQUE(tenant_id, scene_code, business_key)` 就是 FR-1101 的并发 10 次只出 1 张工单**，不靠应用层「先查后插」。
- `compensation_task.compensate_seq` 取原步骤序号，按 `DESC` 消费 → 逆序补偿是**数据约束**而非代码习惯。
- `ticket_step.write_level` 存实际生效等级，供审计核对（FR-1406 验收「等级越级 100% 被拒」需要可举证）。

#### 3.1.3 检查点与断点续跑

**检查点 = 每步一行 `ticket_step` 的终态 + 工单 `state` + 事件表游标**，不引入外部 checkpointer。

恢复流程（进程重启、租约过期、人工「从此处继续」都走同一条）：

```
resume(ticket):
  1. 取租约：UPDATE ticket SET lease_owner=$me, lease_expires_at=now()+30s
             WHERE id=$id AND (lease_owner IS NULL OR lease_expires_at < now())
  2. 读 steps：按 step_no 升序，找到第一个 state ∉ {succeeded, skipped, compensated}
  3. 若该步是 intent（见 3.1.4），先 verify 再决定是否重放
  4. 从该步继续；已 succeeded 的步骤永不重做
```

租约心跳由 worker 每 10 秒续期；`scheduler` 每 30 秒扫描 `lease_expires_at < now() AND state='执行中'` 的工单并重新投递（at-least-once，靠幂等收敛）。**没有租约就不许执行**——这是「半成功」的第一道防线。

#### 3.1.4 崩溃安全的写入：intent → verify（本设计最关键的一处）

外部写入有一个经典缺口：**调用成功但本地事务未提交**（进程被杀、网络超时）。此时既不能当作失败重试（会写两次），也不能当作成功（可能真没写）。

解决办法是**所有写动作必须成对声明 `write` 与 `verify`**，运行时在未知结果时用 `verify` 判定，而不是盲目重试：

```python
# 1) 先落意图（本地事务提交）
step = insert_step(ticket, n, action, state="intent", idempotency_key=k, request_hash=h)
commit()

# 2) 调外部（可能成功、可能失败、可能超时）
try:
    resp = gateway.execute(action, payload, ticket_id, k)   # 唯一出口，见 §3.2
except UnknownOutcome:
    # 3) 结果未知：不重试，先问目标系统
    actual = gateway.verify(action.verify_spec, payload, ticket_id)
    if actual.matches(payload):  step.state = "succeeded"
    elif actual.absent():        step.state = "failed"      # 可安全重试
    else:                        step.state = "unresolved"   # 值不符 → 立即进补偿 (F6)
    commit(); return

# 4) 成功：落结果 + 前像后像（同事务）
step.state, step.response_snapshot = "succeeded", resp
write_audit_image(before=resp.before, after=resp.after, diff=resp.diff, step=step)
commit()
```

代价与约束：
- **连接器能力要求**：`ActionSpec.verify` 必填（可写成 `read by external_id` 或 `read by business key`）。做不到 verify 的动作，最高只能 W0（这与 03 §0 准入标准第 2 条「可回滚」同源）。
- **宁可 `unresolved` 也不猜**：`unresolved` → `需人工处置`（FR-1105 异常分支），并生成人工任务；这是 I-4 的直接体现。

#### 3.1.5 补偿实现

| 触发 | 入口 | 行为 |
|---|---|---|
| 单步失败且重试耗尽（F5） | 运行时 | 停止前向，`compensation_task` 批量入队（逆序） |
| 写入后校验不一致（F6） | 运行时 | 立即停止 + 补偿；连续 2 次 F6 熔断该供应商/场景（AG-1） |
| 人工回滚（FR-1302/1303） | API | 先算 `rollback_plan`（FR-1305），再入队 |
| 补偿自身失败 | 补偿 worker | 重试 3 次（退避）→ 仍失败：`需人工处置` + 指派责任人（FR-1105 验收） |
| 补偿不可用（外部已生效） | 补偿 worker | `已锁定` + 生成处置任务 + 通知（FR-1304） |

补偿动作的三条硬规则：
1. **等级不高于原动作**（PRD §5.0）：`assert comp.level <= original.level`，运行时校验。
2. **补偿也要幂等**：`compensate(compensation, idempotency_key)`，键 = `original_idempotency_key + ":undo"`。
3. **补偿串行**：同一工单同一时刻只允许一个补偿任务在执行（`SELECT ... FOR UPDATE SKIP LOCKED` + 工单行锁），避免「删草稿」和「红冲」交叉。

#### 3.1.6 并发冲突

| 场景 | 机制 | 依据 |
|---|---|---|
| 两 Agent 改同一单据 | `advisory_lock(hash(business_key))` + 目标系统乐观锁（版本号/时间戳）；后到者转 `待确认` | 02 §3.3、F7 |
| 人与 Agent 同时改 | 写入前 re-read 版本号，不一致即 `F7` 中止并重取数 | F7、02 §3.3 |
| 同供应商跨期间 | 分片键含 `period`，跨期差异归后一期 | G-11、02 §3.3 |

### 3.2 写入闸门 W0–W3 的代码层硬约束

目标：**配置错误、代码 bug、Agent 越权三者都不能产生 W3 写入，也不能让 W1 动作绕过审批**（FR-1406/1407「代码层无 W3 执行路径」是验收项，不能用文档承诺代替）。

#### 3.2.1 四层收口（从上到下逐层不可绕过）

```
Agent/场景代码
   │  ① 场景上限：SceneSpec.max_level（代码常量，AG-5 = W0，AG-1 = W1）
   ▼
WriteGateway.execute()   ← 全系统唯一能发起外部写调用的函数
   │  ② 取严：min(场景, 连接器声明, 动作声明, 熔断档位)
   │  ③ 字段 scope 校验：payload ⊆ action.writable_fields
   │  ④ W3 断言：level == W3 → ForbiddenWriteError（无分支）
   ▼
ConnectorClient._transport_write()   ← 私有，import-linter 禁止外部导入
   │  ⑤ 最小权限凭据：连接器账号本身没有资金类 API 权限
   ▼
目标系统
```

#### 3.2.2 「等级在代码里」而不是在配置里

```python
# core/policy/levels.py
class WriteLevel(IntEnum):
    W0 = 0; W1 = 1; W2 = 2; W3 = 3          # W3 仅用于识别与拒绝，永不执行

@dataclass(frozen=True)
class ActionSpec:
    key: str                                 # "connector.alias.action"
    level: WriteLevel                        # 代码声明，非配置
    writable_fields: frozenset[str]          # 字段级 scope (NFR-S-04)
    forbidden_fields: frozenset[str]         # 资金类：bank_account/payment_amount/...
    compensation: CompensateSpec | None      # 无补偿 → 不允许 >W0 (FR-1102)
    verify: VerifySpec                       # 见 §3.1.4
    rate_limit: RateLimit
    idempotent: bool                         # 目标系统是否支持幂等键

# core/policy/gate.py —— 唯一的执行入口
async def execute(self, action: ActionSpec, payload, *, ticket_id, idem_key):
    level = min(action.level, self.scene_cap[scene], self.connector_cap[action.key],
                self.breaker_cap(scene))       # G-03 取严 + G-07 熔断降级
    if level is WriteLevel.W3:
        raise ForbiddenWriteError(action.key)  # G-09 / FR-1407：无 bypass 参数
    if level >= WriteLevel.W1 and not self.approval_satisfied(ticket_id, level):
        raise ApprovalRequiredError(ticket_id)
    self.assert_field_scope(action, payload)   # 多余字段 → FieldScopeViolation
    self.assert_no_forbidden(action, payload)  # 银行账号/科目/已过账凭证 → 拒绝
    ...                                         # 预演 → 写入 → 校验（§3.1.4）
```

**关键点：配置只能「降」，不能「升」**。`connector_cap` 来自连接器的 `describe()`（数据库配置，可被人为改高），因此取 `min`；而 `action.level` 与 `scene_cap` 是代码常量（改它们必须过代码评审 + 回归测试）。

#### 3.2.3 物理与工具链层面的强制

| 手段 | 作用 | 验证方式 |
|---|---|---|
| `import-linter` 契约：`connectors.*.transport` 只允许被 `core.policy.gateway` 导入 | 任何人无法绕开网关直连 | CI 失败 |
| `ActionRegistry` 启动时只注册**签名校验通过**的 ActionSpec（manifest 签名，NFR-S-01 §2 工具注册） | 未签名工具不进候选集（FR-1202） | 启动自检 + 单测 |
| 注册期断言：`level == W3` → 拒绝注册；`level >= W1 and compensation is None` → 拒绝注册（FR-1102） | 高危动作根本进不了系统 | 单测遍历注册表 |
| CI 用例：遍历注册表，断言**不存在** W3 动作，且禁止动词表（`create_bank_account`/`post_voucher`/`certify_invoice`/`execute_payment`/`delete_document`）无匹配 | FR-1407 验收「代码审计验证」 | 每次 PR |
| 连接器镜像内 `ActionSpec` 白名单**编译期生成**（不是运行时读 YAML） | 配置被篡改也不生效 | 构建产物 hash |
| DB 权限：应用账号对 `audit_*` 只有 INSERT/SELECT | 审计不可改（§3.4） | 迁移脚本 + 集成测试 |
| 连接器服务账号最小权限：ERP 侧只授「建草稿/删草稿/读」 | 即使代码有 bug 也过不了 ERP 权限 | 客户验收清单 |

#### 3.2.4 审批不是 UI 行为

审批满足性的判定在**执行器**里，且证据来自 DB：

```sql
CREATE TABLE approval_record (
  id uuid PRIMARY KEY, ticket_id uuid NOT NULL, role text NOT NULL,
  approver_id uuid NOT NULL, initiator_id uuid NOT NULL,
  decision text NOT NULL, comment text NOT NULL CHECK (length(btrim(comment)) > 0),  -- FR-107 空意见阻断
  decided_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_sod_self CHECK (approver_id <> initiator_id),        -- FR-1403 自审 0 例，DB 级
  CONSTRAINT uq_one_per_role UNIQUE (ticket_id, role, approver_id)
);
```

- 双人复核：`approval_satisfied()` 要求**不同 `approver_id` 的两条 `approved`**（金额 >10 万或触及应付，G-04；>50 万再加 CFO 角色）。
- 第二复核人看不到第一人意见（FR-1504）→ API 层按「未提交前不返回他人意见」实现，DB 不做（这是展示规则）。
- 「管理员不得复核业务」（FR-1403）→ `SoDPolicy` 在写入 `approval_record` 前校验角色集合，DB 触发器兜底。

### 3.3 身份与权限

#### 3.3.1 令牌链路

```
用户登录（OIDC / 本地） → 会话 JWT（TTL 8h，HttpOnly Cookie，含 tenant/org/roles/scope）
   ↓ 发起工单
工单携带 initiator_id + scope{org_id, period, system_ids}（G-05，缺一拒绝）
   ↓ worker 执行前
TokenBroker.exchange(initiator, connector, ticket_id)
   ├─ A 级连接器：OAuth2 Token Exchange / 厂商 impersonation → 短时凭据（TTL ≤ 单次任务）
   └─ B 级连接器（不支持委派）：服务账号 + 字段白名单收窄 + 强制双人复核（FR-1401 异常路径）
   ↓
凭据只存在于 connector-gw 进程内存 + `credential_lease`（加密引用，KMS/Vault）
```

硬约束：
- **令牌不出客户网络**：`connector-gw` 部署在客户侧，凭据明文永不进入 API/worker 日志（结构化日志脱敏白名单，NFR-S-10）。
- **令牌绑定 `ticket_id`**（JWT `aud`/自定义 claim），越权复用会因 ticket 不匹配被目标侧或网关拒绝。
- **B 级自动降级**：`ConnectorMeta.supports_obo == false` → `connector_cap = min(W1)` 且 `requires_dual_review = true`，连接器卡片必须显示「仅允许 W1」（FR-1506 §6.1 P6）。这条是代码推导，不靠人工标注。

#### 3.3.2 scope 校验的三道实现

| 层 | 做法 | 防的是什么 |
|---|---|---|
| API 入参 | Pydantic 模型里 `scope` 为必填嵌套对象（无默认值）；缺字段直接 422 | 忘传范围（G-05） |
| 服务层 | `ScopeGuard` 依赖注入，把 `scope` 编译成 SQL 条件（`org_id IN (...) AND period = ...`） | 业务代码手写查询漏条件 |
| 数据层 | SQLAlchemy `with_loader_criteria` 全局事件 + PG Row Level Security（`tenant_id = current_setting('app.tenant')`） | 任何「忘了加 where」的查询 | 

> 有 RLS 还要 `with_loader_criteria`：RLS 保护数据不被读出，loader criteria 让**查询计划**正确使用索引，避免全表扫（NFR-P-06）。

#### 3.3.3 职责分离（SoD）

```python
SOD_RULES = [
  # (主体角色, 禁止兼任的工单角色)
  ("platform_admin", {"reviewer", "approver"}),
  ("initiator",      {"reviewer", "approver"}),
  ("reviewer",       {"approver"}),   # 复核人 ≠ 审批人 (FR-1403)
]
```

- 校验点：① 授权接口（FR-1402 角色互斥拒绝）；② 审批写入前（工单维度）；③ DB `CHECK`（自审自批）。
- 例外路径（人员不足 → 跨组织复核人）必须**记录例外**并可在审计台账检索（FR-1403 异常分支），表结构上 `approval_record.exception_reason` 非空即进入例外视图。

#### 3.3.4 权限变更审计（FR-1408）

所有 `role_assignment` / `scope` / `threshold` / `mapping` / `whitelist` 变更走同一个 `ConfigChangeService`：写 `config_change(before jsonb, after jsonb, actor, approver, ticket_id?)` + 哈希链，禁止直接 UPDATE 配置表（DB 触发器检测「无 config_change 的配置变更」并拒绝）。

### 3.4 审计台账、前像后像与回滚

#### 3.4.1 存储分层

| 内容 | 位置 | 不可变手段 | 依据 |
|---|---|---|---|
| 字段级 diff、工单事件、审批、拦截、指标 | PG（`audit_*`、`ticket_event`） | 应用账号无 UPDATE/DELETE 权限 + 触发器拒改 + 哈希链 | NFR-C-01/02 |
| 完整前像/后像快照、单据影像、导出件 | MinIO 对象存储（Object Lock / 合规保留） | WORM | NFR-C-01 |
| 链锚点（某时刻固化的链尾边界） | `audit_anchor`：主键 `(tenant_id, anchor_date)`，存固化时链前缀的条数 `record_count` 与末行 `last_hash`；`anchor_date` 只是日标签，不代表按自然日切分 + 可选外部时间戳 | 只 INSERT | FR-1307 |

```sql
CREATE TABLE audit_image (
  id uuid PRIMARY KEY, tenant_id uuid NOT NULL,
  ticket_id uuid NOT NULL, step_id uuid NOT NULL,
  system text NOT NULL, object_type text NOT NULL, object_id text NOT NULL,
  before_ref text, after_ref text,                 -- MinIO 指针
  field_diff jsonb NOT NULL,                       -- [{field,before,after,delta}]
  diff_missing boolean NOT NULL DEFAULT false,     -- FR-1301 异常分支
  prev_hash text NOT NULL, hash text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

哈希链：`hash = sha256(prev_hash || canonical_json(除 hash 外全字段))`；**每租户一条单链**——`prev_hash` 从空串起、只在同一 `tenant_id` 内串接，`UNIQUE(tenant_id, prev_hash)` 阻止同父分叉。顺序键是 `chain_seq`（`bigint identity`，全表单调递增、**跨租户跳号**，只用于定序：同一事务内 `created_at` 可相同，不能拿它排链）。**锚点 = 某时刻固化的链尾边界（条数 + 末行哈希）**，`anchor_date` 仅作日标签、不表示按自然日切；固化后只按存储值比较，不按读取时刻的 `now()` 重算。验证任务（scheduler）可全量/分页校验（FR-1307「可校验任意时点完整性」）。**时间字段的规范形式（冻结）**：参与哈希的 `datetime` 先归一到 UTC，再按 `YYYY-MM-DDTHH:MM:SS.ffffff+00:00` 序列化（固定 6 位微秒、后缀 `+00:00`，naive 按 UTC 解释），不得依赖 `str(datetime)`——写入时的 `+08:00` 与从 PG 读回的 UTC `timestamptz` 会得到不同字符串，真实数据会被验成「疑似篡改」；`field_diff` 内嵌时间戳同一规则。依据：`apps/audit/store.py::SqlAuditStore.chain`（`WHERE tenant_id = … ORDER BY chain_seq`）、`apps/audit/models.py::AuditImageRow`（`chain_seq` Identity、`UNIQUE(tenant_id, prev_hash)`）、`apps/audit/ledger.py::AuditLedger.anchor_day`、`apps/platform/contracts/audit.py::format_hash_datetime`。

#### 3.4.2 前像的获取时机（易错点）

**前像必须在 `preview()` 阶段取，取不到就不允许写**（FR-1301 异常：「无法读取写前快照 → 该动作不允许执行，预演阶段阻断」）。实现上 `preview()` 返回三元组：

```python
PreviewResult(diff: FieldDiff, before: Snapshot, verify_spec: VerifySpec)
```

若 `before is None` → 运行时直接把工单置 `已终止`（不是 `待审批`）。这条把「审计覆盖率 100%」从承诺变成了**结构性不可能违反**（没有前像就没有写入路径）。

#### 3.4.3 三级回滚的代码映射

| 级别 | 判定（自动，非人工打标） | 实现 | 时限验证 |
|---|---|---|---|
| L1 自动回滚（FR-1302） | `action.compensation.kind in {delete_draft, release_reservation, cancel_request}` 且目标对象仍为草稿/未生效（verify 确认） | `compensation_task` 直接执行 | 记录 `rollback_started_at/ended_at`，P95 ≤15min 看板 |
| L2 人工确认（FR-1303） | 目标已审核/已占用/已入库 → 需反向单据 | 生成红冲/退回草稿（W1）+ 审批 | 4 小时内提交 = 从申请到草稿生成的 SLA |
| L3 仅告警（FR-1304） | `action.compensable == false` 或 verify 显示外部已生效（F8） | `manual_task` + 通知 + 处置结论字段 | 100% 有责任人与结论（验收项） |

自动/人工的分界由 `compensable` + `verify` 结果判定，不允许 Agent 自述。列表数据来自 `ActionSpec`，所以「哪些能自动回滚」在代码评审时可审（FR-1302 前置「动作类型在可自动回滚清单内」）。

#### 3.4.4 回滚计划（FR-1305）

`GET /tickets/{id}/rollback-plan` 由 `ticket_step` 直接推导：按 `step_no DESC` 列出，标注 `auto | manual | impossible`，汇总受影响单据与金额，并**显式高亮** `impossible` 项；存在 `touches_fund` 时前端禁止一键回滚（FR-1503 操作区规则）。计划与执行共用同一个推导函数，避免「评估说能回滚、执行却不行」。

### 3.5 连接器 SDK 与统一数据模型

#### 3.5.1 接口契约（六能力）

```python
class Connector(Protocol):
    meta: ConnectorMeta            # 系统/版本/级别 L1|L2|L3/安全等级 A|B/限流/版本指纹
    def describe(self) -> CapabilitySet: ...          # 对象、字段、动作、限流、鉴权 (FR-1201)
    async def read(self, entity, query: ReadQuery) -> ReadResult: ...
    async def preview(self, action, payload) -> PreviewResult: ...   # 必含 before + diff (G-01)
    async def write(self, action, payload, *, ticket_id, idem_key) -> WriteResult: ...
    async def verify(self, spec: VerifySpec, payload) -> VerifyResult: ...
    async def compensate(self, comp, *, idem_key) -> CompensateResult: ...
    async def health(self) -> Health: ...              # 最后同步/失败率/限流余量/指纹 (FR-1205)
```

`CapabilitySet` 里的每个 `ActionSpec` 就是 §3.2 的等级载体，**连接器实现者无法只声明「能写」而不声明等级、字段、补偿、verify**——这是 SDK 的核心价值（让 FR-1201/1202 的合规成为编译期问题）。

#### 3.5.2 能力声明与接入分级

| 声明项 | 作用 | 对应 FR |
|---|---|---|
| `access_level: L1\|L2\|L3` | L1 官方 API / L2 只读副本+中间表 / L3 RPA（MVP 不做） | FR-1201、N9 |
| `security_level: A\|B` | A 支持用户态委派；B 只能服务账号+强制双人 | FR-1401 |
| `supported_actions[]` | 动作白名单，未列出即不进 Agent 候选集 | FR-1202 |
| `authority_map` | 字段权威源；冲突禁止保存 | FR-1203、§7.1 |
| `rate_limit` | QPS/日配额/并发上限 | FR-109、FR-1205 |
| `version_fingerprint` | 版本指纹比对，变更即降 W0 | FR-1206 |

「实验性」连接器（`describe` 部分失败或版本不支持）在注册时就写 `experimental=true` → `connector_cap` 强制 W0（FR-1201 验收「实验性连接器无法进入 W1」）。

#### 3.5.3 统一数据模型（Canonical Model）

只做 5 个主对象（02 §2.2）：`Party / Item / Document / Transaction / Money`。每条记录强制携带溯源：

```python
class Canonical(BaseModel):
    model_version: Literal["1.0"]
    source_refs: dict[str, str]        # {"erp_u8": "SUP-0012", "mes": "S-88"}
    authority_system: str              # §7.1 权威源
    evidence: list[Evidence]           # system + doc_no + field + coord
```

约束（直接对应 FR 与数据需求）：
- **只增不改**：`model_version` 版本化，老 Agent 读到老字段不报错（NFR-D-05 向后兼容 ≥2 个大版本）。
- **无法归一的字段不进模型**（02 §2.2）→ 需要时 Agent 直查原系统，避免模型膨胀。
- **金额一律 `Money{amount: Decimal(18,4), currency, tax_included}`**（PRD §5.0 契约约定），禁止裸 float/str；DB 对应 `numeric(18,4)`，比较容差 0.01（G-12）。
- **缺失 ≠ 零**：`Optional[T]` + `missing_reason`，序列化后前端显示 `—`（FR-1504 §6.1「空值显示 — 不显示 0」）。

#### 3.5.4 脏数据降级（宁可不给结论）

```python
class ReadResult:
    items: list[Canonical]
    completeness: Literal["complete", "partial", "unavailable"]
    degraded: list[DegradedReason]     # {"source":"mes","reason":"timeout","from":"10:02"}
```

- `unavailable` 时返回**带类型的失败**，而不是空列表——否则上游 Agent 会把「读不到」当成「数量为 0」，直接产出错误结论（§7.3 禁止「用历史数据填充当期」）。
- 解析侧同理：`ParseResult.fields[].value is None` + `coord` 必须保留，绝不用模型猜（FR-402 验收「空缺字段不得被填充为 0」）。
- 单位换算缺失：该行标 `unit_conversion_missing`，不参与金额汇总（DQ-02/§7.3）。

#### 3.5.5 限流、重试与错误分类

```python
class ConnectorError(Exception):
    kind: Literal["transient","rate_limited","auth","forbidden","not_found",
                  "schema_changed","conflict","unknown_outcome"]
    retryable: bool
    fail_code: str        # F1..F8 映射
```

| 错误 | 重试 | 收敛动作 |
|---|---|---|
| `transient` / `rate_limited` | 指数退避 + jitter，最多 3 次（FR-1104） | 仍失败 → F5 → 补偿 |
| `auth` | 不重试 | 令牌刷新一次；再失败 → 工单中止 + 告警（令牌过期 FR-1401 异常） |
| `schema_changed` | 不重试 | 该连接器最高等级降 W0 + 触发兼容性测试（FR-1206） |
| `conflict` | 不重试 | F7，重取数（不覆盖） |
| `unknown_outcome` | **不重试** | 走 `verify`（§3.1.4） |
| `forbidden` | 不重试 | 写拦截记录（FR-1207）+ 安全告警 |

限流器：令牌桶（**落 PG `rate_bucket(tenant, connector, action, tokens, refilled_at)`**，`UPDATE ... RETURNING` 原子扣减；full 档可加 Redis 加速但 PG 为准），预算预留在**批量发起前**（不是每调用前），余量 <20% 时按比例降并发（FR-1205）。月末批量必须能算出「跑不跑得完」，这决定 NFR-P-02 是否成立（见 §6 风险 1）。

#### 3.5.6 沙箱与出网

- `connector-gw` 每连接器族一个容器：只读根文件系统、非 root、`no-new-privileges`、CPU 1 / 内存 1G / 单次调用超时 30s、出网仅目标域名（NFR-S-03）。
- 无数据库直连权限：所有落库走 `api` 的内部 token 接口 + 该接口只允许写 `interception_log`/`health` 两张表（最小权限）。
- 凭据：容器挂载 KMS/Vault 客户端，运行时取引用；吊销后 5 分钟内失效（FR-1208）→ 吊销先删 `credential_lease`，再通过网关拒绝该 connector 的全部调用。

### 3.6 幂等与去重、重试与死信

三层去重，键不同、作用不同：

| 层 | 键 | 唯一约束位置 | 对应 FR |
|---|---|---|---|
| 工单 | `tenant + scene + business_key`（供应商+期间） | `ticket` 唯一索引 | FR-1101 |
| 步骤/请求 | `{scene}:{business_key}:{line_no}:{step_no}` | `idempotency_record(key UNIQUE)` | G-02、FR-1104 |
| 对象/单据 | `supplier + doc_no + amount + date`（四元组）或文件哈希 | `document_fingerprint` 唯一索引 | FR-406、DQ-10 |

```sql
CREATE TABLE idempotency_record (
  key text PRIMARY KEY,           -- 全局唯一，含 tenant 前缀
  ticket_id uuid NOT NULL, step_id uuid NOT NULL,
  request_hash text NOT NULL,     -- 同键不同参 → 409，而不是返回旧结果
  status text NOT NULL,           -- in_flight|succeeded|failed
  response_snapshot jsonb,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

- **同键同参** → 返回首次结果（G-02）；**同键不同参** → `409 IDEMPOTENCY_CONFLICT`（这是真 bug，必须暴露）。
- 写入目标系统时，能透传幂等键的就透传（SAP/部分 REST），不能透传的（多数国产 ERP）靠「四元组预检 + 唯一约束 + verify」兜底——**这是我们自己的责任，不是目标系统的**。

重试与死信：

```
队列投递（at-least-once）
  → 消费（幂等）
  → 失败：按 error.kind 决定是否重试（最多 3 次，退避 2s/8s/30s）
  → 耗尽：写 failed_job(kind=job|compensation) + 告警
  → 运维在「失败任务」页查看并 requeue（同幂等键，安全重放）
```

`failed_job` 与 `job_queue` **同库同表族**（`failed_job` 只是 `job_queue.status='dead'` 的视图/附属表），理由：demo 不部署 Redis，且私有化环境的缓存不做持久化承诺；死信丢了就等于工单静默消失（违反 I-1）。

### 3.7 可观测性与成本归因

#### 3.7.1 追踪模型（trace 贯穿四跳）

```
trace_id (W3C) 一次工单执行一个
 ├─ span: ticket.step(n)            attributes: ticket_id, step_no, action_key
 │   ├─ span: gateway.preview        attributes: connector, latency, field_count
 │   ├─ span: gateway.write          attributes: level, idem_key, http_status, verify_result
 │   └─ span: llm.chat              attributes: model, prompt_version, in/out tokens, cost
 └─ span: audit.write               attributes: image_id, hash_prev
```

`ticket_event` 冗余存 `trace_id`，保证「任一工单可按 trace 完整回放」（NFR-O-03）不依赖观测后端存续。

#### 3.7.2 Agent 决策链（为什么这么判）

```sql
CREATE TABLE agent_decision (
  id uuid PRIMARY KEY, ticket_id uuid NOT NULL, step_id uuid,
  decision_kind text NOT NULL,        -- match|attribution|route|draft
  rule_id text,                        -- 确定性规则命中（如 attribution.stale_scrap）
  model text, prompt_version text,
  input_digest text, output jsonb,     -- 存输出（脱敏后），不存全量输入
  confidence numeric(3,2) CHECK (confidence BETWEEN 0 AND 1),
  evidence jsonb NOT NULL              -- [{system,doc_no,field,coord}]
);
```

- 置信度 <0.70 视为不可用（PRD §5.0）；`confidence` 与 `evidence` 都能被 P4 复核页直接消费，所以「每个数字可点开证据」是数据层的天然能力，不是前端补丁。
- 提示词与模型版本入库 → 模型漂移可归因（06 §3.1），也是评测集回归的输入（OQ-09 仅入库不训练）。

#### 3.7.3 成本归因

```sql
CREATE TABLE llm_usage (
  id bigserial, tenant_id uuid, ticket_id uuid, scene_code text,
  model text, prompt_version text, input_tokens int, output_tokens int,
  cost_micros bigint,          -- 按 price_version 计算
  price_version text, created_at timestamptz
);
```

用途：① 单客户毛利核算（05 §1.3 订阅毛利率 ≥75% 的验证）；② 定位「哪个 Agent 在烧钱」；③ 私有化客户按算力包计量。**不向客户按 token 计价**（05 §1.4），但我们必须自己知道成本。

#### 3.7.4 熔断与降级（G-07 的落地）

- 计数：**PG `breaker_metric(tenant, scene, bucket_1h, fail_cnt, total_cnt)`**，worker 每步结束时 `INSERT ... ON CONFLICT DO UPDATE` 累加；scheduler 每 60 秒聚合判一次（demo 无 Redis，计数不能放易失存储，否则重启后熔断状态回退，违反 NFR-A-05）。
- 状态：`breaker_state(tenant, scene, level: none|W0_only|readonly, since, reason, released_by)`。
- **生效点在 `WriteGateway`**（读 `breaker_state` 改 `breaker_cap`），不在 Agent 里自觉停手——熔断生效 ≤1 分钟（FR-1107 验收）由 scheduler 周期保证。
- 同租户同日 3 次熔断 → `readonly`：网关拒绝一切 level ≥ W1 的调用，只读与建议不中断（NFR-A-05）。
- 解除需管理员 + 留痕；1 小时内复发冷却 24 小时（FR-1107）。

### 3.8 与既有 ERP 的集成边界（「不建总账」的架构体现）

这条不是口号，它必须体现在**代码里没有那条路**：

| 架构手段 | 具体做法 | 依据 |
|---|---|---|
| SDK 里不存在这些动作 | `ActionRegistry` 的允许对象类型白名单只有：采购订单草稿、应付付款申请草稿、入库单草稿、领料单草稿、发票登记草稿、暂估入库单草稿、凭证草稿（Phase 2）、退货/补单草稿、调拨申请草稿。**没有** `post_voucher`/`execute_payment`/`certify_invoice`/`approve_document` | N1、N4、FR-1407 |
| 统一模型没有账簿实体 | Canonical 只有 5 个对象，没有 `JournalEntry`/`GLAccount`/`BankAccount`；金额只作为单据属性存在 | 02 §4.3 |
| 只读域硬编码 | `CRITICAL_READONLY_FIELDS`（库存数量、库存金额、总账科目、已过账凭证、银行账号、税率）在代码常量里，任何 `ActionSpec.writable_fields` 包含它们 → 注册期断言失败 | G-09、NFR-S-04 |
| 权威源矩阵可执行 | `authority_map` 落库，读路径按权威源取值；写路径只能写「我们为权威源」的域（对账结论、差异、工单、指标）或「原系统为权威源但允许草稿」的域 | §7.1、02 §2.4 |
| 不复制台账 | 库存/总账数据只做「读时聚合视图」，不落持久副本；缓存 TTL ≤ 5 分钟且标记 `stale`；禁止把库存数写进自己的表做「第二本账」 | 02 §4.1、§7.3 |

> 评审时必须能回答：「客户要求我们把凭证也过账，怎么拒绝？」答案：`post_voucher` 在 SDK 中不存在，要加必须过产品委员会 + 安全评审，且会破坏 I-5 与合同责任边界（06 §9 红线 1）。

## 4. 数据模型

### 4.1 核心实体与关系

```
tenant 1─n org 1─n (user_role)
tenant 1─n connector 1─n connector_action(白名单版本) 1─n field_mapping(版本)
                                  │
                                  └─n interception_log / health_sample
tenant 1─n scene(代码注册) 1─n ticket 1─n ticket_step 1─n audit_image
                                  ├─n ticket_event (append-only, hash chain)
                                  ├─n approval_record

tenant 1─n reconciliation_batch 1─n match_result 1─n discrepancy 1─n disposal_draft
tenant 1─n document(单据中心) 1─n parse_result 1─n field_evidence(coord)
tenant 1─n price_agreement(版本) / accrual / metric_baseline / metric_observation
tenant 1─n idempotency_record / failed_job / llm_usage / manual_task / notification
```

实体分组（对应开发流，见 02 §2）：

| 组 | 表 | 归属流 |
|---|---|---|
| 内核 | `tenant` `org` `user_role` `config_change` `scene` | 平台底座 |
| 工单运行时 | `ticket` `ticket_event` `ticket_step` `compensation_task` `manual_task` `breaker_state` `idempotency_record` `failed_job` | Agent 运行时 |
| 连接与主数据 | `connector` `connector_action` `field_mapping` `master_binding` `interception_log` `health_sample` `document_fingerprint` | 连接器与数据模型 |
| 对账域 | `reconciliation_batch` `match_result` `discrepancy` `price_agreement` `disposal_draft` `three_way_match` | 对账引擎 |
| 审计与权限 | `audit_image` `audit_anchor` `approval_record` `permission_audit` | 审计与权限 |
| 录入 | `parse_result` `field_evidence` `document` | 文档解析 |
| 价值 | `metric_baseline` `metric_observation` `billing_draft` | 价值度量 |

### 4.2 多租户隔离

| 形态 | 策略 | 说明 |
|---|---|---|
| 私有化（默认） | 一客户一实例，`tenant_id` 仍保留（便于迁移与备份校验） | 故障天然隔离（NFR-A-06） |
| 混合 | 数据面同私有化；控制面只存 `tenant_id` + L1/L2 元数据 | 06 §4.3 |
| SaaS（Phase 3） | 同一库 + `tenant_id` + RLS；超大客户可选独立 schema | 避免过早分库 |

统一实现（三形态共用一套代码）：
1. 所有业务表首列 `tenant_id uuid NOT NULL`，所有唯一索引以 `tenant_id` 开头。
2. PG RLS：`USING (tenant_id = current_setting('app.tenant_id')::uuid)`，连接池 `SET LOCAL` 每事务设置。
3. 应用层 `with_loader_criteria` 兜底，防「忘了 where」。

### 4.3 审计与版本表设计要点

| 要点 | 做法 | 为什么 |
|---|---|---|
| 只追加 | 应用账号仅 INSERT/SELECT；`BEFORE UPDATE OR DELETE` 触发器 `RAISE EXCEPTION` | 防「运维手改台账」（NFR-C-01） |
| 版本化而非覆盖 | 配置/协议/映射/基线：`(id, version, valid_from, valid_to, superseded_by)`，旧版本保留 | FR-201 协议版本、FR-108 重开产生新版本、FR-1601 基线冻结 |
| 作废不删除 | `status='voided'` + `void_reason` + `voided_by`，界面必须显示作废原因 | FR-108、§6.2 |
| 哈希链 | 每条审计记录 `prev_hash + hash`（每租户单链、按 `chain_seq` 定序）；链尾锚点 | FR-1307、NFR-C-02 |
| 时间 | 全部 `timestamptz`，业务期间单独 `period` 字符串（客户会计期间，G-11） | 跨期检索（NFR-C-04） |
| 脱敏 | 银行账号/手机号/身份证在写入前脱敏（`security.mask()`），原文只存引用 | NFR-S-10 |

### 4.4 容量与分区

| 表 | 量级假设（3 家客户 / 3 年） | 策略 |
|---|---|---|
| `ticket` | 千万级（NFR-P-06 口径） | 按月 RANGE 分区；索引 `(tenant_id, state, created_at desc)`、`(tenant_id, business_key)`、`gin(ticket_no gin_trgm_ops)` |
| `ticket_event` / `audit_image` | 亿级 | 按月分区 + 冷归档（>12 个月转 Parquet 落对象存储：full 用 MinIO，demo 用 `erp_objects` 卷；保留查询代理） |
| `ticket_step` | 数亿 | 按 `ticket` 同月分区（继承分区键） |
| `document` / `parse_result` | 百万 | 按 `period` 分区 |
| 指标 | 千万 | 按 `period` + 物化视图 |

检索 ≤2s 的保证不是「加索引」，而是：① 列表只查投影表 `ticket`（不 join 事件）；② 关键词走 `pg_trgm` 表达式索引；③ 深分页用 keyset（`(created_at, id) < (...)`），不用 `OFFSET`。

## 5. API 与契约

### 5.1 对外 API 风格

| 项 | 约定 | 理由 |
|---|---|---|
| 风格 | REST + JSON，`/api/v1`，资源化（`/tickets`、`/batches`、`/connectors`） | 7 个页面是资源浏览型，不是 RPC；OpenAPI 可直接生成 TS 客户端 |
| 契约来源 | FastAPI 自动生成 OpenAPI 3.1；`contracts/openapi.json` 入库，**CI diff 即破坏性变更检测** | 契约先行（02 文档 §1） |

| 幂等 | 写接口支持 `Idempotency-Key` 头；缺失时对危险接口直接 400 | G-02 |
| 分页 | keyset（`?cursor=&limit=`），导出走异步任务 + 下载链接 | NFR-P-07、FR-1306 |
| 版本 | 只做 `v1`；破坏性变更走 `/v2` 并存 ≥2 个大版本（NFR-D-05） | |

- Schema 与 Pydantic 模型**同源**（Pydantic 生成 JSON Schema，入库 `contracts/agent/*.json`）；CI 校验「代码生成的 schema == 冻结的 schema」，不等即失败。
- 每个工单记录 `input_schema_version` / `output_schema_version`，回放时按当时版本校验（NFR-O-03）。
- `additionalProperties: false` 用于输入（防注入）；输出侧宽容（允许新增字段），但关键字段必须存在。

### 5.3 MCP 工具契约

| 项 | 约定 | 理由 |
|---|---|---|
| 传输 | Streamable HTTP + OAuth2；网关**拒绝**任何 `stdio` server 注册 | NFR-S-01 |
| 工具名 | `{connector_alias}__{action}`，如 `erp_u8__create_payment_draft` | 可反解到 ActionSpec |
| 必填入参 | `ticket_id`、`idempotency_key`、`scope` | 无工单的调用在网关直接拒绝（I-1） |
| 参数 schema | 由 `ActionSpec` 生成，`additionalProperties: false` | 参数注入防护（06 §2.2-3） |
| 工具发现 | 只返回「在当前用户 scope + 连接器白名单 + 场景允许」交集中的动作 | FR-1202 验收「未在白名单的动作不可见」 |
| 签名 | manifest 用 Ed25519 签名，网关校验后才注册 | 工具投毒防护 |
| 出站 DLP | 网关对 payload 做 L3/L4 字段检测，命中即拒绝并记 `interception_log` | NFR-S-06、FR-1207 |

### 5.4 错误码体系

格式：`E-{DOMAIN}-{NNN}`，与 F1–F8 双写（UI 显示 F 码 + 人话 + 下一步，§6.3「Agent 失败」）。

| 域 | 码 | HTTP | F 映射 | 含义 / UI 下一步 |
|---|---|---|---|---|
| 授权 | `E-AUTHZ-001` | 403 | — | 超出数据范围 → 申请入口 |
| 授权 | `E-AUTHZ-002` | 403 | — | 字段 scope 不足（资金字段只读） |
| 策略 | `E-POLICY-W3FORBIDDEN` | 403 | — | W3 动作被拒 → 安全事件，无重试 |
| 策略 | `E-POLICY-LEVEL` | 403 | — | 等级不足（取严后）→ 联系管理员改配置 |
| 策略 | `E-POLICY-APPROVAL` | 409 | — | 审批未满足 → 跳审批页 |
| 幂等 | `E-IDEM-CONFLICT` | 409 | — | 同键不同参 → 报障 |
| 状态 | `E-STATE-ILLEGAL` | 409 | — | 非法状态迁移 → 报障 |
| 数据 | `E-DATA-MISSING` | 422 | F1 | 缺数据 → 显示缺失清单（不猜） |
| 数据 | `E-DATA-UNBOUND` | 422 | F4 | 主数据未绑定 → 绑定流程 |
| 数据 | `E-DATA-AMBIGUOUS` | 422 | F3 | 匹配歧义 → 人工裁决 |
| 解析 | `E-PARSE-FAILED` | 422 | F2 | 转补录（带影像对照） |
| 连接 | `E-CONN-UNAVAILABLE` | 503 | F5 | 连接器不可用 → 只读降级提示 + 重试 |
| 连接 | `E-CONN-RATE_LIMIT` | 429 | F5 | 限流 → 自动退避，显示预计恢复 |
| 连接 | `E-CONN-SCHEMA_CHANGED` | 502 | F5 | 版本漂移 → 已降 W0，联系运维 |
| 校验 | `E-VERIFY-MISMATCH` | 409 | F6 | 写入值不符 → 自动补偿中 |
| 冲突 | `E-CONFLICT-VERSION` | 409 | F7 | 并发版本变化 → 重新取数 |
| 外部 | `E-EXTERNAL-EFFECTIVE` | 409 | F8 | 外部已生效 → 生成处置任务（不可回滚） |

## 6. 关键技术风险与早期验证

每条风险都给「不验证就不能开工」的 spike，产出物入库 `docs/spikes/`。

| # | 风险 | 为什么是架构级 | 早期验证（spike） | 通过判据 | 失败后的架构退路 |
|---|---|---|---|---|---|
| 1 | **ERP 限流撑不住月末批量**（假设 A5） | NFR-P-02（100 批次/2 万行/90 分钟）是商业承诺，限流不够则产品不可用 | 用 Odoo/ERPNext + 客户同款国产 ERP 测试账套，按真实并发 4 跑 100 批次，记录 QPS 上限、429 比例、单批耗时 | 在「限流余量 ≥20%」约束下 ≤90 分钟 | 只读副本承担读 + 写侧串行化 + 错峰窗口（03 §A1 已允许），并把承诺改为「分时段完成」 |
| 2 | **写入结果未知时的 verify 覆盖不足** | §3.1.4 的整个崩溃安全设计依赖 verify 可判定 | 故障注入：在调用后/提交前杀进程、丢响应、超时，共 200 次；统计 verify 结论分布 | `unresolved` <5%，且 100% 进人工处置不被静默 | 对 verify 能力弱的系统强制「写前四元组预检 + 只允许删除型补偿」，并把该类连接器降 W1 上限 |
| 3 | **真实厂商接口不支持用户态委派**（FR-1401） | 若全部退化为 B 级，「以发起人身份执行」的核心承诺失效 | 用友 U8/YonSuite、SAP（OData/BAPI）、通用 REST 各实测 token exchange / impersonation | ≥1 个主力 ERP 支持 A 级；B 级降级路径可跑通双人复核 | 产品口径改为「B 级为主」，把双人复核做成默认而非例外，销售材料同步调整（需产品决策） |
| 4 | **字段级坐标回链准确率**（FR-402、97%） | 证据不可下钻则 P4 复核页失效（I-1/I-4） | 200 张真实脱敏对账单/发票：`pypdfium2`（+ Phase 2 PP-Structure）+ VLM 兜底，测字段准确率与 bbox IoU | 数值字段 ≥99%，bbox 命中（人工判定）≥95% | 退化为「整页高亮 + 行级定位」，并在 PRD 记 OQ；不接受「无坐标」 |
| 5 | **单库 10M 工单检索 + 10 万条导出** | NFR-P-06/P-07 决定私有化是否可用 | 造 1000 万工单 + 1 亿事件数据，跑列表/详情/导出 | 检索 P95 ≤2s；导出 ≤10 分钟 | 引入 `ticket_search` 读模型（物化表）+ 冷热分层；导出改流式 + 分片并发 |
| 6 | **审计 WORM 与哈希链的性能** | 每笔写入都要算链，月结峰值可能拖慢写入 | 1 万条/分钟压测：链写入、锚点固化、全量校验耗时 | 写入 P95 ≤2s（含链）；单日校验 ≤5 分钟 | 链按租户分片并行；单日多锚点 |
| 7 | **私有化无 GPU 时 LLM 能力** | 16C/64G 无 GPU（NFR-D-02）跑本地模型可能不达标；不达标则归因/解释能力缺失 | 本地 7B/14B（4bit）跑「差异归因 + 解释 + 意图识别」200 条金标准 | 归因准确率 ≥85%（与人工一致）；单次 ≤10s | 确定性规则兜底（NFR-A-04 已要求），LLM 仅在联网 API 模式启用；销售时明确算力要求 |
| 8 | **补偿在真实系统不可执行**（如某些 ERP 草稿不可删） | 回滚成功率 100% 是 Go/No-Go 判据（§10.2-5） | 对 6 个 MVP 连接器逐动作做「建草稿 → 删草稿 → 校验」矩阵测试 | 每个 W1 动作都有可验证的补偿路径 | 该动作降为 W0 或改为「红冲草稿」；补偿矩阵成为连接器验收清单的必填项 |
| 9 | **并入 hulkai 后主机容量与路由冲突** | 广州机 4C4G，实测余 ~2.3G 内存 / ~44G 磁盘；`/api/` 已被 mfg 占用；镜像仓库缺失 | 在 hulkai 同构环境（同版本 Docker + nginx 模板）上做一次「双栈并存」演练：起 `smart-erp` demo profile（5 容器 1200m）+ 渲染新 nginx 模板 + 走 `/erp/api/` 全链路 | 5 容器合计 RSS ≤1.5G 且宿主机无 OOM；两栈容器/卷/网络/端口零重名；`/api/` 行为不变 | 关 `obs`、降 worker 并发、推迟 docparse；仍超则按 §1A.10 切档位 2 |
| 10 | **共用 PG15 实例的连带故障**（实例级 OOM/磁盘满/慢查询/连接数打满） | 我们把工单、审计、幂等、队列全压在这一个实例上；实例挂了不只是"读不到"，是**写入审计也停**（I-1 无法满足） | ①在共用实例上做一次「注入坏查询 + 满连接 + 打满磁盘」的故障演练，看 APS 与我们各自的报错形态；②核 `CONNECTION LIMIT` 与实例 `max_connections` 的余量；③演练一次「从共用实例恢复到新库」（`pg_dump -n erp` → `smart_erp_restore` → 改连接串起栈） | ①我们的坏查询被 `statement_timeout=30s` 截断，不拖垮 APS；②`erp_app` 触顶时快速失败并有明确告警；③恢复演练 RTO ≤30 分钟且数据一致 | 档位 2 起不再共用：自带 PG 实例（`self-db` profile 或托管 RDS），连接串与备份体系一并迁移（§1A.10 档位 2 切换动作） |

**开工顺序建议**：风险 1/2/3 必须在「连接器 SDK 定稿」前完成（它们决定 SDK 接口形态）；风险 4 与前端 P4 页并行；风险 5/6 在平台底座阶段完成；风险 7 独立于主线但影响销售口径；风险 8 随每个连接器交付逐项关闭；**风险 9/10 是 M1 出 demo 之前的前置门**（9 决定云端能否起栈，10 决定共用实例能否被接受），其中 10 的恢复演练必须在第一次真实数据入库前完成。
