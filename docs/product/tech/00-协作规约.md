# 协作规约｜并发开发看板 · 聚合型 AI ERP（Phase 1 / MVP）

> 适用：所有参与本仓库并行开发的 Agent 与工程师。
> 基线：[02-并发开发路线.md](./02-并发开发路线.md)（9 条流 S0–S8、契约 C1–C15、里程碑 M0–M6）。
> 三个入口：**看板 `index.html`**（状态与冲突）· **留底 `dev-ledger.json`**（唯一真源）· **本规约**（动作纪律）。

---

## 0. 一条铁律

**代码改了、状态没改 = 没做。** 留底里查不到的工作，视为未发生，评审与验收一律不认。

---

## 1. 开工前（每次任务，无例外）

1. **读 `dev-ledger.json` 与 `index.html`**：确认目标任务当前状态、负责人、最近一次留底时间。
2. **确认未被认领**：任务已是「开发中」且负责人不是你 → 停手，先与负责人/集成负责人确认，不得并行改同一任务。
3. **查路径独占**：项目的每个目录只归一条流（路线 §4.1、§4.6）。看板亮红「路径冲突」时，先解决归属，再写代码。
4. **查串行门**：契约（G0/G1/G2）、迁移链、`WriteGateway`、埋点规范、镜像 tag、共用实例开通——六段未过，不开工（路线 §3.1）。

## 2. 认领（进入「开发中」）

必填三项，缺一不可，看板会拒绝流转：

| 字段 | 要求 |
|---|---|
| 负责人 `owner` | 开发者标识，如 `dev-al-02`（不是姓名缩写、不是「我」） |
| 开始时间 `start` | 实际开工时间，精确到分钟 |
| 独占路径 | 本任务将改动的目录/文件，一条任务一组路径 |

> 同一目录同时被两个「开发中」任务声明 → 看板告警；跨流重叠必须改由 Owner 合并。

## 3. 过程中

- **阻塞立刻标**：转为「阻塞」并写清「等谁 / 等什么 / 预计解锁条件」。不得静默停更超过 1 个工作日。
- **负责人变更必须留痕**：走「变更负责人」，旧负责人保留在留底里，不接受直接改名覆盖。
- **公共资产单独标记**：改 `contracts/`、`db/migrations/`、`apps/api/main.py`/`deps.py`、部署面（`deploy/smart-erp/`、`scripts/`、`projects/smart-ERP/docker/`、`smart-erp.yml`、`tests/deploy/`）→ 任务必须打「共享契约 / 部署面」标记，并走变更流程（路线 §1.3、§4.2、§4.6）。

## 4. 提交评审（进入「待评审」）

- 必填**证据** `evidence`：分支名 / commit sha / PR 号 / 产物路径，至少一项可核验。
- 证据只写「已完成」「见群」视为未填，看板会拒绝（长度 <6 字符也拒绝）。
- 评审人必须是非本流成员 + 独占文件 Owner（路线 §4.5）。

## 5. 关闭（进入「已关闭」）

- 必填**验收结论** `note` + **关闭人** `closer`；结论要写清验收口径与结果，不写「OK」。
- **断言对象集合，不要断言元素个数**（2026-11-11 补充，通用验收原则）：断言「所有入队的补偿行都 done」「所有过期租约都可接管」这类集合性质，不写死「三行」「两条」。写死个数会在 fixture 变化时先红后改数字，把「对象错了但数对了」放过去——今晚这类问题出现过不止一次。用例可以顺带打印实际个数作观测，但判据必须是集合本身。
- **跳过「待评审」直接关闭一律拒绝**：状态机只允许 `待开始 → 开发中 → 待评审 → 已关闭`。
- 关闭后字段锁定，不可改状态/负责人/时间；只能新增「补充记录」（同样进留底）。

## 6. 交接与变更

- 交接 = 导出 `dev-ledger.json` + 快照 JSON，随 PR 或交付物一起提交，接收方导入后再动手。
- 负责人变更、状态回退、取消任务，都必须有留底条目与原因。
- 契约类变更：先改 `contracts/`（RFC），再改实现；不得「先按新契约写，再回头要求契约改」（路线 §4.3）。

## 7. 违规处理

| 现象 | 处理 |
|---|---|
| 改了代码但状态未更新 | 由集成负责人在当日同步会点出，补录留底并说明时间差；重复发生 → 该流暂停合并 1 个工作日 |
| 未评审直接关闭 / 伪造证据 | 关闭记录作废，任务打回「待评审」，当事人当轮不得再关闭任务 |
| 改他人独占目录未提 PR | 变更回退，按原 Owner 流程重提；记入 §4.1 例外统计 |
| 绕过看板直接改 `dev-ledger.json` 历史行 | 视为篡改，整份文件以仓库版本为准回滚，并补一条「更正说明」留底 |

## 8. 看板与留底更新纪律

**这是硬性机制，不是建议。** 看板 `index.html` 与 `dev-ledger.json` 是并发的唯一事实来源；状态落后于工作树，等同于任务未完成。

| # | 时点 | 必须做的事 |
|---|---|---|
| 1 | 每个开发会话开工前 | 读 `docs/product/tech/dev-ledger.json` 与本目录 `index.html`：确认自己的任务未被他人认领、独占目录不与他人「开发中」任务重叠；有冲突先报告，不得先写代码。 |
| 2 | **每次状态变化当轮** | 开工 / 待评审 / 关闭 / 阻塞 / 交接，必须在**同一轮**追加一条留底：真实 `ts`、`actor`、`type`、`from`→`to`、证据（分支 / commit / PR / 产物路径）、备注。**写哪里**：集成写主台账 `dev-ledger.json`，`seq` 取追加时的 `next_seq`（**追加前重读当前 max，不得沿用上一轮读数**）；其他流只写自己的 `ledger/<流>.jsonl`（本地序号自增），需要进主台账的内容交集成汇总。允许在当轮内修改该条，跨轮不允许。 |
| 3 | 关闭 | 必须同时有**验收结论**（`note`）与**关闭人**（`actor`/`by`）；必须经过「待评审」，缺一即拒绝关闭。关闭后字段锁定，只能追加补充记录。 |
| 4 | 发现不一致 | 谁发现看板与工作树不一致（声明有产物但仓库没有、代码已改状态没改），**当轮修正**并在留底 `note` 写明「修正原因 + 核对依据（文件 / 测试命令 / 提交）」；跨轮批量补录不被接受。 |
| 5 | 共享台账写入 | **`dev-ledger.json` 只有集成会话能写**；其他流只写自己的 `ledger/<流>.jsonl`，由集成在合并时汇总进主台账。任何人需要全局序号，查主台账；留底写自己的。集成写入后必须核对 `next_seq == max(seq) + 1`、`dups` 为空。<br><br>**理由（2026-11-11 实测，不是手滑）**：10:22 集成读到 `next_seq=342`；10:43 另一会话按自己的读数写入 342；10:52 集成按 10:22 的旧读数盲写三条 → `dups=[342]`。**「追加前重读 max」只是把窗口变窄，不消除窗口**——两个写者在「读」与「写」之间都能进入，窗口大小只取决于两次操作的间隔。已发生的重号按 `ts` 顺序重编为 343–345，并追加 `seq=346` 记录原因与教训；**保留记录，不抹**。各流自写自的 jsonl 不共享序号，不会互相覆盖。 |

**禁止事项（违反即按 §7 处理）**

- 任务已经做完而看板仍显示「开发中」，或反过来「已关闭」但无产物、无测试、无验收结论。
- 事后批量补状态（例如一次性补十几条历史流转）。补录必须能对应真实交付时点，并在 `note` 注明是补录与原因。
- 用调整 `ts` 的方式掩盖时钟回拨。本机时钟曾从 23:50 回拨到 23:37：**`ts` 仅供参考，先后一律以 `seq` 为准**；检测到倒退 / 未来 `ts` 只告警，不修改时间戳。
- 直接手改 `dev-ledger.json` 的历史行（见 §7 末行）。

**核对口径**：声明「已完成」= 工作树存在对应文件 **且** 能跑通对应测试；两者缺一，状态不得高于「开发中」，并在 `note` 写明缺什么。

## 9. 发布纪律（2026-11-11 补充，硬性）

起因：各流把工作停在**未提交状态**等「统一合并」，导致 `origin/main` 长期落后于工作树。S8 取证时 main 的 gw 镜像启动即 `ModuleNotFoundError`（`CMD` 还指向 `connectors.gateway`，代码实际在 `apps/connectors/gateway.py`），doc 镜像与 full 档在 main 根本不存在。据此立三条硬规矩：

| # | 规矩 | 判定方式 |
|---|---|---|
| 1 | **达到「待评审」必须当轮提交到分支并开 PR**，不允许把工作停在未提交状态等统一合并 | 状态置「待评审」时，留底 `evidence` 必须含分支名 + PR 号；工作树仍有该流未提交文件即判违规 |
| 1.1 | **「待评审」必须同时有 PR 链接；没有 PR 的「待评审」一律视为「未提交」** | 看板上处于「待评审」但 `evidence` 里没有 `#<PR 号>` 的任务，验收方有权直接拒收，且不得计入发版范围 |
| 2 | **`origin/main` 任何时刻必须能构建、能起、测试绿**；发现不能，当轮修，不得留到下一轮 | 以 `git ls-remote origin refs/heads/main` 的 sha 为唯一基准；CI 红、镜像构建失败、容器起不来任一出现即当轮修 |
| 3 | **发布登记前必须验证该 sha 真能构建并起容器**（不是看 Dockerfile） | 构建镜像 → 起容器 → `GET /healthz` 返回 200，三步证据写进 `deploy/smart-erp/RELEASES.md`；`RELEASE-CHECKLIST.md` 第 0 步门禁未过，不得登记发布 |
| 4 | **主工作树永远停在 `main`**；任何分支作业只在独立 worktree 里做 | `git -C <主工作树> rev-parse --abbrev-ref HEAD` 必须是 `main`。切分支必须先 `git status --porcelain > 快照`，切后重比文件集合与内容（行尾归一化后再比 sha256）确认未变；分支在 `git worktree list` 里必须挂到独立目录 |
| 5 | **CI 未触发即视为未验证**，不能算通过 | PR 的 checks 为空或 `skipped` 一律按「未验证」处理，不得据此合并；为此 `pull_request.paths` 改为**排除法**（只忽略确定无关的路径），新增文件类型不会被静默漏掉 |
| 6 | **`contracts/api/*` 单点 owner：只由 API 流生成**，生成命令只允许在 API 流自己的 worktree 里执行，其他人一律只读 | 同一契约文件在短时间内出现多个 sha，或多个会话各自跑 `--write`，即判违规；其他人的契约变更只能通过「等 API 流定版 sha → rebase」获得 |
| 7 | **禁止「临时替换文件再还原」的验证** | 任何验证必须在 `git worktree` 检出的目标分支（或 `git archive` 导出的只读目录）里跑，跑完删 worktree；不许在主工作树手工换文件、跑完再「按字节还原」——不可复现，还原失败就把旧文件留给下一个会话 |
| 8 | **重构安全语义字段必须附「构造期不变量清单」**，由提 PR 的人写进 PR 描述，逐条写「保留 / 等价替代 / 删除理由」 | 见 §9.1。PR 描述无清单即拒收；删除归一化/拷贝/校验且无等价替代者直接拒；评审证据以 blob 级 `+N/−M` 逐行为准，**不以「测试全绿」为通过依据** |

**本次教训（v0.2.0 就是被这条卡出来的）**：发布前核对时发现两条「待评审」任务在留底里只有文字说明、没有 PR——`web/`（S6）与 `contracts/api/` 契约（API 流）都停在「工作树里有、主干里没有」。版本号看起来一切就绪，实际主干缺 45 个前端文件与 1 份契约，`build-images.sh` 直接拒绝构建、`npm run gen:api -- --check` 报 ENOENT。故补第 1.1 条：**没有 PR 的「待评审」按「未提交」处理，不得计入发版范围**。

**配套要求**

- 积压清理按批进行：**一批一个 PR**，批前在独立 worktree 跑该批目录测试，合并后再跑一次全量；进行中的流（产品 API 层、S2 对账改进等）不得掺入。
- 只用独立 worktree 或 `git archive` 作业，禁止在主工作树切分支（会带走其他流的未提交文件）。
- CI 门禁本身也是「main 可发布」的一部分：`pull_request.paths` 必须覆盖 `apps/`、`observability/`、`tests/`、`deploy/`、`projects/`、`db/migrations/`、`contracts/`、`scripts/`、`pyproject.toml` 与工作流自身；发现「只改测试的 PR 不触发 CI」这类盲区，当轮补。**现行做法改为排除法**：只列出确定无关的路径（如 `dist/**` 构建产物），其余一律触发——白名单式 `paths` 每新增一种文件类型就会静默漏跑一次（`.git-blame-ignore-revs`、`docs/**`、`*.md` 都曾这样漏掉）。
- 任何**批量机器修改**（`ruff --fix`、格式化、批量重命名）合并前必须给出「仅等价变换」的逐类证明，格式见 `deploy/smart-erp/RELEASE-CHECKLIST.md` 的「合并前自证」条；该提交 sha 必须写入仓库根 `.git-blame-ignore-revs`。

**已知陷阱：`npm run <script> -- <args>` 的 `--` 不能省。** 省掉后 `--check` 会被 npm 自己吞掉，脚本按默认（生成）模式执行——S8 执行 `npm run gen:api --check` 时因此把 `web/src/api/generated/contract.ts` 重写了一遍，**且没有任何报错**。一律写 `npm run gen:api -- --check`，并在跑完后 `git status` 确认生成物没被动过。

### 9.1 构造期不变量清单（2026-11-11 补充，硬性）

起因：T005 把收窄校验抽成独立方法时，`__init__` 里的

```python
self._narrowed_fields = None if narrowed_fields is None else frozenset(narrowed_fields)
```

被改写成 `self._narrowed_fields = narrowed_fields`，`frozenset` 归一化作为「顺手删掉的一行」消失。**全部测试仍然全绿**：当前所有调用方恰好都传 `frozenset`，校验处还有 `set(...)` 兜底，行为完全一致。危险在于防御性归一化防的是将来有人传 `list` 或可变 `set`——那时白名单与调用方共享引用、可被事后篡改，而类型注解在运行时不做检查。该问题只有在合并前做**逐字节 blob 比对**（`+18/−10` 逐行数）时才现形，看 hunk 的 code review 也容易漏。

**触发条件（任一命中即适用）**

1. 涉及**安全/权限语义字段**：字段白名单、写等级 W0–W3、权限收窄、数据 scope、审计链、幂等键、凭据、金额字段；
2. 涉及**构造期不变量**：归一化（`frozenset`/`set`/`Decimal`/`int`）、防御性拷贝、冻结/只读化、构造期校验；
3. 重构形式为「把含上述任一项的逻辑**抽成独立方法**」。

**执行人**

| 角色 | 什么时候做 | 做什么 |
|---|---|---|
| **改动方（提 PR 的开发流 Agent）** | 开 PR 前自测时 | 在 **PR 描述正文**附「构造期不变量清单」，逐条写「保留 / 等价替代 / 删除理由」；清单缺失即视为未完成自测 |
| **评审方（契约/平台 owner 或对端流）** | 合并前 | 只**抽查**清单与 diff 是否一致；不得替改动方补清单，也不得以「评审时我自己去找」替代 |

清单由**提 PR 的人**写，不是等评审人从 hunk 里倒推；评审人没有清单可直接拒收。

**清单格式（写进 PR 描述，逐条填写）**

```markdown
## 构造期不变量清单（LESSON-01）
| 不变量 | 原实现 | 重构后 | 处理 | 依据 |
|---|---|---|---|---|
| 字段白名单归一化为不可变集合 | `frozenset(narrowed_fields)` | `frozenset(narrowed_fields)` | 保留 | 防止调用方传入可变集合后共享引用 |
| 构造期校验仅接受 W0–W3 | `_validate_level()` | `_validate_level()` | 等价替代（抽为方法） | 断言未变 |
| …… | | | 删除 | 理由必须写明；无等价替代者评审直接拒 |
```

**判定方式（可检查）**

- PR 描述**没有**上述清单 → 不得进入「待评审」，评审方直接拒收；
- 清单出现「删除」但**没有等价替代**、也没写删除理由 → 直接拒；
- 至少补**一条直接断言该不变量的测试**（如传 `list` 后断言内部仍是 `frozenset`），不得只靠端到端功能测试；
- 评审证据以 **blob 级 diff 的 `+N/−M` 逐行**为准，**不以「测试全绿」作为通过依据**——「绿」是必要条件，不是语义等价的证明。

**边界（避免形式主义）**

- 只覆盖上述三类触发条件；普通重构（改名、拆函数、纯格式）不要求附清单。
- 清单只针对**构造期**不变量（`__init__`、工厂、`dataclass` 构造、Pydantic validator 等），不扩展到运行期所有状态。
- 本条不替代 §9 第 3 条的发布验证（构建 → 起容器 → `/healthz` 200），只补「语义等价」这一层。

**为什么同时写进 §9 表格第 8 行**：2026-11-11 已有一次「正文里有规矩、但没人想起来去看」——断言加了、`-o addopts=""` 也加了，仍等到 PR 合完才红。表格是硬规矩的索引，索引漏了等于规矩不存在；正文保留细节，表格只做入口。

**模板只放这一处**：`deploy/smart-ERP/RELEASE-CHECKLIST.md` 的「合并前自证」条只写一行指向本节，不复制模板。同一份声明写在两处，迟早不一致——`8011` 的 compose 与文档、`ERP_*` 的代码与 `.env.example`、`statement` 与 `supplier_statement` 都是这么来的。

## 10. 编码约法：租户谓词必须进查询条件（2026-11-11 补充，硬性）

起因：S4 跨租户 / IDOR 扫描（17 条路径 18 个探测）发现 13 条越权，根因只有一条——**工单相关读取按主键取到记录后再比较租户，没有把租户写进查询条件**。修一次契约比逐端点补 `where` 更耐久，故立为硬规矩：

| # | 规矩 | 判定方式 |
|---|---|---|
| 1 | 面向租户资源的读方法，`tenant_id` 必须是**查询条件**（随查询下推），不得先按主键取回再过滤 | 仓储读方法签名必须含 `tenant_id`（`TicketRepository.get/all/list`、`ReconBatchRepository.get`、`ReconStore.load`、`AuditQuery`）；`tests/security/test_tenant_query_guard.py` 反射守卫，漏一个即红 |
| 2 | 跨租户访问一律 **404**，不得用 403 | 403 等于确认「该 id 存在、只是不属于你」，是跨租户存在性预言机；`tests/security/test_idor_scan.py` 断言 404 |
| 3 | 身份比较必须带租户，即 `(tenant_id, user_id)`，不得只比 `user_id` | UUID 跨租户碰撞时，只比 `user_id` 会让租户闸与身份闸同时失效（GI-11）；`_require_initiator` 与 `test_cross_tenant_colliding_initiator_must_not_execute` |
| 4 | 列表接口必须按会话租户收口，且不得返回他租户行 | `test_idor_scan` 列表型探测：200 可以，但不得出现他租户数据 |

**例外口径**：同租户内「资源不属于当前用户」的拒绝保持 403/409 的语义码，不得一并退化成 404，否则审计无法区分「越权」与「不存在」。拒绝必须发生在写闸门之前（连接器零预览零写入）。

## 11. 内容摘要必须先归一 EOL（2026-11-11 补充，硬性）

起因：同一提交在两个平台算出两个 sha256，已发生**两次**。第一次是 `contracts/api/*.json` 的契约 sha（Windows 落盘 CRLF、提交内 blob 为 LF，三个 sha 对不上）。第二次是 `fixtures/recon/golden/*` 的金标准基线：`tests/recon` 直接对 `read_bytes()` 取 sha256，基线在 Windows 生成、把 CRLF 哈希写进了 `source_sha256` / `sha256`，CI 按 LF 检出后 4 条用例红，而本地（CRLF 工作树）全绿。

| # | 规矩 | 判定方式 |
|---|---|---|
| 1 | 凡对仓库文件取内容摘要（sha256 等），**先归一 EOL 再哈希**：`data.replace(b"\r\n", b"\n")`，或经 `newline="\n"` 的文本模式读取后再编码 | 代码里出现 `hashlib.sha256(...read_bytes())` / 直接对 `read()` 结果哈希且未归一即判违规；`tests/recon/file_digest.py` 是现成入口，新代码一律复用 |
| 2 | 摘要值一旦写进仓库文件（契约 sha、基线 sha、`engine_sha256`），**必须能在纯 LF 检出里复现** | 验证方式：`git checkout-index -a --prefix=<空目录>` 导出 LF 检出，在该目录跑对应测试；不许只在 Windows CRLF 工作树里看到绿就交 |
| 3 | 不要指望 `.gitattributes` 兜底 | 现有 `* text=auto eol=lf` 只保证**检出**为 LF；脚本在 Windows 自己写出的文件仍是 CRLF，所以哈希前归一才是治根 |

## 12. 验证必须显式用 Python 3.12（2026-11-11 补充，硬性）

起因：本机默认 `python` 是 **3.11.9**。`apps/connectors/retry.py` 用了 PEP 695 语法（`type X = ...` / 新式泛型参数），3.11 解释器一读就 `SyntaxError`——看着像代码写坏了，实际是解释器旧了。当晚为此白排查过一轮。

| # | 规矩 | 判定方式 |
|---|---|---|
| 1 | 所有验证（`pytest` / `ruff` / 自检脚本）必须**显式指定 3.12**：仓库 `.venv` 或 `python3.12`，不得裸跑 `python` / `pytest` | 命令里看不到 3.12 的解释器路径，即视为「未验证」 |
| 2 | 报测试结果时必须**注明解释器版本**（`python --version` 的实际输出） | 汇报缺版本号，验收方有权要求重跑 |
| 3 | 遇到 `SyntaxError` 先核解释器版本，再怀疑代码 | — |

## 附 A：`dev-ledger.json` 字段说明

追加式，只允许在末尾新增条目；不改写历史。同目录 `index.html` 可导入/导出该文件。

> **留底随文档一起入库（2026-11-11 变更）。** `docs/product/` 已从 `.gitignore` 放开，留底与规划文档随分支正常提交与 PR；远程协作者通过 `git log` 即可查看每次状态变化。不再需要按 §6 导出文件单独传递，也**不再使用 `git add -f`、不再走补丁包**。唯一例外是 `docs/product/tech/.snapshots/`（旧的无版本控制时期的重复副本），已在 `.gitignore` 单独排除。

| 字段 | 必填 | 说明 |
|---|---|---|
| `seq` | 是 | 单调递增整数，写入时由写入方分配（当前文件最大 `seq` + 1）；**排序与「谁覆盖谁」的唯一依据** |
| `ts` | 是 | `YYYY-MM-DD HH:mm`，本地时区；仅用于展示与时钟异常检测（`ts` 倒退或未来 `ts` 时告警），不参与排序 |
| `task_id` | 是 | 如 `T302` |
| `task_title` | 否 | 便于人读 |
| `stream` | 否 | `S0`–`S8` |
| `type` | 是 | `状态流转` / `负责人变更` / `补充记录` |
| `from` | 是 | 原状态标签；补充记录填 `—` |
| `to` | 是 | 新状态标签；补充记录填 `—` |
| `actor` | 是 | 开发者标识（操作人） |
| `evidence` | 待评审必填 | 分支 / commit / PR / 产物路径 |
| `note` | 关闭必填 | 备注 / 验收结论 / 阻塞原因 |
| `payload_before` / `payload_after` | 否 | 变更前后字段快照（负责人、开始时间、状态） |

**导入合并策略**：按 `seq` 升序追加 → 重复条目（`seq` 相同且内容一致）去重 → 同任务取 `seq` 最大者为当前状态 → 只有 `seq` 大于本地该任务最大 `seq` 的条目才回放任务字段 → 同一 `seq` 指向不同记录时保留本地、导入方顺延新 `seq` 并标红，交人工裁定，不覆盖任何历史。旧格式无 `seq` 的条目按 `ts` 升序接在本地最大 `seq` 之后，回放时以 `ts` 兜底。`ts` 只用于展示与时钟异常检测：**检测到 `ts` 倒退或未来 `ts` 时看板告警，但不改变排序、不阻断操作**（本机曾出现时钟从 23:50 回拨到 23:37，故判定先后一律以 `seq` 为准）。

**未同步提示**：看板顶部显示「留底更新 / 未同步 N 条」。未同步 ≠ 数据丢失，表示页面领先于文件，需要导出并提交。

## 附 C：集成会话（唯一 git 操作方）作业规则

开发流一律不碰 git；提交、分支、PR 只由集成会话执行。以下三条为硬约束。

**C-1 禁止在有流写入时切分支。** 只要工作树里还有开发流在写文件，禁止 `git checkout` / `git switch` 到其他分支。提交必须满足其一：

- 目标分支就是当前分支（直接 `git commit`）；或
- 处于「无任何流写入」的时间窗口内，且**操作前先用 `git status --short` 记录未跟踪文件清单**，操作后逐项核对文件仍然存在。

原因：git 会删除「当前分支已跟踪、目标分支没有」的文件。本仓库的常态是「全部代码以未跟踪文件形式躺在工作树上」，一旦这些文件被另一分支跟踪过，切走即从工作树消失——2026-11-10 已实际发生一次（S0 与 S8 的 `apps/platform/`、`contracts/`、`db/`、`deploy/`、`scripts/`、`.github/`、`tests/platform|deploy/` 被切分支删除，后用 `git restore --source=<分支> --worktree -- <路径>` 全量还原）。

**C-2 每次 commit 前做保护性检查。** 先列出待提交清单（`git diff --cached --name-only`），确认其中**不含** `__pycache__/`、`*.pyc`、`node_modules/`、`dist/`、`.env`（`.env.example` 除外）、`docs/product/tech/.snapshots/`。发现命中即**停下来报告**，不得自行删除别人目录里的文件，也不得用 `git add -f` 绕过忽略规则。只按显式文件名 add，禁用 `git add -A` / `git add .` / 目录级 add。

**C-3 留底与规划文档随分支正常提交与 PR（2026-11-11 变更）。** `docs/product/**` 已从 `.gitignore` 放开，不再依赖本地工作树；文档改动与代码改动一样走「分支 → commit → PR → 评审 → 合并」，**不再使用 `git add -f`，不再走补丁包**。原因：文档在忽略列表里时，定稿依据只存在于口头汇报和台账中，`git log` 查不到、PR 里看不到，评审无从核对（2026-11-11 三份文档定稿即为此付出代价，教训见 `流差距卡.md` §3.3 第 16 条）。唯一单独排除项是 `docs/product/tech/.snapshots/`（旧的无版本控制时期的重复副本，理由写在 `.gitignore` 注释里）。
