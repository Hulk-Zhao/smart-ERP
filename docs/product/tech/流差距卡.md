### 3.1 共享工作树纪律（2026-11-11 定，S8 提出、集成采纳）

- **⛔ 三条前置条件（2026-11-11 04:58 事故后追加，硬性）**：任何对共享工作树的**破坏性操作**（`reset` / `rebase` / `checkout` / `stash` / `clean`）执行前必须同时满足三件——① **已在全部在跑会话广播并收到确认**；② **已做时间戳快照**（含未跟踪文件本体与 `git diff`）；③ **在台账记「谁批准、谁执行、影响了谁」**。三件缺一不得执行。04:56:12 那次 reset 只做到 ②（且未含全部未跟踪文件），跳过 ①，代价是 16 个已跟踪文件里 S6 的 6 个前端改动被还原成 main。
- **⛔ 第四条（2026-11-11 05:0x 追加）**：执行前再问一句「**这棵树现在有没有人把它当工作区**」。答案不能靠「按约定它只读」推出，**要看实际 mtime 与近期台账**。例如 04:56 前 S6 的 6 个文件 mtime 全是 04:56:12（即被 reset 那一刻），说明在那之前它们一直是活的；`git status` 干净不构成「没人丢东西」的证据，**干净恰恰是刚被还原的表现**。
- **⛔ 第五条：reset 前必须先贴 `git status --porcelain` 并取得集成会话确认（2026-11-11 05:1x 追加）**：任何会话要在共享工作树执行 `reset`，先跑一次 `git status --porcelain` 把**原样输出**贴给集成会话；由集成会话逐条确认「无归属不明的在途改动」后才可执行。缺这一步，任何「按约定它只读」的推论都不成立——S6 那 6 个文件的丢失，根因就是 reset 在另一会话有未提交改动时执行。**根因不是 diff 不清，是没问谁在写。**
- **`unowned-changes/tracked.diff` 的地位是「留档，不是补丁源」**：该文件含 16 个文件的改动，其中 `.github/workflows/smart-erp.yml` 是删掉整个 `web-checks` job 的废弃残留。**禁止整体 `git apply`**——那会在恢复代码的同时删掉一个 CI job。恢复单个文件必须显式 `--include=<path>`，且恢复前先对该文件单独复核 diff。实测该 diff 无法干净地正向应用（preimage blob 不在仓库历史里，`git apply -3` 也回退到直接应用并失败），因此**逐个文件人工确认是唯一安全做法**。
- **绝对禁止带 `-x` 的 clean**（`git clean -fdx` / `-fdX` / 任何含 `-x` 的形式）。原因：`docs/product/` 整个目录被 `.gitignore` 第 8 行忽略、**从未进过任何提交**（`git log --all` 对这些路径输出为空），里面有看板 `index.html`、`dev-ledger.json`、`00-协作规约.md`、`01–07` 规划与商务文档、`tech/` 全部技术文档与 `ledger/*.jsonl`——**没有任何 git 历史可以恢复**。`git reset --hard` 本身不动忽略文件，危险在于「顺手清理」。需要清理构建产物时只针对具体路径执行，不做目录级清理。
- **禁止清理 `dist/` 与 `web/dist/`**：它们是当前前端产物的唯一证据（`web/dist` 里还留着 S6 正在回收的新文案），删掉就没有可比对的产物了。
- **快照（唯一的时间线）**：`docs/product/` 无版本控制却有多人同时写，靠「快照 + MANIFEST（每文件 sha256 + 行数）」替代版本库。路径 `e:\tools\Factroy_Agents\smart-ERP\2026-11-11\docs-snapshot\<YYYYMMDD-HHMMSS>\`；已执行：`20261111-045417`（reset 前，33 文件 / 1,360,039 bytes，另含 `unowned-changes/`）、`product-pre-overwrite`（四份机械覆盖前的原件）。频率：**每日一次 + 每次合并批次后一次**，不做定时任务。快照目录本身按 `.gitignore` 新规则 `/20YY-MM-DD/` 忽略。
- **并发写入必须留痕**：任何会话改了 `docs/product/` 下的文件，须在台账各记一条「改了哪个文件、为什么」，否则分叉调查只能靠 sha256 逐文件比对（04:56 就发生过一次：`07-商务口径与POC验收*.md` 与 `ledger/S8.jsonl` 在快照后被并发写入 +686 bytes）。
- **该树只读**：允许读取文件与只读命令（`ls`、`cat`、`git status` / `diff` / `log` 等），**禁止提交，也禁止在这棵树上跑测试**。需要提交或跑测试时一律在独立 worktree 完成（`git worktree add <dir> -b <branch> <40位sha>`），PR 由集成会话开。

### 3.5 证据纪律（四条并列）

1. **只认容器外/主干上的证据**：本地跑绿、口头汇报、工作树里的绿都不算数。引用数字必须能落到「干净检出 + 该 sha + CI 或容器内命令 + 原文输出」；见 §3.3 第 2 条「测试数只认干净检出 + 该 sha 的数字」。
2. **本地复现 CI 必须带 `-o addopts="" -rs`**：`pyproject.toml` 的 `addopts = "-q"` 与命令行 `-q` 叠加成 `-qq`，pytest 会吞掉 `N passed / M skipped` 汇总行，于是引用的数字没有出处（2026-11-11 的「本地 72 / CI 68」假差异即由此而来：汇总行缺失 + 本地多收集）。命令模板：

   ```bash
   python -m pytest <dir> -q -o addopts="" -rs
   ```

   汇报时必须贴这条命令的汇总行原文（含 `passed` / `skipped` 与 skip 原因），不能只写「通过了」。CI 的按目录步骤已统一使用该口径（`-q -o addopts="" -rs`），本地复现不得简化。
3. **跨分支语义冲突：各自绿、合起来错**。两条分支验的是同一个函数的两个版本时，「都验过」不产生任何保证。2026-11-11 实例：demo 种子（#121，`c8b62a9`）用修复前的 `compute_image_hash` 生成并验得 `54/0`，而 #119 的 `a127378` 改了规范形式（UTC、固定 6 位微秒、`+00:00`，`canonical_json` 不再用 `str(datetime)`）；两者合并后种子与验链函数版本不一致，演示页会再报「疑似篡改」。规则：改了被下游依赖的函数，PR 描述必须列出「谁在用旧口径」，并对每个下游给出重生成 / 重验要求；引用数字必须带生成它的函数版本（sha）。这是「本地绿、CI 红」的同族问题——验证环境与被验证环境不是同一个。
4. **stacked PR 的 diff 不能混入依赖分支的提交**。base 设错（该 base=依赖分支却设成 `main`）会让 diff 把依赖分支的改动算进本 PR，评审看不出哪几行是本意。2026-11-11 实例：demo 分支 rebase 到 `feat/audit-anchor-wiring` 后，base 必须显式设 `feat/audit-anchor-wiring`，描述第一行写「本 PR 依赖 #119，必须先合 #119」；依赖合入后 retarget 到 `main` 再合。同族检查：合并前核净差异文件清单，出现依赖分支的文件即说明 base 设错。
