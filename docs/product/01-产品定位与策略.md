# 产品定位与策略

> 版本：v0.1（待评审）
> 上游依据：《AI ERP 市场与竞品调研》（2026-11-10）。本文所有定位与卖点均可追溯到该报告，引用格式为「§章节」或「§0-编号」（摘要第 N 条）。凡属本团队推断而非报告结论的，标注「推断」。

## 1. 一句话定位

> **我们不做 ERP，做存量异构系统之上的一层"可审计业务执行层"：让 Agent 在客户现有的 ERP、MES、财务、供应商协同之间，把那些必须跨系统才能完成、今天只能靠人来回搬单据的事务真正做完；每一笔写操作都可查、可批、可回滚；只对可验证的业务结果收费。**

三个要件缺一不可，且各自对应报告里的一条结构性空白：

| 要件 | 对应的空白 | 证据 |
|---|---|---|
| 跨系统**写入**（不是问答） | 头部厂商的 Agent 只在自己域内闭环，跨异构"写入型"Agent 无成熟供给 | §0-2、§1.1 表后读法、§2 表 G 行 |
| **可审计、可回滚** | 厂商的 human-in-the-loop 停留在话术；安全厂商只做网关不做业务语义审计 | §0-9、§4.3、§6-卖点5 |
| 按**结果**计费 | 按动作计费让账单不可预测，CFO 反感，且无主流厂商提供按结果计价 | §0-4、§4.4、§6-卖点2 |

## 2. 从报告里读出的四条硬事实，以及由此排除的四个方向

### 2.1 四条硬事实

**F1｜"跨系统写入"是唯一没人做透的位置。**
SAP Joule action bar 声称跨应用，但实际写入仍以 SAP 对象为主；金蝶灵基定位"企业级 AI 统一入口"，入口背后只连金蝶自己的模块；NetSuite、Oracle、Workday 同理（§0-2）。报告在 §2 的形态分类里把这一类归为 G 型，并明确其天花板就是"权限、审计、计费、厂商配合四道坎"（§2 表 G 行、§5.2）。

**F2｜"聚合"这个说法本身已经不值钱。**
SAP、NetSuite、浪潮 Mano Work、金蝶灵基、IBM 都在讲同一件事（§0-3、§5.3）。把"聚合"当卖点的产品，一出生就要和五家更大的公司抢同一个形容词。

**F3｜计费方式是当前最干净的攻击面。**
SAP 0.02 AI Unit/动作、Microsoft Copilot Credits（Agent 动作 5 分）、NetSuite AI Units，共同制造了"AI 用得越多账单越不可预测"的问题（§0-4、§1.1 各厂商定价列、§4.4）。报告同时指出席位制正在失效——一个 Agent 可以替 20 个人干活，"用的人"和"付钱的人"分离（§4.4）。

**F4｜换掉 ERP 不是理性选择，"补一层"才是。**
Gartner 判断到 2027 年超 70% 的新实施 ERP 无法完全达成原始商业目标，约 25% 属灾难性失败；中型企业实施成本 15 万–85 万美元，平均超支达原估算 189%，离散制造 215%（§0-5、§4.3）。在这种赔率下，客户更倾向保留存量、补一层执行能力（§5.1-1）。

### 2.2 由此排除的四个方向

| 不做的方向 | 为什么不做 | 证据 |
|---|---|---|
| 全能 ERP（财务+供应链+制造全自建） | 与 SAP/Oracle/用友/金蝶正面竞争，且报告已证明"重构"只在财务域被验证过（Rillet 明确不做库存与运营） | §0-6、§1.3 |
| 又一个"统一入口 / 超级入口" | 位置已被五家占位，且入口之争的赢家是已经躺在用户 Teams/钉钉/企微里的玩家 | §0-3、§5.3 |
| 单系统内的 Copilot / 预置 Agent | A/B/C 三型已是商业套件入场券，不构成差异化 | §2 关键观察 |
| AI 原生重写总账（Rillet 路线） | 需要客户数据干净、流程标准，且明确放弃多工厂/多 BOM/非标制造——这正是我们要服务的客户 | §1.3 共同点、§0-6 |

## 3. 目标客户：谁最痛、谁最可能签

### 3.1 客户画像（四个条件必须同时满足）

| 维度 | 定义 | 判断理由 |
|---|---|---|
| 行业 | 离散制造：电子组装、装备制造、汽车零部件 | 报告指出制造/供应链侧没有等价的 AI 原生挑战者（§0-6），且离散制造的实施超支最严重（215%，§4.3），替换动机最弱、补层动机最强 |
| 规模 | 营收 3–20 亿元，2–5 个工厂/法人，200–2000 人 | 大到系统已经异构、痛到愿意付钱；小到决策链不被 6–18 个月的采购流程拖死（§4.2） |
| 系统现状 | 至少 2 套异构业务系统 + 1 套自研或轻量 MES + Excel 排产 + 钉钉/企微审批 | 报告点名"一个中型制造集团可能同时有 SAP/用友财务、自研 MES、Excel 排产、钉钉审批，员工每天在 6–10 个系统间切换"（§5.1-2） |
| 组织现状 | 有明确的"月结/对账/交付"考核指标，且指标由 CFO 或运营负责人承担 | 经济买家是 CFO，但否决权在 CIO/安全（§4.2），必须同时给出财务口径的价值和安全口径的答案 |

### 3.2 明确排除的客户（同样重要）

- **单一厂商全家桶且无意混用**：这类客户的最优解是买原厂的 Agent，我们进去只会变成集成商。
- **流程制造（化工、食品、医药）**：批次/配方/合规追溯的领域模型差异过大，MVP 阶段不覆盖。
- **营收 5000 万以下的小微制造**：报告把"轻 ERP + 强 Agent"列为卖点 8，但同时指出其风险是"客单价低、服务重"（§6-卖点8）。我们选择私有化/混合交付与审计能力，成本结构撑不住这个客群，强行做会把公司做成 Odoo 伙伴。
- **要求"整体替换现有 ERP"的客户**：需求本身与我们的定位冲突。

### 3.3 这类客户为什么现在会买

1. **预算科目已经存在**：AI 支出目前多挂在数字化/ERP 升级预算下，而非独立科目（§4.2）；但国内厂商的 AI 收入证明这个科目正在变实——金蝶 2026H1 AI 原生收入 2.96 亿元（同比 +189%），用友 AI 相关签约 9.06 亿元（§0-7）。我们卖的是"在已批的数字化预算里，做原来做不成的那部分"，不需要客户新开科目。
2. **不换系统的决策成本最低**：不动总账、不动法定报表、不动生产执行，只在系统之间加一层执行与审计。
3. **安全叙事第一次能讲圆**：MCP 的系统性 RCE（2026 年 4 月，CSA 记录影响约 20 万实例）与 confused deputy 问题让 CIO 高度警惕（§0-9），此时"可审计、可回滚、用户态令牌"不是加分项而是准入条件——先做出来的产品直接吃掉这个准入门槛。

## 4. 第一个楔子：委外与采购的"跨系统对账与结算闭环"

### 4.1 楔子定义

**业务范围**：中型离散制造企业的委外加工费对账 + 采购三单匹配（订单/收货/发票）+ 差异处置 + 付款申请草稿。
**系统范围**：ERP（委外订单、采购订单、应付）＋ MES/WMS（收发料、报工、收货）＋ 供应商侧对账单（微信/邮件/Excel/PDF）＋ 财务（付款申请）＋ IM（企微/钉钉审批）。
**产出**：每个"供应商 × 期间"一张对账结论（无差异 / 有差异及归因 / 待补单据），差异项自动生成处置单，付款申请以草稿形式回写 ERP 应付。

### 4.2 为什么是这个楔子（五条判据，缺一不可）

| 判据 | 说明 | 证据 |
|---|---|---|
| 高频且周期性 | 每月必发生，不依赖客户改变工作习惯，Agent 有稳定的训练与验证样本 | 推断（基于月结周期的业务常识） |
| 天然跨系统 | 一张委外对账单要同时对齐 ERP 委外单、MES 报工、WMS 收发料、供应商自算账、财务应付，五个来源缺一不可 | §5.1-2、§6-卖点1 |
| 写入风险可控 | 产出是差异单与付款申请**草稿**，不过账、不碰资金、不动法定凭证——CIO 最容易批的第一刀 | §5.2 权限门槛、§4.3 AI 可信度 |
| KPI 是 CFO 语言 | 月结天数、对账差异率、三单匹配直通率，都是客户已有考核口径，可直接作为计费锚点 | §4.4、§6-卖点2 |
| 对手结构性缺席 | 金蝶灵基的"银企对账/三单匹配"只在自家域内（§1.2）；国际厂商不覆盖中国式委外加工费结算（§1.1）；制造侧无 AI 原生挑战者（§0-6） | 同左 |

补充一条工程判据：**这个场景不要求我们自研 APS 或 MES**，用现有系统的读写就能闭环，因此 MVP 的技术风险集中在连接器与审计，而不是领域算法——这符合"先证明执行层、再证明智能"的顺序。

### 4.3 楔子里的具体业务流（第一个闭环）

```
① 触发     月末 D-3，对账 Agent 按「供应商 × 期间」生成对账批次
② 取数     ERP 委外订单/采购订单/入库单 → WMS 收发料 → MES 报工与报废 → 供应商对账单（PDF/Excel/微信文件）
③ 归一     单据 OCR/解析 → 统一数据模型（物料/供应商/数量/单价/金额/税率）
④ 匹配     三层匹配：单据号直配 → 物料+数量+期间模糊配 → 金额差异阈值内的人工候选
⑤ 归因     差异分类：单价不一致 / 数量不符（多发少发/报废未扣）/ 税率或含税口径 / 缺单 / 重复计费
⑥ 处置     无差异 → 生成付款申请草稿；有差异 → 生成差异处置单（补单/退换/索赔/调账建议），按金额分层审批
⑦ 回写     草稿写回 ERP 应付，处置结论回写供应商协同记录；全流程留 Agent 工单（前像/后像/补偿动作）
```

### 4.4 楔子如何长成 ERP（扩张路径与每步的增量）

我们不靠"功能清单变长"来变成 ERP，而靠**持有的跨系统状态变多**：

| 阶段 | 新场景 | 新增持有的状态 | 新增写入风险等级 |
|---|---|---|---|
| 楔子 | 委外/采购对账与结算 | 对账批次、差异项、处置单 | W1（草稿） |
| 扩张 1 | 采购比价与下单建议 | 询价记录、比价结论、价格基线 | W1 → W2 |
| 扩张 2 | 库存与齐套预警、跨厂调拨 | 齐套缺口、可用量承诺（ATP）、调拨建议 | W2 |
| 扩张 3 | 生产异常处置与排程协商 | 异常单、改期/改派/委外转移决议 | W2（排程只建议，W0） |
| 扩张 4 | 报价与成本模拟 | 报价版本、成本构成、毛利底线 | W1 |
| 结果 | **一张跨系统的"执行账"**：所有跨系统事务的状态、责任、证据都在这层 | 执行账 + 审计台账 | — |

**这条路径的关键判断**：我们最终不会拥有"法定账"（总账、税务、资金），但会拥有"执行账"。这正是与 ERP 厂商的分工边界，也是我们不会被替代的原因——原厂的账里没有"跨系统"这个维度。

### 4.5 楔子选择的代价（主动承认）

- 对账是**财务运营**场景，金蝶灵基的 40+ 智能体里已包含费用审核、银企对账、采购付款三单匹配（§1.2）。我们与它在同一片战场，但差异在于：它只连金蝶，我们连客户的异构现状。**如果目标客户刚好是纯金蝶客户，这个楔子不成立**——销售侧必须把"异构"作为准入条件（见 3.1）。
- 对账的价值天花板有限（节约的是财务人力与月结天数），单靠它撑不起一家公司。它的作用是**拿到写入权限与审计信任**，为扩张 2–4 铺路。

## 5. 卖点与价值主张：8 条候选收敛成 3 条主卖点

报告第 6 节给了 8 条候选卖点（含 1 条备选）。全部保留等于没有卖点，因此必须收敛。收敛的判据不是"哪条更好听"，而是**它是否对应采购决策链上的一个具体质疑**（决策链见报告 §4.2：CEO 批准、CFO 口径验收、COO 流程验收、CIO 安全验收）。

三条主卖点分别回答三个必答题：

| 主卖点 | 回答谁的质疑 | 一句话主张 |
|---|---|---|
| **M1 跨系统闭环** | COO/业务："你能不能真的把事情办完？" | 别人给你建议，我们把它在 3–5 个系统里办完 |
| **M2 可审计执行** | CIO/安全："我凭什么敢让你写我的生产系统？" | 每一次 AI 动作都是一张可查、可批、可回滚的业务单据 |
| **M3 结果计费** | CFO："我花这笔钱能得到什么，账单会不会失控？" | 只为可验证的业务结果付费，且全年支出有上限 |

### 5.1 M1｜跨系统的事，只有我们能办完

| 项 | 内容 |
|---|---|
| **一句话主张** | 原厂的 Agent 只在自己家里干活；客户的活却横跨 3–5 个系统。我们把"最后一公里"的写入真正做完，而不是给一份建议让人去搬。 |
| **支撑证据** | §0-2：所有头部 Agent 只在自己域内闭环，跨异构"写入型"Agent 无成熟供给；§1.1 表后读法：没有一家把"跨异构系统的写入"作为核心卖点；§2 形态表 G 型：聚合入口的天花板就是四道坎，说明这块地没人做透；§5.1-2：员工每天在 6–10 个系统间切换 |
| **可量化价值** | 单笔事务的系统切换次数从 6–10 次降到 1 次；单据处理时长下降 50–70%；跨系统事务闭环率（真正办完而非"发出去了"的比例）从不可测变为可测 |
| **被谁占据** | SAP Joule action bar（可跨应用发起，但写入仍以 SAP 对象为主）；浪潮 Mano Work（入口聚合，偏查询与办公）；金蝶灵基（只连金蝶模块） |
| **我们的差异** | 三个能力同时具备：跨系统**写入** + 失败**补偿** + 过程**审计**。原厂有前两个的一半，没有第三个；集成商有第一个，后两个靠人。并用产品纪律保证不跑偏：跨系统数 < 2 的 Agent 不立项 |
| **怎么证伪** | 若客户的业务实际上 80% 能在单一系统内闭环，则 M1 不成立——这也是我们坚持"≥2 套异构系统"作为客户准入条件的原因 |

### 5.2 M2｜每一次 AI 动作，都是一张可审计、可回滚的业务单据

| 项 | 内容 |
|---|---|
| **一句话主张** | 我们不让 Agent"悄悄改数据"。每一笔写入都有工单号、有前像后像、有补偿方案、有审批人、可导出给内审和外审。 |
| **支撑证据** | §0-9：2026 年 4 月 MCP SDK 系统性 RCE（CSA 称影响约 20 万实例）与 confused deputy，导致 CIO 本能拒绝第三方写入；§4.3 把"AI 可信度（幻觉、权限越界、不可审计）"列为实施失败原因之一；§6-卖点5：原厂的 human-in-the-loop 多停留在话术，没有把 Agent 动作做成产品对象；§5.2 第二道坎：跨系统事务无法用单一数据库事务保证，失败后谁负责没有答案 |
| **可量化价值** | 写入动作审计覆盖率 100%；可回滚场景回滚成功率 100%；审计准备时间从"数天翻日志"降到"小时级导出"；安全评审一次通过率 ≥ 50%（行业常态是第三方写入方案被否） |
| **被谁占据** | SAP / Workday 的"人仍在环"叙事（有概念无对象）；安全厂商的 Agent 网关（有拦截无业务语义，不知道"这笔付款该不该放"） |
| **我们的差异** | 把审计做成**业务单据**而不是日志：工单有状态机、有影响面（金额/单据/系统）、有三级回滚策略、有双人复核防锚定、可导出对齐内审与外审。因此它既是合规能力，也是销售时的准入通行证 |
| **怎么证伪** | 若客户的安全评审即使看到工单与回滚仍一律拒绝第三方写入（通过率 < 30%），则需退化为"只读 + 建议 + 客户侧执行"模式（见 §8 证伪条件 2） |

### 5.3 M3｜按可验证的结果付费，账单有上限

| 项 | 内容 |
|---|---|
| **一句话主张** | 不按席位（AI 让席位失去意义）、不按动作（账单不可预测）。按客户已有的 KPI 计费，全年封顶，签合同时就能算出最多花多少。 |
| **支撑证据** | §0-4：SAP 0.02 AI Unit/动作、Microsoft Agent 动作 5 分、NetSuite AI Units，客户第一次面对"用得越多账单越不可预测"；§4.4：席位制正在失效（一个 Agent 替 20 人干活），按动作是新共识但体验差，CFO 尤其反感；§6-卖点2：暂无主流厂商提供按结果计价，Rillet"按复杂度不按席位"只走了半步；Gartner 调查显示 45% 的财务 AI 投入偏向提效、仅 20% 偏向决策质量，与董事会期望错位 |
| **可量化价值** | 客户年度支出可预算（有硬封顶）；对账差异率相对基线下降 ≥ 30%；月结天数下降 ≥ 3 天；有效对账行可按行计量与折算（这是默认计费口径，工时仅作封顶参照） |
| **被谁占据** | 暂无主流厂商；Rillet 的"按复杂度"是半步；按结果计费的难点在归因，报告已指出"需要合同层面设计" |
| **我们的差异** | 把归因做成产品能力而不是商务扯皮：上线前 4 周冻结基线（合同附件）、三重归因校验（前后对比 + 未接入组织对照 + 人工抽检）、只对增量且设封顶、争议时按客户口径结算。并把"价值对账"与"账单"放在同一个界面（见界面文档 P7） |
| **怎么证伪** | 若单客户为归因投入的销售/法务成本超过首年合同额 30%，则退回纯订阅模型（见 §8 证伪条件 4） |

### 5.4 其余 5 条候选怎么办（降级而非丢弃）

| 报告候选 | 处置 | 理由 |
|---|---|---|
| 卖点 3 数据体检 + 主数据修复 | **降级为销售工具与准入筛选器** | 客户不会为"体检"单独立项，但它能让我们在收钱前判断"这个客户能不能做"。做成 2 周、8–15 万的付费诊断，兼获客钩子 |
| 卖点 4 上线周期从月压到周 | **降级为交付承诺（写进 SLA）** | 它是承诺不是能力差异；Rillet 已用 4–6 周证明财务域可行，"周级上线"不再是独家卖点。但必须做到，否则连入场资格都没有 |
| 卖点 6 私有化多智能体底座 | **降级为交付选项** | 浪潮 MoirAI 已用"私有化 + 多智能体"占位；且它是部署形态而非客户价值。我们必须支持，但不作为主张 |
| 卖点 7 给存量老 ERP 补最后一公里 | **合并进 M1** | 与 M1 是同一件事的两种说法，M1 更具体、更可验证。保留其"不要求替换"的表述作为销售话术 |
| 卖点 8 中小制造轻 ERP + 强 Agent（备选） | **明确放弃** | 报告自己指出风险是"客单价低、服务重"；更关键的是它会让我们变成 Odoo 伙伴，与"跨系统执行层"的身份直接冲突。做轻 ERP 就等于放弃审计与私有化的成本结构 |

**为什么是三条而不是五条**：卖点数量必须匹配决策链上的否决点数量。三个否决点（业务、安全、财务）对应三条主张；再加任何一条都会稀释记忆点，也会让销售在面对 CIO 时讲不清重点。

## 6. "凭什么由你聚合"：四个可论证的差异

### 6.1 先承认对手的位置

| 位置 | 已被谁占 | 他们做到哪一步 | 证据 |
|---|---|---|---|
| 跨应用任务栏 / 入口 | SAP Joule action bar | 可跨应用发起，但写入仍以 SAP 对象为主 | §0-2、§6-卖点1 |
| 统一入口 / 超级入口 | 浪潮 Mano Work | 解决多系统切换与工具零散，偏查询与办公 | §1.2、§6-卖点1 |
| 企业级 AI 统一入口 | 金蝶灵基 | 40+ 智能体，但只连金蝶自家模块，客户数 26 家 | §0-3、§1.2 |
| 企业 Agentic AI 平台 / 控制塔 | IBM | 平台论述，缺业务语义的写入治理 | §0-3、§2 表 G 行 |
| 已躺在用户工作界面里 | Microsoft Copilot | Teams/Outlook 内分发，ERP 深度弱 | §1.1、§5.3 |

**结论：不能在"入口"这一层竞争。** 所以我们的答案是不去争入口，而是做入口后面的东西。

### 6.2 四个差异（D1–D4）

**D1｜寄生而非竞争：我们不建入口，寄生在客户已有的入口上。**
交互主战场是企微/钉钉/Teams 的卡片，加上一个"只需要在异常时才打开"的工作台。这与金蝶灵基、浪潮 Mano Work 的"统一入口"叙事正好相反：他们要客户把入口迁过来，我们要客户什么都不用迁。
→ 可验证指标：客户员工的日均"新系统登录次数"目标为 **0**（全部从 IM 卡片或原系统内嵌触发）。

**D2｜只做跨系统，单系统内的事主动让给原厂。**
这是产品纪律，不是话术：每个 Agent 上线前必须声明"跨了哪几个系统"，**跨系统数 < 2 的 Agent 不立项**。单系统内能完成的（例如金蝶域内的费用审核）我们不做，甚至主动引导客户用原厂能力。
→ 可验证指标：Agent 清单里 100% 的条目跨系统数 ≥ 2；产品需求评审有一票否决项"这是不是原厂能自己做完的事"。

**D3｜审计与回滚是产品对象，不是合规附件。**
每一次 Agent 写入生成一张"Agent 工单"（详见架构文档），含前像/后像、幂等键、补偿动作声明、审批链、可导出的审计台账。原厂讲 human-in-the-loop，但没有把 Agent 动作做成可检索、可审批、可补偿的业务单据（§6-卖点5）。
→ 可验证指标：写入动作的审计覆盖率 100%、回滚成功率 100%（含不可回滚场景的"升级为人工处置"路径）。

**D4｜按可验证结果计费，且账单有上限。**
计费锚点是客户已有的 KPI（对账差异率、月结天数、三单直通率），用上线前采集的基线做增量归因，年度封顶。这条直接攻击 SAP/Microsoft/NetSuite 的按动作计费（§0-4、§4.4）。
→ 可验证指标：客户可提前算出年度账单上限；账单波动 ≤ 平台费的固定比例。

**D5（支撑性差异）｜厂商中立。**
我们不卖 ERP，因此没有"把客户往自家模块迁移"的动机。金蝶、浪潮、SAP 的 Agent 都带着"扩大自家模块占比"的隐含 KPI，这让 CIO 无法把它们当作中立的审计证据提供方。中立性是结构性优势，不是能力优势。

### 6.3 为什么原厂不会马上做（以及这个窗口有多长）

**不会马上做的原因是激励结构，不是能力：**

1. **跨厂商写入会削弱自己的护城河。** 金蝶灵基若认真做"把数据写进用友/SAP"，等于帮客户降低替换成本；SAP 同理。这是典型的创新者困境。
2. **原厂的 Agent 收入模型建立在自家域内。** 按 AI Unit 计费的前提是动作发生在自家对象上（§1.1 SAP 定价列），跨系统写入的动作他们既收不到钱也管不了责。
3. **他们要背账。** 一旦 Agent 写坏第三方系统的数据，原厂要承担的是自己无法控制的系统的责任，法务与保险都不支持。

**但要承认：他们有资源在 12–24 个月内做出"够用版"。** 因此护城河不能是"想法"，只能是三样需要时间积累的东西：

| 护城河 | 为什么难被追上 | 积累方式 |
|---|---|---|
| 连接器密度与兼容性 | 每个 ERP 版本的字段、限流、鉴权都不同，是脏活；原厂没有动力做别人的 | 每签一个客户就沉淀一套连接器与兼容性测试用例 |
| 失败样本库 | "哪种单据在哪个系统会写失败、怎么补偿"只能靠真实事故积累 | 每次回滚都入库，形成补偿动作知识库 |
| 审计台账的切换成本 | 一旦内审/外审依赖我们的工单台账，换掉我们就等于丢掉审计证据链 | 审计导出格式对齐内审与外审习惯 |

**窗口判断（推断）**：报告指出未来 2–3 年拼的不是模型而是集成与治理（§4.4 末）。我们判断窗口为 **18–24 个月**，且窗口关闭的信号是：任一原厂发布"跨第三方系统写入 + 补偿事务"的 GA 版本。这个信号必须进入季度竞争监控。

## 7. 四道硬门槛怎么绕（产品机制 / 技术机制 / 合同机制）

报告 §5.2 列出四道坎。下面每条都给三层解法，并说明"绕不开的部分怎么认输"。

### 7.1 权限与安全（confused deputy、MCP RCE）

| 层 | 机制 |
|---|---|
| 产品 | **不做万能凭据**。Agent 以"发起人身份"运行（用户态令牌透传），不持有超越发起人的服务账号；连接器注册时必须声明"动作白名单 + 字段级 scope"，未声明的字段物理不可写；金额/系统/字段三维阈值触发动作级审批 |
| 技术 | 凭据存客户侧 KMS，令牌不出客户网络；禁用 MCP 的 STDIO 传输，仅允许 HTTP + OAuth2；连接器运行在沙箱容器内（出网白名单 + 只读挂载）；工具清单签名 + 版本锁定 + 参数 schema 校验 |
| 合同 | 明确"我们不是数据处理者而是受托执行方"的边界；越权写入的责任划分；客户保留随时吊销连接器凭据的单方面权利 |

**认输的部分**：对不提供用户态委派（impersonation）的老系统，我们只能退化为"服务账号 + 字段白名单 + 双人复核"，并在产品里显式标注该连接器的安全等级为 B 级，不允许承载资金类动作。

### 7.2 写入的审计与回滚

| 层 | 机制 |
|---|---|
| 产品 | 引入 **Agent 工单**作为一等对象：每次写操作一张单，含前像/后像、幂等键、补偿动作声明、影响面（金额/单据数/系统）、审批链。跨系统事务用 Saga 编排，失败按逆序执行补偿 |
| 技术 | 补偿分三级：自动回滚（安全域，如未审核的草稿单）、人工确认回滚（资金/库存域）、仅告警并升级人工（外部已发出，如已付款/已通知供应商）。不可补偿动作一律走"红冲/反向单据"，绝不删数据 |
| 合同 | 定义"部分成功"的验收口径；明确回滚的时限承诺（如 15 分钟内完成自动补偿）；把审计台账的保留期写进合同（建议 ≥ 法定会计档案年限） |

**认输的部分**：跨系统无法做到数据库级强一致。我们不承诺"要么全成要么全不成"，只承诺"每一步都有可查状态 + 有明确补偿路径 + 有人负责"。这句话必须写进销售材料，不能藏在附录。

### 7.3 厂商配合度（API 限流、字段缺失、版本变更）

采用三层接入策略，按系统开放程度分级，**不追求"什么系统都能写"**：

| 级别 | 接入方式 | 允许的写入等级 | 典型对象 |
|---|---|---|---|
| L1 官方 API / 开放生态 | 原生 API、OData/BAPI、公开扩展点 | W0–W2 | Odoo、ERPNext、用友/金蝶开放平台、SAP OData |
| L2 数据只读 + 标准中间表 | 只读副本 / 视图 / 中间表交换 | W0–W1（写回走客户既有接口） | 老版本 ERP、自研系统 |
| L3 界面语义化 RPA（兜底） | 理解业务动作的 RPA，不是录屏脚本 | W0–W1 | 无 API 的封闭系统 |

配套机制：每个连接器有**健康度 SLA**（最后同步时间、失败率、限流余量）与**版本变更监控**；同一系统尽量保留两条接入路径（接口优先、界面兜底），避免单点被厂商掐断。合同层面要求客户在其 ERP 合同中确认"允许第三方集成"，把厂商封禁的风险前置暴露。

### 7.4 计费与价值归属

| 层 | 机制 |
|---|---|
| 产品 | 内置"基线—当期"对照仪表盘，客户与销售看同一组数字；只对可归因增量收费 |
| 技术 | 上线前 4 周采集基线（同一口径、同一数据源）；增量归因采用"前后对比 + 未接入组织作对照 + 人工抽检校准"三重校验 |
| 合同 | 基线协议作为合同附件；计费只算增量且设年度封顶；明确"不参与 ERP 许可分成、不改变客户与原厂的合同关系" |

**认输的部分**：归因争议永远存在。我们的做法是"争议时按客户口径结算 + 下一周期重谈基线"，把争议成本当作获客成本，而不是靠法务硬扛。

## 8. 这个定位在什么情况下不成立（证伪条件）

写清楚证伪条件，比写清楚优势更有用。以下任一条件成立，定位需要重做：

1. **异构客户不存在**：目标行业里 80% 以上的中型制造企业已是单一厂商全家桶，且不打算混用。→ 需要销售在一线用 20 家客户样本验证。
2. **CIO 一律拒绝第三方写入**：即使有审计与回滚，安全评审通过率低于 30%。→ 退化为"只读 + 建议 + 客户侧 RPA 执行"模式，商业模式需重算。
3. **原厂在 12 个月内 GA 跨第三方写入 + 补偿事务**：护城河窗口消失。→ 转为"垂直行业执行模板"提供商，靠行业 know-how 而非平台能力竞争。
4. **结果计费的归因成本高于收益**：每个客户为归因投入的销售/法务成本超过首年合同额的 30%。→ 退回"平台订阅 + 连接器数"的纯订阅模型。
5. **楔子跑不通**：3 家试点客户在 6 周内无法把对账闭环跑到"差异率下降 30%"。→ 说明数据质量或系统开放度不达标，应前置"数据体检"产品（报告 §6-卖点3）作为筛选器。

## 9. 本文件的结论摘要（给评审用）

1. **定位**：异构存量系统之上的可审计业务执行层，不是 ERP、不是入口。
2. **客户**：营收 3–20 亿、2–5 个工厂、≥2 套异构系统 + 自研 MES 的离散制造企业；排除单一全家桶、流程制造、小微。
3. **楔子**：委外加工费 + 采购三单的跨系统对账与结算闭环；选它的核心理由是高频、天然跨系统、写入风险可控、KPI 可直接计费、对手结构性缺席。
4. **卖点**：从 8 条候选收敛为 3 条——M1 跨系统闭环（答业务）、M2 可审计执行（答安全）、M3 结果计费封顶（答财务）；其余 5 条分别降级为销售工具、交付承诺、交付选项、合并或放弃。
5. **差异**：寄生入口（D1）、只做跨系统（D2）、审计回滚产品化（D3）、结果计费封顶（D4）、厂商中立（D5）。
6. **门槛**：权限靠用户态透传 + 字段白名单 + 动作级审批；回滚靠 Agent 工单 + Saga 补偿 + 三级回滚；厂商靠 L1/L2/L3 分层接入 + 健康度 SLA；计费靠基线协议 + 三重归因 + 封顶。
7. **代价**：对账的价值天花板有限，它的作用是换取写入权限与审计信任；纯金蝶客户不适用本楔子。
