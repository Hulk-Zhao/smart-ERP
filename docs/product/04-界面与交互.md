# 界面与交互

> 版本：v0.1（待评审）
> 前提：产品要求"界面简洁方便"。本文不写视觉风格，只写信息架构与交互规则——因为界面复杂度的根因不是配色，是**层级、入口和默认值**。

---

## 1. 五条界面原则（每条都配一条可验收的标准）

### 原则 1｜统一入口，但入口不止一个

主入口只有一个（工作台），但**大部分日常动作不发生在工作台里**：Agent 的结果以卡片形式推到企微/钉钉/Teams，在原系统里以浮层形式出现。工作台是"异常时才打开"的地方。

- 可验收标准：业务人员完成一次对账确认，**不需要登录我们的系统**（在 IM 卡片里完成）。
- 反例：要求用户每天上班先打开我们的首页看仪表盘——那就是又一个系统，报告 §5.1-2 说的"6–10 个系统切换"问题会被我们加重一次。

### 原则 2｜对话是入口，卡片是结果

对话只负责两件事：**表达意图**（"帮我看下 A 供应商这个月的账"）和**追问**（"为什么这行差了 3200"）。所有结构化产出必须是卡片（表格、diff、单据预览、影响评估），不是一段文字。

- 可验收标准：对话回答里**不允许出现超过 3 行的纯文字结论**；任何数字都可点击下钻到来源单据字段。

### 原则 3｜层级不超过两层

导航最多两层：一级是"今天要做什么"，二级是对象详情。**没有"模块树"**——不设"采购管理 → 订单管理 → 订单列表"这种三级结构。

- 可验收标准：从首页到任意一个业务对象的详情页，点击次数 ≤ 2。
- 反例：照抄 ERP 的菜单结构。客户已经有 ERP 了，我们不是替代它。

### 原则 4｜任务流优先，模块让位于"这件事办完没有"

首页的组织单位是**待办任务与异常**，不是功能模块。同一个业务事务（如"某供应商 10 月对账"）在首页、对话、审批、报表里都是**同一张卡**，状态同步。

- 可验收标准：一个事务在任意入口打开，看到的工单号、状态、金额、责任人完全一致（同一对象，不同视图）。

### 原则 5｜默认给结论和下一步，不给数据

每个页面打开时，第一屏必须回答"现在什么情况、我该做什么"。数据表放在第二屏。

- 可验收标准：任何页面的首屏必须包含一句自然语言的**状态结论**和一个**主操作按钮**；没有主操作的页面不允许存在。

### 补充：三条克制

| 克制 | 说明 |
|---|---|
| 不做仪表盘墙 | 指标最多 6 个，且每个指标必须能下钻到单据。堆 20 个图的首页等于没首页 |
| 不做功能培训 | 如果某个页面需要培训才会用，说明信息架构错了。只做"业务语义"培训（什么叫差异归因），不做"功能"培训 |
| 不做移动 App（MVP） | 移动场景全部用 IM 卡片覆盖。做 App 等于多一个要维护的入口 |

## 2. 导航结构

```
┌ 工作台（Today）              ← 默认落地页，一屏
├ 对话（Ask）                  ← 全局唤起（⌘K / 悬浮球 / IM 里 @机器人）
├ 我的事项
│   ├ 待复核                    ← 我作为审批人的队列
│   ├ 异常队列                  ← 需要人判断的异常
│   └ 我发起的                  ← 我触发的 Agent 任务
├ 连接器                       ← 管理员视图
└ 报表与结算                   ← 月度/季度查看，非日常
```

**只有 5 个一级入口**，其中"我的事项"下 3 个二级。没有第三个层级。

## 3. 七个核心页面

### P1 工作台（Today）

**目的**：30 秒内知道今天要处理什么、有多少钱卡在这里。
**进入方式**：登录默认页；IM 卡片"查看全部"；每日 8:30 推送摘要。

```
┌───────────────────────────────────────────────────────────────────────┐
│ 今天 11月10日 周二      月末对账进行中：38/52 家已平  [进入对账视图]    │  ← ① 状态结论条
├───────────────────────────────────────────────────────────────────────┤
│ 待我处理 (7)                                                          │
│ ┌───────────────────────────────────────────────────────────────────┐ │
│ │ [高] A 供应商 10 月对账 · 差异 ¥32,400 · 归因：报废未扣            │ │  ← ② 任务卡
│ │      建议：核减 12 件 · 影响付款 · 截止 11/12    [复核] [详情]      │ │
│ ├───────────────────────────────────────────────────────────────────┤ │
│ │ [中] 收货单 SR-20261108-014 抽取置信度 0.72 · 缺"批次号"  [补录]    │ │
│ ├───────────────────────────────────────────────────────────────────┤ │
│ │ [低] B 供应商对账单未收到 · 已催 2 次 · 逾期 3 天        [催办]      │ │
│ └───────────────────────────────────────────────────────────────────┘ │
├───────────────────────────────────────────────────────────────────────┤
│ 本月指标（对比基线）                                                  │
│ 对账差异率 1.8% ↓42%  │ 单供应商工时 26min ↓61% │ 直通率 78% ↑        │  ← ③ 6 个以内，可下钻
├───────────────────────────────────────────────────────────────────────┤
│ Agent 正在跑 (3)  A1 对账批次#2211 · 执行中 62%  │ A8 暂估 · 待审批     │  ← ④ 后台任务（可折叠）
└───────────────────────────────────────────────────────────────────────┘
```

**放什么 / 不放什么**：

| 区域 | 放 | 不放 |
|---|---|---|
| ① 状态结论条 | 一句话说明当前业务状态（月末进度、异常总数、影响金额） | 欢迎语、产品公告 |
| ② 待处理卡片 | 按"影响金额 × 截止时间"排序，每张卡必须含：对象名、关键数字、一句话建议、主操作 | 只有标题没有结论的待办 |
| ③ 指标条 | ≤6 个，带基线对比与趋势箭头 | 折线图墙、环形图 |
| ④ Agent 后台任务 | 正在执行的工单、进度、卡在哪一步 | 技术日志 |

**关键交互**：
- 卡片主操作直接在卡片上完成（如"复核"弹出侧栏，不跳页）。
- 任意数字点击 → 侧栏打开来源（单据字段 + 原单影像 + 匹配依据）。
- 空状态不写"暂无数据"，写"本月 52 家供应商已全部对平，下一批 12 月 3 日生成"。

### P2 对话（Ask）

**目的**：用一句话拿到结论或发起任务；不支持"聊天式闲聊"。
**进入方式**：⌘K / 右上角悬浮球 / IM 里 @机器人 / 原系统浮层。

```
┌───────────────────────────────────────────────────────────────────────┐
│ 范围：[全部组织 ▾] [2026-10 ▾] [已连接 4 个系统]                       │  ← ① 范围选择器（常显）
├───────────────────────────────────────────────────────────────────────┤
│ 你：A 供应商这个月为什么差了 3 万多                                     │
│                                                                       │
│ ┌─ 结论卡 ────────────────────────────────────────────────────────┐   │
│ │ 差异 ¥32,400，主因：报废未扣（¥28,900，89%）                      │   │  ← ② 结论先行
│ │ 次因：单价不一致（¥3,500，1 笔）                                  │   │
│ │ 依据：MES 报工报废 12 件，对账单未扣减；采购单 PO-...-091 单价 42 │   │
│ │ 建议：核减 12 件后重新对账，付款金额 ¥1,286,300                   │   │
│ │ [生成调整单草稿] [查看差异明细] [转人工]                          │   │  ← ③ 主操作即写入
│ └───────────────────────────────────────────────────────────────────┘   │
│                                                                       │
│ 你：为什么是 12 件                                                   │
│ ┌─ 证据卡 ────────────────────────────────────────────────────────┐   │
│ │ 工序 30 报工 120 件 / 报废 12 件（11/03、11/07 各 6 件）          │   │
│ │ 来源：MES · 工单 WO-...-2211 · 可点击跳转原系统                  │   │
│ └───────────────────────────────────────────────────────────────────┘   │
├───────────────────────────────────────────────────────────────────────┤
│ [输入框] 支持：@单据号 / @供应商 / 上传对账单 / "帮我对平这个月"       │  ← ④ 输入区带能力提示
└───────────────────────────────────────────────────────────────────────┘
```

**规则**：

| 规则 | 说明 |
|---|---|
| 范围必须显式 | 不选范围不允许提问（避免"问的是全公司还是这个厂"的歧义），默认带上次范围 |
| 结论卡必须有主操作 | 只给结论不给动作的对话 = 聊天机器人 |
| 写入必须二次确认 | 点击"生成调整单草稿"后弹出 diff 预览（写哪个系统、哪些字段、金额），确认才执行 |
| 不做多轮闲聊 | 超出业务范围的输入直接回"我只能处理已连接系统里的业务问题" |
| 引用可点 | 每个数字带来源角标，点击打开证据面板 |

### P3 Agent 任务详情（Agent 工单）

**目的**：回答"它到底做了什么、能不能信、出问题怎么办"。这是产品的信任核心页。

```
┌───────────────────────────────────────────────────────────────────────┐
│ AT-20261110-0038  A 供应商 10 月对账          [已完成]  ¥32,400 差异   │  ← ① 标题 + 状态 + 影响
│ 发起：定时任务（月末 D-3）  执行：2m18s  写入 2 个系统   ⓘ 跨 5 个系统   │
├───────────────────────────────────────────────────────────────────────┤
│ ① 计划 → ② 预演 → ③ 审批 → ④ 执行 → ⑤ 校验 → ⑥ 完成                  │  ← ② 状态机进度条
├───────────────────────────────────────────────────────────────────────┤
│ 执行时间线                                                            │
│ ┌ 10:02:11  读取 ERP 委外订单 14 张 · 入库单 22 张                    │  ← ③ 每步可展开
│ ├ 10:02:19  读取 MES 报工 120 件 / 报废 12 件                         │
│ ├ 10:02:41  解析供应商对账单 PDF（置信度 0.94）                        │
│ ├ 10:03:02  匹配：直配 18 行 / 模糊 6 行 / 未匹配 1 行                 │
│ ├ 10:03:15  发现差异 1 项 · 归因「报废未扣」                          │
│ ├ 10:04:20  创建差异处置单 DT-...-091（草稿）   [查看 diff]           │  ← ④ 写入行必须带 diff 入口
│ └ 10:04:29  校验通过：草稿金额 = 结论金额                              │
├───────────────────────────────────────────────────────────────────────┤
│ 变更影像（2 个对象）                                                  │
│ ┌ DT-...-091 差异处置单 · 新建                                         │
│ │ 供应商 A │ 数量 -12 │ 金额 -¥28,900 │ 原因：报废未扣                 │  ← ⑤ 字段级 before/after
│ └ 应付·付款申请草稿 · 未创建（等待差异确认）                           │
├───────────────────────────────────────────────────────────────────────┤
│ 影响面：应付减少 ¥28,900 · 影响 1 家供应商 · 不触及资金与凭证          │  ← ⑥ 影响面独立成块
├───────────────────────────────────────────────────────────────────────┤
│ [批准并提交] [驳回] [回滚此工单] [导出审计记录]                        │  ← ⑦ 操作区（按权限显隐）
└───────────────────────────────────────────────────────────────────────┘
```

**设计要求（逐条对应可审计性）**：

| 区块 | 为什么必须有 |
|---|---|
| 跨系统数 | 让客户一眼确认"这确实是我们做不了的事" |
| 状态机进度条 | 让"卡在哪一步"成为可观测状态，而不是黑箱 |
| 时间线每步可展开 | 展开后可见：调用了哪个接口、读了哪些字段、返回了什么、耗时多少 |
| diff 入口 | 审批人不需要理解 Agent，只需要看懂"改了什么" |
| 变更影像 | 支持"前像/后像"逐字段对比，红绿标注 |
| 影响面 | 用业务语言（金额、供应商、是否触及资金）而非技术语言描述后果 |
| 导出审计记录 | 内审/外审要的是文件，不是界面 |

**回滚交互**：点击"回滚"先展示**回滚计划**（将撤销哪几步、哪些可自动、哪些需人工、预计耗时），确认后执行；不可回滚的步骤置灰并说明原因（如"该单据已在 ERP 审核，需红冲"）。

### P4 复核与审批中心

**目的**：让复核成为"看证据做判断"，而不是"点同意"。
**进入方式**：工作台卡片、IM 卡片、导航"待复核"。

```
┌───────────────────────────────────────────────────────────────────────┐
│ 待复核 7   [按风险 ▾]  批量：[选择]  [全部批准(0)]                     │  ← ① 批量但有门槛
├──────────────────┬────────────────────────────────────────────────────┤
│ 队列              │  复核详情：AT-20261110-0038                        │
│ ┌──────────────┐ │ ┌─ 并排对比 ────────────────────────────────────┐  │
│ │▸A 供应商 ¥32k │ │ │ 项目      │ 我方（ERP+MES）│ 供应商账单 │ 差异 │  │  ← ② 三方并排
│ │ B 供应商 ¥1.2k│ │ │ 数量      │ 132 件         │ 144 件     │ -12  │  │
│ │ C 供应商 ¥80  │ │ │ 单价      │ 42.00          │ 42.00      │ 0    │  │
│ │ ...           │ │ │ 金额      │ ¥5,544         │ ¥6,048     │ -504 │  │
│ └──────────────┘ │ └───────────────────────────────────────────────┘  │
│                  │ ┌─ 证据 ────────────────────────────────────────┐  │
│ 风险标识          │ │ [MES 报工单截图] 工序30 · 120件 · 报废12件     │  │  ← ③ 原始证据
│ · 金额 > 1万      │ │ [供应商对账单 PDF · 第2页高亮第7行]            │  │
│ · 首次合作供应商   │ │ [采购单价协议 · 2026-06 生效]                  │  │
│ · 触及应付        │ └───────────────────────────────────────────────┘  │
│                  │ ┌─ 判断 ────────────────────────────────────────┐  │
│                  │ │ Agent 建议：核减 12 件，¥28,900                │  │
│                  │ │ 归因：报废未扣（置信度 0.91）                  │  │
│                  │ │ 我的意见：[________________]                   │  │  ← ④ 必填意见
│                  │ │ [批准] [修改后批准] [驳回并说明] [转上级]      │  │
│                  │ └───────────────────────────────────────────────┘  │
└──────────────────┴────────────────────────────────────────────────────┘
```

**关键规则**：

1. **双人复核防锚定**：第二复核人打开时，**默认不显示第一复核人的意见**，只显示证据与结论；两人都提交后才互相可见。若两人结论不一致，强制三方会审。
2. **批量批准有硬门槛**：只有金额 < 500 元、无差异、非首次合作供应商的任务可批量；其余必须逐条。
3. **批准必须留意见**：空意见不允许批准（防止"一路点同意"）。意见进入审计台账。
4. **"修改后批准"是主路径**：允许复核人直接改金额/数量再批准，系统记录"人工修正值"与"Agent 建议值"的差——这些差值就是模型改进的训练样本。
5. **驳回必须选原因**：归因错误 / 数据错误 / 证据不足 / 规则不合理 / 其他（必填文本）。原因直接进评测集。

### P5 异常队列

**目的**：把"没人管的事"变成"有人管、有期限、有归因"的事。
**与 P4 的区别**：P4 是 Agent 已给结论、等人签字的；P5 是 Agent 也给不出结论、必须人来判断的。

```
┌───────────────────────────────────────────────────────────────────────┐
│ 异常 23   [全部 ▾] [按影响金额 ▾] [我的 ▾]         SLA 超期 4          │
├───────────────────────────────────────────────────────────────────────┤
│ 类型分布：缺单 9 │ 账实不符 6 │ 单位换算 3 │ 匹配歧义 3 │ 接口失败 2   │  ← ① 分诊视图
├───────────────────────────────────────────────────────────────────────┤
│ ┌───────────────────────────────────────────────────────────────────┐ │
│ │ 缺单 · A 供应商 · 有收货无订单 · ¥86,400 · 逾期 2 天               │ │  ← ② 一行说清
│ │ 缺：PO 关联 · 收货单 SR-...-014（11/08）                          │ │
│ │ 建议动作：补建采购订单草稿（依据 3 个月历史价 ¥42）  [生成] [分派]  │ │
│ ├───────────────────────────────────────────────────────────────────┤ │
│ │ 账实不符 · 物料 M-8821 · 系统 1,200 / 盘点 980 · 差异 220         │ │
│ │ 建议动作：发起盘点复核（Agent 不改库存）           [发起] [忽略]   │ │
│ └───────────────────────────────────────────────────────────────────┘ │
├───────────────────────────────────────────────────────────────────────┤
│ 本周根因 Top3：供应商未按格式开单(12) · 单位换算(5) · 收货未关联订单(4)│  ← ③ 根因聚合，反哺流程改进
└───────────────────────────────────────────────────────────────────────┘
```

**规则**：

| 规则 | 说明 |
|---|---|
| 排序按"影响金额 × 客户等级 × SLA" | 不按创建时间，避免"重要的事沉底" |
| 每条异常必须有建议动作 | 没有建议动作的异常不允许入队（否则就是甩锅给客户） |
| 可分派给 Agent 或人 | 分派给 Agent 即转为一次新的 Agent 任务（回到 P3） |
| 根因聚合是产品的一部分 | 帮助客户改流程（如要求供应商按模板开单），这是"越用越省"的来源 |
| 忽略必须留原因 | 且进入下期复检 |

### P6 连接器管理

**目的**：让 IT 管理员能自己看清"接了什么、能写什么、健康不健康、出问题怎么办"。这是 CIO 的页面，也是安全评审的实物证据。

```
┌───────────────────────────────────────────────────────────────────────┐
│ 连接器 4/6 就绪        [+ 新建连接]  [导入兼容性报告]                  │
├───────────────────────────────────────────────────────────────────────┤
│ ┌ ERP · 用友 U8 v16 ──────────────┐ ┌ MES · 自研（REST）──────────┐  │
│ │ 状态 ● 正常   最后同步 2 分钟前   │ │ 状态 ● 正常  同步 5 分钟前   │  │
│ │ 接入级别 L1（官方 API）           │ │ 级别 L2（只读副本）          │  │
│ │ 安全等级 A（支持用户态透传）       │ │ 安全等级 B（服务账号）        │  │
│ │ 写入白名单：                      │ │ 写入：只读                   │  │
```

**必须放的东西**（对应四道门槛的可验证性）：

1. **接入级别 + 安全等级**：让 CIO 一眼看出哪些连接器是 A 级（可承载 W2）、哪些是 B 级（只能 W1）。
2. **写入白名单（含永久禁止项）**：银行账号、会计科目等结构性禁令要显式展示为"永久禁止"，不是藏在文档里。
3. **字段映射 + 权威源**：对应架构文档的权威源矩阵，可搜索、可校验、显示冲突。
4. **健康度与限流余量**：运维需要提前知道"快被限流了"。
5. **拦截记录**：越权请求被拦了几次、拦了什么——这既是安全证据，也是销售材料。
6. **版本指纹变化告警**：厂商改版是最大外部风险（报告 §5.2 厂商配合度）。

**不做**：不做"连接器市场/应用商店"（MVP 阶段只做 6 个自营连接器，商店会把我们变成集成平台，与定位冲突）。

**目的**：用客户的语言证明价值，并让账单可预测。**这个页面同时是续费页和计费依据页。**

### P8 IM 卡片（跨端，不是独立页面但必须设计）

**目的**：让 80% 的日常动作发生在客户已经在的地方。

```
┌─ 智能执行助手 ──────────────────────┐
│ 🔔 A 供应商 10 月对账待复核          │
│ 差异 ¥32,400（报废未扣 12 件）       │
│ 将核减应付，影响付款 ¥1,286,300      │
│                                      │
│ [查看证据]  [批准]  [驳回]           │
└──────────────────────────────────────┘
```

**规则**：
- 一条消息只讲一件事，必须带金额与后果。
- 卡片上最多 2 个按钮：一个"看"、一个"做"。批准类动作在 IM 里点完仍需在 IM 内二次确认（金额 > 1 万时跳转工作台）。
- 不做"在 IM 里聊业务"的多轮对话（IM 只做通知与一键动作，追问回落到工作台/对话页）。

## 4. 走一遍：一个差异从发现到关闭（验证界面原则）

| 步骤 | 所在页面 | 用户动作 | 点击次数 |
|---|---|---|---|
| 1 | IM 卡片 | 早上收到"A 供应商对账待复核"通知 | 0 |

## 5. 视觉与工程约束（不做风格定义，只定硬约束）

| 约束 | 要求 | 理由 |
|---|---|---|
| 首屏信息密度 | 桌面 1440×900 下单屏可见 ≥ 5 个待办卡片 | 客户是"处理事情"不是"浏览" |
| 数字规范 | 金额千分位 + 单位；差异必须带正负号与颜色；日期统一 `YYYY-MM-DD` | 财务口径容不得歧义 |
| 表格 | 支持固定首列、行内展开、列可配置；不做横向滚动超过 2 屏 | 对账明细列多 |
| 加载 | 首屏 < 1.5s；Agent 任务详情允许骨架屏但必须显示"正在读取哪个系统" | 跨系统读写有延迟，要让等待可解释 |
| 无障碍 | 颜色不作为唯一差异标识（红绿同时用 +/- 符号） | 财务人群色弱比例不低 |
| 中文本地化 | 全中文，术语与客户 ERP 用词一致（如客户叫"委外"就不叫"外协"） | 术语不一致会直接被一线拒绝 |

## 6. 界面上明确不做的事

| 不做 | 原因 |
|---|---|
| 模块树导航（采购/销售/库存/生产…） | 客户已有 ERP，我们复制一套菜单只会增加切换成本 |
| 首页仪表盘墙 | 与原则 5 冲突；指标超 6 个就失去焦点 |
| Agent 市场 / 应用商店 | 会让我们变成集成平台，与"只做跨系统执行"的定位冲突（MVP） |
| 自由拖拽的看板 | 制造业客户不需要，且会变成"配置地狱" |
| 在界面里写 SQL / 搭流程 | 那是给实施顾问用的，不是给业务用的；MVP 阶段拒绝 |
| 移动 App | IM 卡片已覆盖移动场景 |
