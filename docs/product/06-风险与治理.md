# 风险与治理

> 版本：v0.1（待评审）
> 本文件不是免责声明。每条风险都要给出：什么信号说明它正在发生、谁负责、出了事怎么处置。
> 风险等级：P0 可能致命 / P1 严重 / P2 可控。

## 1. 风险总表

| 编号 | 风险 | 等级 | 触发信号（可观测） | 首要缓解 |
|---|---|---|---|---|
| R1 | Agent 执行事故（写错、写重、写一半） | P0 | 熔断触发次数上升、复核驳回率 > 20% | 写入分级 + 影子运行 + Saga 补偿 |
| R2 | 安全入侵（MCP 层 RCE、凭据泄露、越权） | P0 | 异常工具调用、出站流量异常、越权拦截告警 | 禁 STDIO、沙箱、用户态令牌、字段白名单 |
| R3 | 合规与责任边界（凭证、数据出境、AI 备案） | P0 | 客户审计提出问题、监管问询 | 不持总账、草稿制、数据不出域、备案先行 |
| R4 | 厂商反制（限流、封 API、改版本、合同禁止） | P1 | 接口失败率突增、版本指纹变化、厂商商务施压 | 分层接入 + 双路径 + 客户侧代理 + 合同前置 |
| R5 | 实施失败（数据脏、一线不用、范围蔓延） | P1 | 上线延期、日活低、定制人天超 15 | 诊断前置 + 单点闭环 + 定制配额 |
| R6 | 商业模型失效（归因争议、客单价低、周期长） | P1 | 结果费争议率 > 10%、CAC 回收 > 18 个月 | 默认 R1 口径 + 封顶 + 诊断收费 |
| R7 | 竞争挤压（原厂 GA 同类能力） | P1 | 竞品发布跨系统写入 + 补偿事务 | 连接器密度 + 失败样本库 + 行业纵深 |
| R8 | 组织能力（缺复合人才、顾问依赖） | P2 | 实施人天居高不下、交付质量波动 | 模板化 + 认证体系 + 定制配额 |

## 2. R2 安全：MCP 与连接器是最大攻击面

### 2.1 事实基线

报告 §0-9 与 §5.2 记录了三件事，必须当成设计前提而不是"新闻"：

1. **2026 年 4 月，OX Security 披露 MCP SDK 的系统性 RCE 设计缺陷**，CSA 研究笔记称影响约 20 万个实例。
2. **MCP 的 STDIO 传输可执行任意命令**——这是 RCE 的主要路径。
3. **confused deputy（权限冒用）**：Agent 代表低权限用户调用高权限连接器，形成越权。

对一个要向客户生产 ERP 写数据的系统，这三条意味着：**默认不安全，安全必须由架构保证，不能靠提示词或"我们很小心"。**

### 2.2 十条控制措施（按攻击面排列）

| # | 攻击面 | 控制 |
|---|---|---|
| 1 | 传输协议 | **禁用 MCP STDIO**，只允许 HTTP + OAuth2；网关拒绝任何本地进程启动类工具 |
| 2 | 工具注册 | 工具清单签名 + 版本锁定；未签名的工具不进候选集；工具定义变更需人工审批 |
| 3 | 参数注入 | 每个工具的参数做 schema 校验 + 白名单枚举；拒绝自由文本拼接进查询/命令 |
| 4 | 权限冒用 | Agent 一律用户态令牌透传；禁止服务账号跨用户复用；令牌生命周期 ≤ 单次任务 |
| 5 | 字段越权 | 字段级 scope；资金字段（单价/税率/银行账号/付款额）默认只读，需单独授权 |
| 6 | 结构性禁令 | 硬编码：不可创建/修改供应商银行账号、不可新增会计科目、不可改已过账凭证、不可删除单据 |
| 7 | 运行隔离 | 连接器跑在沙箱容器：出网白名单、只读根文件系统、CPU/内存/时长限额 |
| 8 | 凭据管理 | 凭据存客户侧 KMS/Vault，不出客户网络；我们侧只存引用不存明文；支持随时吊销 |
| 9 | 数据外泄 | 出站 DLP：拦截业务明细外发；控制面只收元数据与脱敏指标 |
| 10 | 供应链 | 依赖 SCA + 镜像扫描 + SBOM；第三方组件升级需过兼容性与安全门禁 |

### 2.3 验证方式（不能自我宣称安全）

- **上线前红队**：每季度一次，攻击目标固定四条——越权写入、凭据窃取、工具投毒、数据外带。
- **故障注入演练**：每月一次，人为制造"写一半失败""补偿也失败""并发写冲突"，验证回滚与告警。
- **客户侧渗透**：允许客户安全团队做渗透测试，结果作为销售材料（这是最好的信任证明）。
- **拦截记录可视化**：连接器管理页展示"拦截了多少次越权请求"（见界面文档 P6），把安全变成可见能力。

## 3. R1 Agent 执行风险：失败模式与处置

### 3.1 失败模式分类（每一类都必须有对应机制）

| 失败模式 | 具体表现 | 机制 | 检测时点 |
|---|---|---|---|
| 幻觉写入 | Agent 编造了不存在的供应商/物料/金额 | 写入前强校验主数据存在性；金额必须来自来源单据字段，不允许模型生成数字 | 预演阶段 |
| 重复写入 | 同一张单被处理两次 | 幂等键（场景 + 业务键 + 期间）+ 唯一约束 | 写入前 |
| 部分成功 | 跨系统 Saga 中途失败 | 逆序补偿；不可补偿则升级人工 | 执行中 |
| 并发冲突 | 两人/两 Agent 同时改同一单据 | 业务键分布式锁 + 版本号校验（乐观锁） | 写入时 |
| 静默错误 | 写成功了但值是错的（如单位换算） | 写入后校验（草稿金额 = 结论金额）+ 量级合理性检查 | 写入后 |
| 模型漂移 | 换了模型或提示词后准确率下降 | 金标准回归集；变更必须过评测才能发布 | 发布前 |
| 过度自信 | 置信度虚高，低质量结论流到审批 | 置信度校准（用历史准确率校准）；低置信强制人工 | 全流程 |

### 3.2 三道闸（缺一不可）

1. **预演（Preview）**：任何写动作先出 diff，不落库。预演失败 = 零写入。
2. **熔断**：单 Agent 1 小时失败率 > 20% 自动降级 W0；同租户同日 3 次熔断进入只读。
3. **人工复核**：W1 必须有人签；W2 超阈值必须双人；W3 一律禁止（MVP）。

### 3.3 事故分级与处置（Playbook）

| 级别 | 定义 | 响应时限 | 处置 |
|---|---|---|---|
| **P0** | 数据被错误写入生产且影响资金/凭证/库存，或发生越权 | 15 分钟响应，2 小时止血 | 立即冻结租户写入 → 定位工单 → 执行补偿或红冲 → 通知客户财务负责人 → 24 小时内出事故报告 → 7 天内出根因与改进 |
| **P1** | 批量任务失败、单场景停摆、审计记录缺失 | 1 小时响应，8 小时恢复 | 熔断该 Agent、回滚未完成批次、人工兜底跑一期 |
| **P2** | 单笔结论错误、界面异常、性能下降 | 1 个工作日 | 常规修复；错误结论进入评测集 |

**"数据被污染但无法自动回滚"是唯一需要动用公司级响应的场景**：必须由 CTO 与客户 CFO/CIO 直接沟通，并提供完整工单台账作为对账依据。这条路径每半年演练一次。

## 4. R3 合规与责任

### 4.1 责任边界（最重要的合规资产）

必须让客户、审计、监管都清楚三件事：

1. **我们不持有法定账簿**，不是会计主体，不承担会计核算与申报责任（架构 §4.3）。
2. **我们只写草稿**，所有生效动作由客户的人在其系统内确认（W1 为主）。
3. **我们是执行过程的权威源**，因此对"有没有做过、做对没有、能不能回滚"承担全部责任。

这三句话要同时出现在：产品文档、合同附件、界面（连接器管理页与工单详情页的说明）、安全白皮书。**口径不一致是合规风险的主要来源。**

### 4.2 合规清单

| 领域 | 要求 | 我们的动作 | 状态 |
|---|---|---|---|
| 生成式 AI 服务 | 《生成式人工智能服务管理暂行办法》：面向境内公众提供服务需备案/安全评估 | 面向企业客户（非公众）的私有化部署路径优先；如提供公有 SaaS，须完成算法备案与大模型备案 | Phase 2 前完成评估 |
| 数据安全 | 《数据安全法》：数据分类分级、出境评估 | 数据分级（见 4.3）；默认数据不出域；控制面只走元数据 | 设计内建 |
| 个人信息 | 《个人信息保护法》：供应商联系人、员工信息 | 最小化采集；联系人信息仅存必要字段；提供删除能力 | 设计内建 |
| 会计档案 | 《会计档案管理办法》：电子会计档案的归档与保管期限 | 客户凭证仍在其系统归档；我们的工单台账保留期 ≥ 客户会计档案期限（默认 10 年，可配） | 合同约定 |
| 网络安全等级保护 | 等保 2.0（私有化客户通常要求三级） | 私有化部署包按三级要求设计（审计、边界防护、入侵防范、数据完整性） | Phase 1 起支持 |
| 审计独立性 | 我们既执行又提供审计证据，存在角色冲突 | 审计台账只呈现事实（时间、动作、前后像、审批人），不呈现"我们的评价"；支持第三方审计直接调阅原始记录 | 产品约束 |

### 4.3 数据分级

| 级别 | 内容 | 存放 | 出域 |
|---|---|---|---|
| L4 核心 | 银行账号、成本结构、报价、客户名单 | 客户侧 | 禁止 |
| L3 敏感 | 单据明细、供应商价格、BOM | 客户侧 | 禁止 |
| L2 内部 | 工单元数据（时间、状态、动作类型）、指标 | 客户侧（默认）/ 控制面（可配） | 需客户书面同意 |
| L1 公开 | 版本号、许可、健康心跳 | 控制面 | 允许 |

**规则**：L3 及以上数据**在任何情况下不得进入我们托管的控制面**。这条由网关强制，不靠承诺。

### 4.4 AI 输出的责任声明

界面与合同中必须明示：Agent 输出为**建议**，W1/W2 动作需人工确认；客户不得将 Agent 输出直接作为对外承诺（如对客户的交期承诺、对供应商的付款承诺）而跳过确认环节。这一点在异常处置与报价场景尤其重要。

## 5. R4 厂商反制

### 5.1 厂商可能做什么

| 手段 | 概率 | 影响 |
|---|---|---|
| API 限流收紧 | 高 | 批量任务变慢，月末跑不完 |
| 字段/接口下线或变更 | 中高 | 连接器失效，需要紧急适配 |
| 商务施压（要求客户二选一） | 中 | 客户被迫放弃我们 |
| 合同条款禁止第三方写入 | 中 | 直接封死 L1 路径 |
| 推出同类能力并打包赠送 | 中 | 价格战，价值被稀释 |

### 5.2 缓解（技术 + 契约 + 商业三层）

**技术层**
1. **双路径接入**：同一系统尽量保留两条路径（API + 只读副本 + 语义化 RPA 兜底），接口断了降级不中断。
2. **兼容性测试矩阵**：每个 ERP 版本一套已验证映射；版本指纹变化自动告警并触发回归。
3. **限流感知调度**：把批量任务排在客户业务低峰；带配额预算与退避重试；月末前预留余量。
4. **只读副本兜底**：读永远有备份路径，写才依赖 API——保证"至少能看"。

**契约层**
5. **客户侧代理**：连接器部署在客户内网，调用方是客户自己的系统身份。厂商看到的是客户在调用，降低封禁动机。
6. **合同前置**：要求客户在其 ERP 合同中确认"允许第三方集成"，把风险在签约前暴露；合同中约定厂商变更导致停摆时的责任与补偿。
7. **数据可迁移**：工单台账与映射配置可完整导出，客户不被锁定（也是我们敢承诺结果计费的底气）。

**商业层**
8. **优先服务开放生态客户**：Odoo/ERPNext/有开放平台的国产 ERP 优先（报告 §5.2 缓解思路）。
9. **与原厂做互补而非替代**：我们不做单系统内的事，甚至可以成为原厂的"跨系统补丁"伙伴，把对抗关系转为渠道关系。

### 5.3 监测指标

每月跟踪：各连接器的接口失败率、限流命中率、版本指纹变化次数、厂商商务接触记录。任一连接器连续两周失败率 > 2%，升级为 P1 风险项。

## 6. R5 实施失败（对照报告的失败原因逐条建防线）

报告 §4.3 列了六类失败原因。我们逐条建防线，而不是笼统说"我们实施很轻"。

| 报告中的失败原因 | 我们的防线 | 可验证指标 |
|---|---|---|
| 目标与业务战略脱节（75% 对齐度不强） | 只卖绑定 KPI 的场景（差异率/月结天数/直通率），不卖"AI 能力" | 每个合同的 ROI 口径必须写入基线协议 |
| 预算与工期失控（超支 189%，离散制造 215%） | 固定价 + 单点闭环 4–6 周 + 不做大爆炸上线 | 上线周期 ≤ 6 周；超期免费延期 |
| 数据质量（AI 项目在数据准备阶段耗尽预算） | 诊断前置，不达标不签；数据修复做成产品 | 诊断通过率（预计 50–60%） |
| 集成成本（超支首因） | 连接器产品化 + 兼容性矩阵 + 模板复用 | 第二客户起实施人天 ≤ 25 |
| 组织与变更管理（一线不用，Excel 回潮） | 寄生 IM，不改工作习惯；界面原则 1 | 周活跃率 ≥ 80%（在受影响岗位） |
| AI 可信度（幻觉、越权、不可审计） | 工单 + 影子运行 + 双人复核 + 审计导出 | 驳回率 ≤ 15%；审计覆盖率 100% |

**范围蔓延是最大杀手**。制度性防线：单客户定制 ≤ 15 人天，超出需产品委员会批准；每个新需求先问"第二个客户会不会也要"。

## 7. R6/R7/R8 商业与组织风险

### 7.1 R6 商业模式

| 风险 | 缓解 |
|---|---|
| 归因争议（客户不认结果费） | 默认 R1 有效对账行口径（可逐行抽查、逐行取消计费资格）；基线协议作为合同附件；争议时按客户口径结算并重谈基线 |
| 客单价撑不住私有化成本 | 私有化收一次性部署费 + 订阅 ×1.5；只对 ≥ 5 亿营收客户提供全私有化 |
| 销售周期长导致现金流紧张 | 诊断收费；优先已有 ERP 服务商关系的客户；控制售前投入 |
| 结果费封顶导致收入天花板 | 平台订阅必须覆盖成本；结果费定位为"价值证明"而非主要收入（目标 ≤ 40%） |

### 7.2 R7 竞争

| 风险 | 缓解 |
|---|---|
| 原厂 GA 跨系统写入 | 护城河只能靠连接器密度、失败样本库、审计切换成本（定位文档 §6.3）；同时准备"被集成"方案（成为原厂的跨系统插件） |
| 集成商低价竞争 | 明确差异：产品化执行层 vs 人天项目；回滚责任在我们 |
| 开源方案（ERPNext + 社区 Agent） | 我们卖的不是模型能力，是审计与回滚工程 + 行业模板；开源社区做不了跨厂商补偿 |

### 7.3 R8 组织能力

- **复合人才稀缺**（既懂制造又懂 Agent 工程）：以"制造业务专家 + Agent 工程师"结对，不要求单人多能。
- **顾问依赖**（报告指出实施重是行业病）：实施认证体系 + 模板化，把顾问从"设计者"降为"配置者"。
- **交付质量波动**：每个客户的"首个闭环"由一个固定小队交付，不外包关键环节。

## 8. 治理机制（谁在什么时候看什么）

| 机制 | 频率 | 参与人 | 输出 |
|---|---|---|---|
| 风险评审会 | 每月 | 产品、技术、安全、交付负责人 | 更新风险总表与责任人 |
| 红队演练 | 每季度 | 外部安全团队 + 内部 | 漏洞清单与修复验收 |
| 故障注入演练 | 每月 | 技术 | 回滚成功率报告 |
| 事故复盘 | 每起 P0/P1 | 全员 | 根因、改进项、评测集新增样本 |
| 竞品监控 | 每月 | 产品 | 原厂能力更新、窗口关闭信号判断（定位文档 §6.3） |
| 合规审查 | 每半年 | 法务 + 安全 | 备案、合同条款、数据处理活动记录更新 |

### 保险与兜底

- **网络安全责任险**：覆盖数据泄露与入侵导致的第三方损失。
- **职业责任险（E&O）**：覆盖因执行错误导致的客户财务损失。
- 两者都要求在合同中明确赔付上限与免责情形（尤其是"客户跳过人工复核直接对外承诺"的情形）。

## 9. 三条"不可协商"的红线

写在最后，因为它们是所有风险缓解的前提：

1. **永不持有第二本总账，永不写已过账凭证。** 一旦破例，产品性质、责任边界、合规成本全部改变。
2. **永不允许 Agent 触碰供应商银行账号与资金支付。** 这是唯一无法用技术补偿的错误类型。
