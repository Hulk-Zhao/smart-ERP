# 产品架构

> 版本：v0.1（待评审）
> 本文回答三个问题：分层怎么切、每层的职责边界在哪、ERP 业务内核里哪些自建哪些复用存量。
> 架构原则先于技术选型：**权威源唯一、写入分级、补偿优先、审计内建。**

---

## 1. 分层总览

```
┌──────────────────────────────────────────────────────────────────────────┐
│ L0 交互层                                                                 │
│  工作台 · 对话入口 · Agent 任务详情 · 复核审批 · 异常队列 · 连接器管理 · 报表 │
│  （形态：Web 工作台 + IM 卡片 + 原系统内嵌浮层）                             │
├──────────────────────────────────────────────────────────────────────────┤
│ L1 Agent 层                                                               │
│  预置 Agent 清单（8 个） │ 场景编排器（Supervisor） │ 工具网关（MCP/HTTP）    │
│  Agent 工单运行时（状态机 · 幂等 · 补偿） │ 评测与影子运行 │ 模型路由        │
├──────────────────────────────────────────────────────────────────────────┤
│ L2 连接与聚合层                                                            │
│  连接器（ERP/MES/WMS/财务/供应商协同/IM/文件）                              │
│  统一数据模型（Canonical Model） │ 主数据映射与权威源矩阵                    │
│  身份与权限（用户态透传 · 动作白名单 · 字段 scope）                          │
│  审计与回滚（前像后像 · 补偿动作库 · 审计台账）                              │
├──────────────────────────────────────────────────────────────────────────┤
│ L3 ERP 业务内核（薄内核，只持有跨系统状态）                                  │
│  单据中心 │ 对账账 │ 差异与处置 │ 供应商协同 │ 执行账 │ 指标基线仓          │
│  （法定总账/税务/资金/库存台账/生产执行 → 复用存量，不自建）                  │
├──────────────────────────────────────────────────────────────────────────┤
│ L4 模型与数据层                                                            │
│  模型路由（本地模型 / 商用 API） │ OCR 与文档解析 │ 向量库 │ 业务知识图谱     │
│  特征与基线指标仓 │ 数据体检 │ 样本与评测集 │ 全链路 Trace                   │
└──────────────────────────────────────────────────────────────────────────┘
```

**一句话解释每层的存在理由：**

| 层 | 存在理由 | 如果去掉会怎样 |
|---|---|---|
| L0 交互 | 让业务人员在不改变工作习惯的前提下完成任务 | Agent 再强也没人用（报告 §4.3：一线不用、Excel 回潮是失败首因之一） |
| L1 Agent | 把"业务判断"与"系统操作"分离，判断可换模型、操作可复用 | 每个场景都要重写一遍集成代码 |
| L2 连接与聚合 | 把 N 个系统的差异收敛成一套语义，并在这里做权限与审计 | 异构复杂度渗透到每个 Agent，无法维护 |
| L3 业务内核 | 持有"跨系统"特有的状态（对账账、执行账、差异），这些在原系统里不存在 | 每次都要临时拼装，无法回答"这笔事务到底办完没有" |
| L4 模型与数据 | 模型可替换、证据可追溯、效果可度量 | 无法应对模型迭代与合规审查 |

## 2. L2 连接与聚合层（产品的真正壁垒）

### 2.1 连接器

**统一接口**：每个连接器实现同一组能力，Agent 不感知厂商差异。

| 能力 | 说明 |
|---|---|
| `describe()` | 自描述：系统类型/版本、可用对象、字段、动作、限流、鉴权方式、安全等级（A/B） |
| `read(entity, query)` | 只读查询，支持增量水位（modified_since）与分页 |
| `preview(action, payload)` | **预演**：返回将要发生的变更（diff），不落库。所有写动作必须先 preview |
| `write(action, payload, idempotency_key)` | 受控写入，必须携带幂等键与 Agent 工单号 |
| `compensate(compensation)` | 执行补偿动作（撤销草稿/红冲/反向单据/通知撤回） |
| `health()` | 健康度：最后同步、失败率、限流余量、版本指纹 |

**接入分级**（对应定位文档 §7.3）：L1 官方 API → L2 只读副本/中间表 → L3 语义化 RPA 兜底。连接器元数据里显式标注级别与允许的最高写入等级，**Agent 不能越过连接器声明的上限**。

**MVP 连接器清单（6 个）**：用友 U8/YonSuite（或客户现有国产 ERP，二选一）、SAP（OData/BAPI，按客户定）、Odoo 或 ERPNext（标准化试点用）、自研 MES 通用 REST 适配器、企微/钉钉（消息与审批）、文件通道（邮箱/共享目录/IM 文件，用于供应商对账单）。

### 2.2 统一数据模型（Canonical Model）

不做"全字段映射"，只做**跨系统事务所需的最小语义集**。五个主对象：

| 主对象 | 关键字段 | 说明 |
|---|---|---|
| **Party**（主体） | 供应商/客户/内部组织/员工，含外部系统 ID 映射 | 一个供应商在 ERP、MES、财务里可能三个编码 |
| **Item**（物料） | 物料/半成品/委外件，含单位换算、替代料关系 | 单位换算是制造对账第一大坑 |
| **Document**（单据） | 类型（订单/收货/报工/发票/对账单）、行项目、状态机 | 所有单据归一到同一状态语义：草稿/已提交/已审核/已关闭/已冲销 |
| **Transaction**（事务） | 数量变动、金额变动、库存移动，带来源单据引用 | 对账的本质是事务对齐 |
| **Money**（金额） | 含税/不含税、税率、币种、汇率、费用类型 | 委外加工费、运费、杂费必须分列 |

**设计约束**：
- 每个字段必须标注**权威源系统**（见 2.4），非权威源的数据只作参考，不参与判定。
- 模型只增不改：字段变更走版本化，老 Agent 不受影响。
- 不追求覆盖 ERP 全字段。**无法归一的字段不进模型**，由 Agent 在读取时按需直查原系统。

### 2.3 身份与权限

四道闸，逐层收窄：

1. **身份**：Agent 以发起人身份运行（OAuth2 on-behalf-of / 系统原生 impersonation）。没有"系统机器人"这种超权账号。定时任务以"业务Owner"身份运行，且该 Owner 必须是一个真实岗位而非共享账号。
2. **动作白名单**：连接器注册时声明可执行动作集合（如 `create_purchase_order_draft`），未声明的动作在网关层直接拒绝，不进入 Agent 的候选工具列表。
3. **字段 scope**：写动作必须声明可写字段集合。资金类字段（单价、税率、银行账号、付款金额）默认只读，需单独授权。
4. **动作级审批**：按 `金额 × 系统 × 动作风险` 三维阈值触发。例如"付款申请草稿 > 50 万"或"任何写 SAP 生产机"必须双人复核。

**结构性禁令（硬编码，不可配置）**：Agent 永远不能创建/修改供应商银行账号、不能新增会计科目、不能修改已过账凭证、不能删除任何单据。这四条是"资金外流"与"账务失真"的最后防线。

### 2.4 权威源矩阵（Source of Truth）

这是整个架构最重要的一张表。**原则：谁的账谁负责，我们只持有跨系统一致性所需的最小状态。**

| 数据域 | 权威源 | 我们的角色 | 冲突处理 |
|---|---|---|---|
| 法定总账、税务、报表 | 客户原 ERP | 只读引用 | 永不覆盖 |
| 资金支付、银行流水 | 客户财务/银企直连 | 只读引用 | 永不写入 |
| 库存台账（数量与金额） | 客户 ERP/WMS | 只读引用 | 永不覆盖 |
| 生产执行（工单/报工/报废） | 客户 MES | 只读引用 | 永不覆盖 |
| 采购/委外订单 | 客户 ERP | 读 + 写草稿 | 以 ERP 为准 |
| 供应商主数据 | 客户 ERP | 读 + 建议（不可直写） | 以 ERP 为准 |
| 物料主数据 | 客户 ERP | 读 + 建议 | 以 ERP 为准 |
| **对账状态与差异** | **我们** | 权威源 | 以我们的对账账为准 |
| **Agent 工单与审计台账** | **我们** | 权威源 | 不可篡改（追加写） |
| **执行账（跨系统事务状态）** | **我们** | 权威源 | 以我们为准 |
| **指标基线与结算记录** | **我们** | 权威源 | 合同附件效力 |

这张表决定了产品的法律与责任边界：**我们从不成为法定账的权威源，因此不承担会计责任；但我们是执行过程的权威源，因此必须承担执行责任。** 这句话要同时出现在架构文档、销售材料和合同里。

### 2.5 审计与回滚

**Agent 工单（Agent Ticket）** 是产品的核心对象，不是日志。

```
AgentTicket
├─ 基本信息：工单号 / 场景 / 发起人 / 触发方式（定时·事件·人工）/ 关联业务单据
├─ 执行计划：步骤序列（S1..Sn），每步声明 目标系统 / 动作 / 预期影响 / 补偿动作
├─ 执行记录：每步的 输入快照 / 返回结果 / 耗时 / 幂等键
├─ 变更影像：每个被写对象的 前像(before) / 后像(after) / 字段级 diff
├─ 审批链：谁在什么时间基于什么证据批准（含双人复核的第二人独立意见）
├─ 状态机：见下
└─ 影响面：涉及金额 / 单据数 / 系统数 / 是否触及资金或库存
```

**状态机**：

```
计划中 ──预演通过──> 待审批 ──批准──> 执行中 ──全部成功──> 已完成
  │                    │                 │
  │                    └──驳回──> 已驳回   ├──部分失败──> 补偿中 ──> 已回滚
  │                                       │                └──补偿失败──> 需人工处置
  └──预演失败──> 已终止（不产生任何写入）    └──外部已生效──> 已锁定（仅告警 + 人工升级）
```

**补偿三级**（对应定位文档 §7.2）：

| 级别 | 适用 | 机制 | 时限 |
|---|---|---|---|
| 自动回滚 | 未审核草稿、可撤销的分配、未发送的通知 | 调用 `compensate()`，逆序执行 | 15 分钟内 |
| 人工确认回滚 | 已审核单据、已占用库存 | 生成红冲/反向单据草稿，需人批准 | 4 小时内提交 |
| 仅告警升级 | 已付款、已发货、已通知供应商、已过账 | 不改数据，生成处置任务并通知责任人 | 立即 |

**审计不可篡改**：工单与影像是追加写（append-only），落对象存储并做哈希链；任何修改以新版本追加，保留历史。导出格式需同时满足内审（按人/按系统/按金额检索）与外审（按期间/按凭证号溯源）。

## 3. L1 Agent 层

### 3.1 组成

| 组件 | 职责 | 关键设计 |
|---|---|---|
| **预置 Agent 清单** | 8 个业务 Agent，见《03-AI能力清单》 | 每个 Agent 必须声明：跨系统数、写入等级、失败策略、复核点、计费锚点 |
| **场景编排器（Supervisor）** | 跨 Agent 的任务编排：如"对账发现差异 → 触发补单 → 触发重新对账" | 图/状态机模型（LangGraph 路线），带检查点与可恢复；报告 §3.3 选型建议即此 |
| **工具网关** | Agent 与连接器之间唯一通道 | MCP over HTTP + OAuth2（禁用 STDIO，见风险文档）；工具清单签名；参数 schema 校验；出站 DLP |
| **Agent 工单运行时** | 执行状态机、幂等、补偿、并发锁 | 幂等键 = 场景 + 业务键 + 期间；同一业务键并发时加锁并串行化 |
| **评测与影子运行** | 新 Agent / 新模型上线前的安全网 | 影子模式：连续 N 个周期只产出建议不写入，与人工结果比对，准确率达标才开写 |
| **模型路由** | 按任务选模型 | 抽取/分类走小模型或本地模型；推理/生成走大模型；敏感客户全本地部署 |

### 3.2 为什么编排用状态机而不是"角色对话"

对账与异常处置有三个特征：**长事务**（跨天、跨系统）、**需要回滚**、**需要人工介入**。角色化对话框架（CrewAI 路线）适合快速搭 Demo，但无法表达"第 3 步失败了要回到第 1 步"这种语义。报告 §3.3 的选型结论与之一致：LangGraph 的状态机 + 检查点模型最贴合 ERP 事务流（§3.3 选型建议）。

### 3.3 并发与冲突

| 场景 | 机制 |
|---|---|
| 两个 Agent 同时改同一单据 | 业务键级分布式锁 + 幂等键；后到者进入"待确认"而非覆盖 |
| 人与 Agent 同时改 | 人优先；Agent 检测到版本号变化即中止并重新取数 |
| 同一供应商被两个期间的对账同时处理 | 按"供应商 × 期间"分区，跨期间差异归入后一期 |
| Supervisor 与子 Agent 冲突 | Supervisor 持有全局计划，子 Agent 只能在其步骤内写入 |

## 4. L3 ERP 业务内核：哪些自建、哪些复用存量

这是"聚合型 ERP"最容易做错的地方。做多了变成又一个 ERP，做少了变成又一个集成商。我们的判据只有一条：

> **只自建"跨系统才有意义"的对象；凡是单一系统能作为权威源的，一律复用它。**

### 4.1 逐域决策表

| 业务域 | 自建 / 复用 | 具体做什么 | 判断依据 |
|---|---|---|---|
| **财务** | **复用为主，自建一小块** | 复用：法定总账、税务、资金支付、固定资产、报表（均在客户 ERP）。自建：对账账、差异账、暂估与结算台账、凭证草稿生成 | 报告指出财务域已被 AI 原生重构过（Rillet），但明确不做库存与运营（§1.3）；我们不在财务域正面对抗，只做"跨系统的财务衔接" |
| **采购** | **混合** | 复用：采购订单、供应商主数据、价格条件。自建：询价比价记录、比价结论、跨系统到货一致性、供应商协同记录 | 比价需要跨"历史价 + 行情 + 替代料 + 交期"，原系统只存结果不存过程 |
| **销售** | **复用为主** | 复用：销售订单、价格、信用、发货。自建：订单承诺（ATP）的跨系统汇总、交付异常记录 | 销售域的原厂能力足够，我们的增量只在"承诺是否可信" |
| **库存** | **复用 + 只读聚合** | 复用：库存台账、批次、库位（ERP/WMS 为权威源）。自建：跨系统可用量视图（ATP）、齐套缺口、调拨建议 | 绝不自建库存台账——两套库存是制造业最危险的事故源 |
| **生产 / 委外** | **自建委外协同，复用生产执行** | 复用：工单、报工、报废、设备（MES 为权威源）。自建：委外发料/收货/加工费结算协同、异常单、改期与改派决议 | 委外是"跨企业"的，原系统普遍只有半截（发出去了，收没收回来、料有没有损耗、加工费怎么算，靠 Excel） |
| **成本** | **复用 + 自建成本模拟** | 复用：实际成本核算（ERP）。自建：报价成本模拟、委外加工费差异分析、异常成本归因 | 成本核算依赖账簿，必须复用；成本"模拟"是决策场景，原系统没有 |
| **报表** | **复用 + 自建跨系统指标** | 复用：财务报表、法定报表（原 BI）。自建：跨系统执行指标（对账差异率、直通率、闭环时长）、价值仪表盘、审计台账 | 报告指出客户 KPI 是 CFO 语言（§4.4），这些指标在原系统里天然算不出来 |

### 4.2 内核的四个核心对象

薄内核不等于没内核。我们自建的对象只有四类：

1. **单据中心**：跨系统单据的统一视图与状态（不是单据本身，单据仍存在原系统）。
2. **对账账（Reconciliation Ledger）**：每笔跨系统事务的"应收/应付/已收/已付/差异"五列对照，是对账 Agent 的产出与依据。
3. **执行账（Execution Ledger）**：每个跨系统事务的完整生命周期（谁发起、经过哪些系统、当前卡在哪、责任人是谁）。这是"到底办完没有"的唯一答案。
4. **指标基线仓**：上线前基线、当期实际、增量归因，支撑结果计费（对应定位文档 §7.4）。

### 4.3 一条硬边界

**我们永远不持有第二本总账。**
理由有三：①法定账簿的唯一性由会计法保证，两本账必然引发审计问题；②一旦持有总账，我们就要承担会计责任与合规责任，产品性质从"执行层"变成"账务系统"，销售周期与实施成本翻倍；③原厂的账已经能跑，重复建设没有客户价值。

这条边界会反复被销售和客户挑战（"你们能不能直接把账也管了"），必须写进产品原则并由产品负责人一票否决。

## 5. L4 模型与数据层

| 组件 | 用途 | 选型取向 |
|---|---|---|
| 模型路由 | 按任务分配模型：抽取/分类用小模型，推理/生成用大模型 | 双轨：商用 API（快、便宜）+ 本地部署（敏感客户、数据不出域，对应报告 §6-卖点6 的私有化诉求） |
| 文档解析 | 供应商对账单、送货单、发票、委外领料单 | OCR + 版面分析 + LLM 结构化抽取；保留原始影像与抽取置信度，低置信度进人工队列 |
| 业务知识图谱 | 物料-BOM-工艺-供应商-价格历史的关系 | 支撑比价、替代料推荐、差异归因；不追求全量，按场景建子图 |
| 特征与基线仓 | 结果计费与效果度量的底座 | 指标口径版本化；基线冻结后不可改（合同效力） |
| 数据体检 | 上线前的数据质量诊断（科目一致性、供应商重复、BOM 断链、单位换算错误） | 报告 §6-卖点3 的产品化；作为获客钩子与准入筛选器（见商业模式文档） |
| 样本与评测集 | Agent 效果回归 | 每个 Agent 一套金标准样本；模型或提示词变更必须过回归 |
| 全链路 Trace | 排障与审计 | 每次工具调用记录入参/出参/耗时/模型版本/提示词版本 |

## 6. 写入分级（贯穿全架构的约束）

**所有写入动作必须被打上一个等级，等级决定审批与回滚策略。** 这是权限门槛（报告 §5.2）的产品化落地。

| 等级 | 定义 | 典型动作 | 审批要求 | 回滚方式 | 允许的 Agent |
|---|---|---|---|---|---|
| **W0 只读建议** | 只产出建议，不写任何系统 | 排程建议、调拨建议、比价结论 | 无（人自行决定是否采纳） | 不需要 | 全部 |
| **W1 草稿写入** | 写入草稿/未审核单据 | 采购订单草稿、付款申请草稿、差异处置单 | 单人复核（业务岗） | 删除草稿（自动） | 全部 |
| **W2 低风险自动过账** | 直接写入已生效但不涉资金的单据 | 到货差异登记、库存分配、状态回写 | 阈值内免审，超阈值双人 | 红冲/反向单据 | 库存预警、异常处置（对账在 Phase 2 开放差异登记后进入 W2） |
| **W3 资金与合规敏感** | 触及资金、税务、法定凭证 | 付款执行、发票认证、凭证过账 | **必须双人复核 + 金额上限** | 仅告警 + 人工升级（不自动回滚） | MVP 阶段**不允许任何 Agent 进入 W3** |

**硬规则**：
- 任何 Agent 不得自我提升写入等级，等级由连接器声明与场景配置双向约束，取严。
- 新 Agent 上线首 4 周强制 W0（影子运行），达标后才可申请升级。
- W3 在 MVP 与 Phase 2 完全关闭；Phase 3 视客户审计结论再评估。

## 7. 部署形态

**私有化优先、控制面分离**（对应报告 §6-卖点6 的国资/制造诉求，但作为交付选项而非卖点）：

| 平面 | 部署位置 | 存什么 | 是否出域 |
|---|---|---|---|
| **数据面** | 客户内网/私有云 | 业务数据、单据影像、连接器凭据、Agent 运行时 | 否 |
| **控制面** | 我们托管（或客户私有化） | 租户配置、许可、计费元数据、脱敏指标、版本与补丁 | 仅元数据，不含业务明细 |
| **模型面** | 客户内网（本地模型）或受控 API | 推理请求 | 敏感客户全本地，不出域 |

**三种交付形态**：
1. **私有化全量**（大客户/国资）：三平面全部在客户侧，我们只提供镜像与远程支持。
2. **混合**（默认）：数据面在客户侧，控制面托管。
3. **SaaS**（Phase 3，小客户）：多租户，但审计台账仍可导出到客户侧。

## 8. 技术选型取向（不锁死版本）

| 领域 | 取向 | 理由 |
|---|---|---|
| Agent 编排 | 状态机 + 检查点（LangGraph 路线） | 长事务、可回滚、可人工介入（§3.3） |
| 接入协议 | MCP over HTTP + OAuth2，禁用 STDIO | STDIO 可执行任意命令，是 2026-04 RCE 的主要面（§0-9） |
| ERP 参考实现 | ERPNext / Odoo 的数据模型与流程参考；不自建全量 ERP | 报告 §3.4 明确二者覆盖中小制造标准流程，但无原生 Agent 层 |
| 排产内核 | Frepple（Phase 3），不自研 APS 求解器 | 报告称其为开源 APS 最成熟内核（§3.2） |
| 存储 | PostgreSQL（事务与工单）+ 对象存储（影像与审计归档）+ 向量库 | 工单需强事务；影像需不可变 |
| 前端 | Web 工作台 + IM 卡片渲染 + 原系统浮层 | 对应"少层级、任务流"的界面原则 |

## 9. 架构层面的三个取舍（评审重点）

1. **不自建库存台账、不自建总账**：牺牲"完整 ERP"的叙事，换取责任边界清晰与实施成本可控。代价是客户会问"那你们和集成商有什么区别"——答案是 L3 的执行账与对账账，这两样集成商不提供。
2. **写入分级 W3 在 MVP 关闭**：牺牲短期场景覆盖（如自动付款），换取安全评审通过率。代价是价值叙事必须落在"人力与周期"而非"资金效率"。
3. **统一模型只做最小语义集**：牺牲"接什么系统都能无缝映射"的理想，换取交付速度。代价是每接一个新系统仍需定制映射，这部分成本必须计入实施报价。
