## 1. 计费单元：行，不是批次

### 1.1 定义

**有效对账行（计费单元）= 引擎自动完成匹配、且不需要人工介入的供应商侧对账行，包含已自动归因的差异行。**

判定要点：

1. 该行来自供应商对账单；
2. 引擎已给出明确匹配结论；
3. 不需要人工复核；
4. 匹配方式为精确匹配、模糊匹配或聚合匹配之一。

### 1.2 明确计入

- 零差异、直接匹配的行；
- 已自动归因的差异行：单价不一致、数量不符、税率口径、报废未扣；
- 单行金额舍入容差行（已自动放行，不生成差异单）；
- 聚合匹配且合计已闭合的拆单行。

### 1.3 明确不计入

- 待人工复核、匹配歧义、仅给出候选的行；
- 供应商未匹配（缺单）、重复计费、不可解析的行；
- 合并开票行（一张供应商行覆盖我方多行，拆分口径不唯一，必须人工确认）；
- 整批「无法对账」的批次：引擎未执行任何匹配，不产生可计费行。

### 1.4 为什么不用「零差异行」计费

- 差异判断本身就是交付结果：把差异找出来、归好类、留下证据，客户已经因此省去人工；
- 零差异比例会随供应商开票质量波动，用它计费会让账单不可预测；
- 舍入容差行虽有小额差异，但已按规则自动放行，属于已处理行；
- 零差异比例不作为计费基数。

### 1.5 批次未放行，行照计

**合同兜底句：计费不以批次放行为前提。**

批次处于「待人工复核」，只表示该批仍有未决项，不影响其中已自动匹配的行计费。**本期结算：**争议行当期不计费、单独挂起，不冻结整批账单；争议确认后，按确认结果在次月账单补计或冲抵。补计以**双方书面确认**为前提，且**不追溯超过一个账期**，超出部分不再补计。

### 1.6 舍入容差

- 单行金额舍入差在容差内的，已自动放行、计入有效对账行。
- 整批舍入差累计超限时，批次转人工复核；**按合同口径，转人工的那部分不计费**。
- **本期结算：**本期账单按上界出账，该部分在双方确认后于次月账单以红字调整或贷记单冲抵。本节不承诺「系统自动剔除」，该项见 §4.2。

## 2. 计量公式与算例

### 2.1 公式

```
应处理行数 = 供应商对账单行数
有效对账行 = 自动匹配且无需人工的供应商侧行
计费行数 = 有效对账行
           − 已确认错放行
           − 客户原因不计费行
           − 整批舍入超限转人工行
本期金额 = 计费行数 × 合同单行单价（保留 4 位小数）
累计金额 = 上期累计 + 本期金额
```

三项减项在本期账单中暂不预扣，因此**账单上的计费行数为上界**；**本期结算：**双方确认后于次月账单以红字调整或贷记单冲抵。三项减项的计算方式以合同/协议文本为准。计费基数始终是有效对账行，不因单价取自合同价目还是备用配置而变化。

### 2.2 算例

> 假设合同单行单价为 P（以合同附件为准），以下仅为算例。容差与封顶以合同/配置为准。

某批次共 7 条供应商行：

| # | 情形 | 引擎结论 | 四类归属 | 是否计费 |
|---|---|---|---|---|
| 1 | 数量、单价、金额全一致 | 自动放行 | 计费 | 计入 |
| 2 | 单价差 0.50 元，已归因为单价不一致 | 自动放行 | 计费 | 计入 |
| 3 | 金额差 0.04 元，在舍入容差内 | 自动放行 | 计费 | 计入 |
| 4 | 金额差 5.00 元，无法归入已知类型 | 待人工 | 争议挂起 | 不计 |
| 5 | 存在两条候选、无法判定 | 匹配歧义 | 争议挂起 | 不计 |
| 6 | 供应商有、我方无 | 供应商未匹配 | 其他不计费 | 不计 |
| 7 | 与第 1 行整行重复 | 重复计费 | 其他不计费 | 不计 |

```
应处理行数 = 7
自动放行（即计费行）= 3（第 1、2、3 行）
争议挂起 = 2（第 4、5 行）
其他不计费 = 2（第 6、7 行）
校验：3 + 2 + 2 = 7

本期金额 = 3 × P = 3P（算例）
```

该批次因存在人工行，整体为「待人工复核」；但第 1、2、3 行仍然计费，这就是「批次未放行，行照计」。

### 2.3 反向减项示例

若第 2 行事后被双方确认「自动放行结论错误」，第 3 行被确认属客户原因：

```
计费行数 = 3 − 1 − 1 = 1
本期金额 = 1 × P = P（算例）
```

账单先按上界显示 3 行、3P（即**本期按上界出账**）；双方确认后，在次月账单以红字调整或贷记单冲抵。扣减的计算方式以合同/协议文本为准。

## 3. 争议与反向减项

### 3.1 只扣两类，按行扣

| 减项 | 定义 | 谁提出 | 谁认账 |
|---|---|---|---|
| 已确认错放行 | 引擎判为自动放行并已计费，复核确认该行结论错误 | 客户财务或我方对账运营 | 双方复核人签字 |
| 客户原因 | 客户侧原因导致该行无效，按合同不计费 | 我方客户成功/商务 | 客户书面确认 + 确认人 |

**本期结算：**两类减项均先按上界出账，双方确认后于次月账单以红字调整或贷记单冲抵；调整只涉及对应行，不冻结整批账单。

**系统性错误不逐行扣减**，走整批追溯：原批次保留不动，重跑生成新批次，以新批次重算。**本期结算：**涉及行先按上界出账，双方确认后，差额在次月账单一次性以红字调整或贷记单冲抵。是否构成「系统性」由双方在争议确认单上共同判定。

### 3.2 举证材料

- 批次号、行号、供应商、我方单号、供应商单号；
- 系统结论、差异类型、证据链（系统、单据号、字段）；
- 逐行导出文件及其内容摘要，可离线校验；
- 已确认错放行：双方签字的复核结论；
- 客户原因：原因说明、确认人、客户书面确认。

上述两类确认以双方签署的确认单为凭，按签署结果登记并在次月账单调整。

### 3.3 认账与调整

- 我方对账运营提出复核意见，客户财务确认，双方在月度对账单签字；
- 争议只影响争议行，不冻结整批账单；
- 调整在次月账单以红字或贷记单执行。

### 3.4 时限

争议提出、证据交换、答复与升级的时限，**以合同/协议为准**；本文不给具体天数。

### 3.5 赔付上限

- 合同口径：**赔付上限 = 年订阅额的 20%**；触发条件与计算方式以合同/法务文本为准。
- 该上限与「结果费封顶」不是一回事，不得混用或互相替代。
- 触发赔付时，我方在**年订阅额 20%** 的上限内按合同约定核定并支付。
- **本期结算：**赔付不计入计量账单，也不自动抵扣账单金额；按合同约定的流程单独核定、单独支付。

## 4. 交付范围（本期包含 / 本期不包含）

### 4.1 本期包含

- 按批次输出计量表：应处理行数，以及自动放行（即计费行）、争议挂起、其他不计费三类明细计数；
- 逐行明细与导出，附内容摘要，可离线复算；
- 计量只读：不写客户 ERP、不碰资金、不改业务状态；
- 写路径演示（**只在本公司自带的模拟外部系统上**）：演示中会完整走一次「审批通过 → 预演 → 建草稿 → 回查 → 删除草稿」。审批由演示身份 `dddddddd` 完成（操作单实测：这一段八步只需这一个身份）。**失败分支**用 `bbbbbbbb` 对 73.5 万单点「通过」，会返回 403 权限拒绝、审批记录不新增，切回 `dddddddd` 即恢复；全程零写入，不制造桩故障。连接器是真实代码、真实发出 HTTP 请求，失败会显式报错；但**对端是模拟系统，不是贵司的 U8，也不是任何真实 ERP**，可以用它自己的请求与回执记录当场核对。**贵司的系统在本期保持零写入。**
- 对账演示的输入数据由我方当场提供：引擎、落库、差异计算与审计是真实运行的；**主路径的行级数据由我方当场提供，贵司系统不回传，也不被读取**。本期不对接供应商系统；也没有文件/邮件自动解析。
- **现场上传（演示环境，可选）**：对账页选择供应商对账单 CSV → 点「开始对账」→ 生成真实批次。实测 `supplier_lines=3`、`our_lines=3`、`matched=3`（**3 行全匹配：其中 2 行零差异、1 行单价差异**）、`diff_lines=1`、`diff_amount=10.0000`；差异为单价差异，引用 `file:PO-2026-0001#3`。**我方 3 行是预先导入的演示数据，供应商 3 行是现场上传的文件**，不是同一个文件自己跟自己比。失败也能演：单位写错 → `422`，页面指出「第 3 行…单位不认识」，且批次不创建。**该能力仅在演示环境接通，生产接线未做。** 该步骤已在 live 实测通过；上传登记在 api 进程内存，**重启 api 后需重传**；样例为 2026-10 期。
- 批次与行快照只追加，改判只能重跑新批次，原批次不变；
- 单行单价只从合同价目读取，不使用任何默认价；未配置时不出账，也不会返回空价继续出账。
- 下一步处理建议：只读，不写客户系统、不执行任何动作。模型可用时给出模型建议；模型不可用时降级为规则建议，并在界面上标注「模型未参与」。任何情况下都只是建议，决策由人做。
- 审计可核验：审计影像带字段级前后差异；哈希链可逐条校验；锚点可按日期查询。

**写路径的真与模拟（一眼分清）：**

| 是真的 | 是模拟的 |
|---|---|
| 连接器真实发出 HTTP 请求：预演 → 建草稿 → 回查 → 删除草稿；请求失败会显式报错，不会「假成功」 | 对端系统：本公司自带的模拟系统（启动日志有横幅、每个响应带回执头、响应体标注 `simulated: true`），**不是 U8、不是任何真实 ERP** |
| 审批、状态机、写前校验、审计影像，与正式版本同一套逻辑 | 写入内容：模拟系统里的草稿，重启即清空；不产生真实凭证、付款或账务影响 |
| 请求与回执可以在模拟系统的记录里当场核对 | 演示数据：预置的演示数据，不是贵司数据 |
| 资金等级（W3）的拦截、金额与双人复核规则 | —— |

**本期写实现的边界：**只有「U8 制单（草稿）」这一类有写实现；WMS 没有写实现、文件通道只读。因此**不存在「多系统写入」**，也不对任何真实系统做写入。

**本期结算：**合同单价未配置时不出账、不估账，也不会以空价或默认价继续出账；配置完成后按合同单价出账，计量表标明本次单价的取值来源。

### 4.2 本期不包含

以下能力**不在本期 POC 与交付范围内**，正式约定见合同附件；不得在方案、POC 报告或验收结论中写成「已具备」：

- 跨系统写入后的**自动**回滚、补偿与撤销（补偿执行器已交付，但本期没有业务建单入口、没有生产者把工单送入补偿队列，自动补偿**本版不演示、不验收、不作书面承诺**）。**手动补偿本版也不现场点**：入口默认关闭（接口返回 503），且该路径不记录完整事件链、无重试。补偿段改为讲**种子里已回滚的工单**：能核对模拟系统上的冲销记录，但**不作为审计意义上的回滚闭环**，这是下一步要补的缺口。对贵司系统本期零写入；
- 已确认错放行、客户原因的自动扣减（本期以线下确认、人工登记并出具调整单的方式执行）；
- 系统内的人工复核留痕（本期以双方签署的复核记录为准）；
- 整批舍入超限的自动剔除（本期按合同/协议文本处理）；
- 系统生成的月度账单、发票与贷记单（本期以双方确认的对账单及线下单据为准）；
- 赔付的自动计算与上限校验（本期按合同约定核定）；
- 外部通知渠道与 7×24 值班（本期不交付；指标端点与 11 条告警规则在完整部署中可用，告警最多到达告警管理组件，本期不接任何通知渠道，不会通知到人）；
- 多币种、阶梯单价、按行类型差异化定价。

## 5. POC 验收

### 5.1 前置条件（缺一不开跑）

| # | 条件 | 责任方 |
|---|---|---|
| 1 | 签署 POC 协议：范围、样本量、样本期间、口径、时限、数据授权 | 商务 + 客户 |
| 2 | 指定 1 个期间、1 个供应商群、1 套我方 ERP 数据源 | 客户 |
| 3 | 主数据齐备：供应商、物料、单位换算 | 客户 |
| 4 | 提供供应商对账单（Excel/PDF/CSV 任一） | 客户 |
| 5 | 提供上一期双方已确认的对账结果，用于人工对照 | 客户 |
| 6 | 配置合同单行单价、封顶、上期累计 | 我方实施 |
| 7 | 明确 POC 对贵司系统全程零写入：不写回 ERP、不产生付款或凭证；演示写路径只指向我方自带的模拟系统 | 双方 |

### 5.2 客户提供的数据

- 供应商对账单：覆盖约定期间的全部行，含单据号、行号、物料、数量、单价、金额、税率；
- 我方 ERP 行：采购/委外订单、收货、发票对应的行级数据；
- 主数据：供应商编码与别名、物料编码、单位与换算关系；
- 上期已确认的对账结果；
- 覆盖以下形态的样本：零差异、单价差异、数量差异、舍入差、缺单、重复计费、匹配歧义、不可解析行（样本量由协议约定）。
- **数据交付方式：**本期由我方将双方提供的对账单整理为行级数据集后运行；**不通过接口从贵司系统拉取，贵司系统不回传也不被读取**。**演示环境**支持现场上传 CSV 并跑真实批次（我方行预置，见 §4.1）；**生产接线未做**，因此正式交付仍由我方整理行级数据集，不承诺「生产上传文件即对账」。

### 5.3 跑几步

| 步 | 动作 | 观察点 |
|---|---|---|
| 1 | 数据体检与口径确认会 | 哪些行算、哪些不算，双方先签字 |
| 2 | 配置主数据、单价、封顶、上期累计 | 单价来自合同配置，不用口头价 |
| 3 | 发起对账 | 批次号、批次状态、统计结果 |
| 4 | 查看批次 | 是否有缺失项；是否「无法对账」 |
| 5 | 查看差异 | 分类计数与列表是否一致 |
| 6 | 生成计量表 | 三类明细之和 = 应处理行数；缺失项逐条可见 |
| 7 | 导出明细并校验 | 内容摘要可离线复算 |
| 8 | 人工抽样复核 | 逐行判定「自动放行是否正确」 |
| 9 | 争议演练 | 模拟 1 行「已确认错放行」，走次月调整 |
| 10 | 出具 POC 报告 | 只写实测事实与双方确认的口径 |

### 5.4 通过标准（6 条全部满足）

| # | 通过条件 |
|---|---|
| P1 | 批次能出明确结论（已对账或待人工复核）；若为无法对账，必须给出可执行的缺失项清单（该情形归为数据/前置问题，不算产品通过） |
| P2 | 分类自洽：自动放行（即计费行）+ 争议挂起 + 其他不计费 = 应处理行数 = 供应商侧明细行数 |
| P3 | 可复算：计费行数 × 合同单价 = 本期金额（4 位小数），导出摘要校验一致 |
| P4 | 可追溯：每条计费行都有证据，或带可解释的自动归因类型 |
| P5 | 抽样复核：自动放行行的错误率 ≤ POC 协议书面约定的阈值 |
| P6 | 对贵司系统零外部写入：不写客户系统、不产生付款或凭证；演示写路径只指向我方自带的模拟系统，并以其请求记录自证 |

P5 的阈值必须在 POC 前由双方书面约定；未约定则不把 P5 当作通过项，只做描述性统计。

### 5.5 不纳入验收的项

- 监控与告警通知（指标端点与 11 条告警规则在完整部署中可用，并已演练到进入告警管理组件；本期不接外部通知渠道，不会通知到人，因此不纳入验收）；
- 自动回滚、自动补偿与撤销（补偿执行器已交付，但本期无业务建单入口、无生产者；入口默认关闭；本版不演示、不验收）。手动补偿本版**也不现场点**（入口默认关闭、不写审计链），只讲种子里已回滚的工单；
- 写路径验收（真实 U8 / WMS / 多系统写入）：本期只有 U8 制单草稿有写实现，且对端为我方模拟系统；WMS 无写实现、文件通道只读。不对任何真实系统做写入验收；
- 已确认错放行、客户原因的自动扣减；
- 赔付自动计算与上限校验；
- 月度账单、发票、贷记单。

以上任一项都不得作为 POC 通过条件，也不得在验收报告中写成「已验证」。

### 5.6 不通过怎么办

| 情形 | 判定 | 处理 |
|---|---|---|
| 主数据缺失、行不可解析导致无法出结论，且缺失项指向数据/前置问题 | 不算产品不通过 | 限期修数后重跑；重跑生成新批次，不算新争议 |
| 双方对某类行是否计费口径不一致 | 不算产品不通过 | 停跑，先签补充口径；未签前该行不计费 |
| 计数与明细不一致、同一批次两次读取结果不同、批次无法出结论且无明确数据原因 | 产品缺陷 | 我方修复后免费重跑一次；仍不通过，客户可终止 POC |
| 抽样错误率超协议阈值 | 效果不达标 | 按合同/协议约定处理 |
| 发生指向**贵司真实系统**的外部写入 | 立即停 | 按安全事故流程处置；POC 直接判不通过。（写入我方自带模拟系统不算，且可当场核对其请求记录） |

「免费重跑一次」仅限**产品缺陷**导致的重跑；数据源自身错误、客户侧数据变更、口径调整导致的重跑不在免费范围。

## 6. 对外表述边界

### 6.1 可以说

1. 按行计费：只有引擎自动完成匹配、且不需要人工的对账行才计费；需要人工的行不计费。
2. 批次即使最终没有自动放行，只要该行已自动匹配，仍然按行计费；合同会写「计费不以批次放行为前提」。
3. 已自动归因的差异行也计费；单行舍入容差行计费；整批舍入超限转人工部分按合同口径不计费，本期按上界出账、次月冲抵，不承诺系统自动剔除。
4. 单价写在合同附件，系统只从合同价目读取；未配置单价时不出账、不估账，也不会以空价继续出账。
5. 每一行都能导出并校验摘要；批次与行快照只追加，改判只能重跑新批次，原批次不变。
6. 计量只读：不写客户 ERP、不碰资金、不改状态。
7. 赔付上限为年订阅额的 20%，写在合同里，由我方按合同约定核定并执行。
8. 发布门禁全绿。
9. 跨系统写入后的**自动**回滚与补偿不在本期 POC 演示范围：补偿执行器已交付，但本期没有业务建单入口、没有生产者，自动补偿本版不演示。能在演示中看到的是**手动补偿**，且只在我方自带的模拟系统上：补偿动作是删除草稿（不是反做一张红冲单），入口默认关闭、不记录完整事件链、无重试。**能核对的是冲销结果，不是审计意义上的回滚闭环**（冲销没有进入审计链），因此只作能力展示。
10. 下一步处理建议是只读的：模型可用时给模型建议，不可用时降级为规则建议并标注「模型未参与」；建议不写库、不执行动作，决策仍由人做。
11. 审计可核验三件事：审计影像带字段级前后差异、哈希链可逐条校验、锚点可按日期查询。
12. 11 条告警规则已启用并演练到进入告警管理组件；本期不接外部通知渠道，告警不会通知到人。
13. **写路径只在本地模拟外部系统上演示**：连接器真实发出 HTTP 请求（预演 → 建草稿 → 回查 → 删除草稿），对端是我方自带的模拟系统——启动日志有横幅、响应带回执头、响应体标注 `simulated: true`，不是 U8、也不是贵司系统；请求与回执可在模拟系统的记录里当场核对。**对贵司系统本期零写入。**

### 6.2 不得说、也不得暗示

| 禁区 | 为什么 | 客户问时怎么答 |
|---|---|---|
| 任何百分比、分数或「接近全对」「业内领先」的效果承诺 | 未在客户数据上验证 | 按第 0 节那一句回答 |
| 任何性能秒数、行数或吞吐承诺 | 内部测试条件与客户环境不同；基线是合成数据、16C/32T、单进程单 worker，不含 HTTP/上传/连接器/鉴权/前端；单次跑不足以对外报 | 「性能以 POC 环境实测为准；已在 16C/32T 工作站完成合成数据基线，目标规格尚未验证。分阶段：引擎约 316×、端到端约 24×（10 万档 2664.2s→7.17s / 2380.1s→99.0s）。」 |
| 「整体提升两个数量级」 | 只对引擎阶段成立（约 316×）；端到端约 24×，合并说会高估约 4 倍 | 「分阶段看：引擎约 316×、端到端约 24×。」 |
| 「已在目标规格（4C4G）验证」 | 基线在 16C/32T 工作站，4C4G 没拿到、没有数据 | 「已在 16C/32T 工作站完成合成数据基线，目标规格尚未验证。」 |
| 「全自动对账，无需人工」 | 存在人工行、歧义、合并开票、缺单时必须人工 | 「自动放行的是行；整批放行要没有人工行。」 |
| 「效果不好不收费 / 成功后付全款」 | 商业模式是订阅底座 + 结果费 | 「平台订阅是底座，结果费有封顶；没有成功后付全款。」 |

| 「已实时告警通知 / 有人值班 / 告警会打电话」 | 本期不接外部通知渠道，告警只进入告警管理组件，没有人被叫醒 | 「本期不接通知渠道；告警只进入告警管理组件，不会通知到人，也没有值班。」 |
| 「AI 在自动决策 / 没模型也说是 AI 建议」 | 建议是双态且只读：无模型时是规则建议并标注「模型未参与」；任何状态下都不自动决策 | 「模型可用时给模型建议，不可用时降级为规则建议并标注『模型未参与』；建议不写库、不执行动作，决策由人做。」 |
