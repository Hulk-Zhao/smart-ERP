# 主数据体检性能基线（只读）

本文件记录 24 条规则在**确定性合成主数据**上的耗时与峰值内存，用来回答
「10 万行能不能在几分钟内跑完」。所有数据由
`apps/masterdata/benchmark.py` 生成，同一 `--rows` 两次运行结果完全一致；
不含数据库、网络、GPU 或任何写回操作。

## 1. 测试机规格

| 项目 | 值 |
| --- | --- |
| CPU | AMD Ryzen 9 9955HX 16-Core（16 核 / 32 逻辑线程） |
| 内存 | 31.2 GB |
| 操作系统 | Windows 11 家庭版中文版 10.0.26200（build 26200） |
| Python | CPython 3.11.9（64 位，Windows AMD64） |
| 运行方式 | 单进程、单线程、纯 CPU；无 GPU、无网络、无数据库 |
| 计时方法 | `time.perf_counter()`；内存取进程峰值工作集（含解释器基线） |

> 说明：核数只影响并行方案的潜力，本基线是单线程串行执行，不能按 16 核折算。

## 2. 实测结果

数据构成按固定比例拆分：供应商 20%、客户 15%、物料 35%、单据 30%；
每个量级都在**独立进程**中运行，避免上一个量级的峰值污染。

| 总行数 | 供应商 / 客户 / 物料 / 单据 | 体检耗时 | 序列化 | 峰值工作集 | 其中增量 | 差异条数 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 200 / 150 / 350 / 300 | 0.224 s | 0.002 s | 23.9 MB | 2.1 MB | 205 |
| 2,000 | 400 / 300 / 700 / 600 | 1.733 s | 0.005 s | 25.5 MB | 4.3 MB | 406 |
| 4,000 | 800 / 600 / 1,400 / 1,200 | 5.162 s | 0.007 s | 29.9 MB | 8.6 MB | 809 |
| 10,000 | 2,000 / 1,500 / 3,500 / 3,000 | 29.448 s | 0.015 s | 39.0 MB | 17.7 MB | 2,020 |
| 100,000 | 20,000 / 15,000 / 35,000 / 30,000 | **2,385.206 s（39 分 45 秒）** | 0.319 s | 176.4 MB | 155.2 MB | 20,192 |

结论：**10 万行实测 39 分 45 秒，判定为「跑不动」**（目标为几分钟），
且耗时几乎全部来自单线程 CPU 计算（进程 CPU 时间约 2,385 秒，无 I/O 等待）。
当前实现的实际可用上限约为 **1 万行（约 30 秒）**；
要支撑 10 万行，必须先把重复名称比对从「两两全比」改成索引/分桶，否则单纯分批
只是把同样的总计算量摊开，不会更快。

规模关系（实测）：1k→10k 行数放大 10 倍，耗时放大 131 倍（0.224 s → 29.448 s）；
10k→100k 再放大 10 倍，耗时放大 81 倍（29.448 s → 2,385.206 s）。
两段都接近平方级，与 §3 的 `combinations` 热点一致。
峰值内存随实体数近似线性增长：每 1,000 行约 1.6–1.8 MB 增量，
10 万行峰值 176 MB，内存不是瓶颈，时间才是。

## 3. 热点与判断依据

`cProfile`（1,000 行）显示 98% 的体检时间集中在一条规则：

- `rules.check_duplicate_supplier_other`（`rules.py:660`）：对同一组织内供应商做
  `combinations(values, 2)` 两两比较，每对都要做税号/银行账号/名称归一化，
  名称长度 ≥ 6 时再调 `difflib.SequenceMatcher` 算相似度；
- 1,000 行时供应商 200 家 → 19,900 对；10,000 行时 2,000 家 → 1,999,000 对；
  100,000 行时 20,000 家 → 199,990,000 对，增长是平方级。

因此耗时曲线随**供应商数量的平方**增长，而不是随总行数线性增长；
客户/物料/单据规则在 1,000 行时合计只占约 0.02 秒，不是瓶颈。

## 4. 分批与增量方案（只给判断依据，本轮不实现）

### 4.1 按主体类型切分

先跑供应商/客户/物料内部规则，再跑单据规则。

- 能降低单次内存峰值（不必同时持有全部差异），但**不减少**重复名称规则的两两比较总数；
- 单独使用不足以让 10 万行进入分钟级，只能作为内存兜底。

### 4.2 按编码区间分桶（shard）

把供应商按稳定哈希/编码前缀切成 N 桶，桶内两两比较；跨桶候选先用低成本指纹预筛
（税号后 4 位、归一化名称的前 2 个字符、银行账号后 4 位）。

- 依据：相似度阈值 0.92 的候选对必然共享高比例字符，指纹预筛可把候选集从 O(n²)
  降到近似 O(n·k)；
- 风险：指纹选择不当会漏报（例如名称仅中间字不同），必须先用真实样本验证召回率
  不低于全量比对，再作为默认路径；
- 这是唯一能实质降低 10 万行耗时的方向，应优先于「分批跑」。

### 4.3 增量（只检查变更主体）

数据源提供主体 `last_modified`/版本号时，只重跑变更主体；但重复名称规则需要与
**全量存量**比对。

- 做法：存量侧维护一次 O(n) 的归一化名称/税号索引，新增或改名主体用索引查询候选，
  单次成本 O(k)（k 为变更数）；
- 依据：k << n 时收益明显；但删除、改名、组织调整会让索引失效，需要重建；
- 风险：如果只跑增量而跳过全量索引重建，会漏掉「改名后与存量撞名」，因此索引必须
  与主体变更同事务更新，或定期全量校准。

### 4.4 预算建议

以「单次体检 ≤ 3 分钟」为目标，按实测平方级曲线约 **2.2–2.6 万行**是上限；
要支撑 10 万行，需要先完成 §4.2 的分桶索引，再谈分批/增量。

## 5. 可复现性

同一输入两次运行，报告与降级清单的规范 JSON **逐字节相同**：

- 序列化固定为 `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(",", ":"))`；
- 规则输出本身已按 `(严重度, rule_id, 对象类型, 对象编码, 期间)` 排序，
  降级清单再按 `(主体类型, 主体编码, rule_id, 期间, 原因)` 排序；
- 1,000 行基线摘要：
  - `report_digest = a9baa12a14abbdf716e91eeb89c0fdf3cc3807a750912e2988a524021ab973e8`
  - `downgrade_digest = bf91621cc27152d4767c0bf587d4389fe71a37163875b7a5783d26101e8977df`
- 100,000 行基线摘要：
  - `report_digest = 551da6e173ccb79db781de7d1f2e87c82565dc852c184fb56f89877bd57bf58a`
  - `downgrade_digest = 28b1eda68ff7a5b27e366eda2d92e76d975bca2c0b546484a01aa264c778f84a`
- 断言位置：`tests/masterdata/test_masterdata_benchmark.py`
  （`test_same_input_produces_byte_identical_report`、
  `test_downgrade_list_is_byte_identical_across_runs`）。

## 6. 复跑方法

```powershell
python -m apps.masterdata.benchmark --rows 1000
python -m apps.masterdata.benchmark --rows 10000 --json bench-10k.json
python -m apps.masterdata.benchmark --rows 100000
```

建议每个量级单独起进程；数据生成不使用随机数，`--rows` 相同则输入相同。
