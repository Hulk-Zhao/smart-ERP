# 主数据体检性能基线（只读）

本文件记录 24 条规则在**确定性合成主数据**上的耗时与峰值内存，用来回答
「10 万行能不能在几分钟内跑完」。数据由 `apps/masterdata/benchmark.py` 生成，
同一 `--rows` 两次运行结果完全一致；不含数据库、网络、GPU 或任何写回操作。

> 解释器统一为 **CPython 3.12**（CI 与线上一致，见 `00-协作规约.md` §12）。
> 早期 3.11.9 的基线已作废，只在下文对比里保留说明。

## 1. 测试机与解释器

| 项目 | 值 |
| --- | --- |
| CPU | AMD Ryzen 9 9955HX 16-Core（16 核 / 32 逻辑线程） |
| 内存 | 31.2 GB |
| 操作系统 | Windows 11 家庭版中文版 10.0.26200（build 26200） |
| Python | **CPython 3.12.12**（64 位，Windows AMD64） |
| 运行方式 | 单进程、单线程、纯 CPU；无 GPU、无网络、无数据库 |
| 计时方法 | `time.perf_counter()`；内存取进程峰值工作集（含解释器基线） |

> 核数只影响并行方案的潜力，本基线是单线程串行执行，不能按 16 核折算。
> 每个量级都在**独立进程**里跑，避免上一个量级的峰值内存污染下一个。

数据构成按固定比例拆分：供应商 20%、客户 15%、物料 35%、单据 30%。

## 2. 修复前后对比（同机、同数据、同解释器 3.12.12）

「修复前」是重复名称规则按 `combinations` 两两全比的实现；「修复后」是
本轮改成的索引/分桶实现（见 §3）。

> **对外口径：下表（含「10 万行 45 秒」）与本文引用的降级占比（如 40%）全部来自
> 确定性合成主数据的最坏构造，只用于内部回归与容量判断；耗时才绑定本机
> （Ryzen 9 9955HX），换机不成立，既不能对外引用，也不能外推到真实客户数据。**

| 总行数 | 供应商 / 客户 / 物料 / 单据 | 修复前体检 | 修复后体检 | 加速 | 修复前峰值 | 修复后峰值 | 差异条数 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 200 / 150 / 350 / 300 | 0.284 s | **0.21 s** | 1.4× | 24.4 MB | 24.0 MB | 205 |
| 10,000 | 2,000 / 1,500 / 3,500 / 3,000 | 27.05 s | **3.69 s** | 7.3× | 35.7 MB | 38.2 MB | 2,020 |
| 100,000 | 20,000 / 15,000 / 35,000 / 30,000 | 2,417.25 s（40 分 17 秒） | **44.93 s** | **53.8×** | 152.9 MB | 148.5 MB | 20,192 |

结论：

- **10 万行 44.93 秒**，满足「≤ 5 分钟」；**1 万行 3.69 秒**，满足「≤ 30 秒」；
- 峰值内存基本持平（10 万行 148.5 MB），耗时从「随供应商数量平方增长」变成
  近似线性：1k→10k 行数 ×10、耗时 ×17.6；10k→100k 行数 ×10、耗时 ×12.2。

### 2.1 「改快了但没改错」的证据

只看耗时不够，下面三条是逐项核对过的：

1. **差异条数逐量级一致**：205 / 2,020 / 20,192，修复前后总数完全相同；
   1k/10k 另按规则与触发编码逐条对照（见第 3 条），100k 以总数与降级清单
   摘要为准（未逐条重放旧实现，避免再跑一次 40 分钟）；
2. **降级清单逐字节一致**：`downgrade_digest` 在 1k、10k、100k 三个量级上
   与修复前完全相同（1k `bf91621c…`、10k `6f15e8c5…`、100k `28b1eda6…`），
   说明下游影响面没有变化；
3. **触发对象集合一致（1k/10k 逐条对照旧实现）**：DUP-002 的触发编码集合
   不多不少；差异只在形近名称的**证据行**上——窗口外的一小部分候选不再列出
   （10k 实测 50 条证据行、约占 0.4%，见 §4.1 的召回折中与运维结论）。

`report_digest` 会变，但原因只有两个，且都不改结论：`options` 新增了三个阈值
键；上述形近名称证据行的窗口差异。全仓除 S9 自身（`benchmark.py` 产出、
`PERFORMANCE.md` 记录、基准测试做两次运行的相等断言）外，**没有任何其他流
消费 `report_digest`**（S2 金标准用的是夹具 `sha256` 与仅覆盖 `apps/recon`
的 `engine_sha256`，与本报告无关）。

### 2.2 与 3.11 的差异

同一份数据、同一实现，3.11.9 与 3.12.12 的体检耗时差在 3% 以内
（10 万行 2,385.21 s vs 2,417.25 s，3.12 略慢），输出完全一致（差异条数与
规范 JSON 摘要相同）。**结论以 3.12 为准**，3.11 的数字不再作为基线引用。

## 3. 热点与修法

`cProfile` 显示修复前 98% 的体检时间集中在一条规则：
`rules.check_duplicate_supplier_other`（DUP-002）。它对同一组织内供应商做
`combinations(values, 2)` 两两比较，每对都重复做税号/银行/名称归一化，名称
长度 ≥ 6 时再调 `difflib.SequenceMatcher`。供应商 2,000 家时是 199.9 万对，
20,000 家时是 1.999 亿对。

本轮把三类命中全部改成索引：

1. **精确相等（O(n)）**：`DUP-001` 同税号、`CUST-001` 同税号、`DUP-003`
   名称/规格/单位、`CUST-002` 归一名称、`CODE-001` 折叠编码，本来就是字典分组，
   不参与两两比较；本轮复核确认没有残留的 `combinations` 热点。
2. **DUP-002 的银行账号 / 归一名称**：按归一后的键直接 `dict` 分组，组内才是
   候选；同一对供应商的多个原因合并成一条证据，输出格式不变。
3. **形近名称**：不再两两全比，改为
   - 按归一化名称**正序**排序取邻域（捕捉共享长前缀）；
   - 按**反转名称**排序取邻域（捕捉共享长后缀，例如「XX公司A」与「XX公司AB」）；
   - 补一遍「短名是长名前缀」的**二分候选**（同一前缀下名字太多时，避免被窗口漏掉）；
   - 比较前先过**长度差阈值**与 `SequenceMatcher.real_quick_ratio()`，都通过才
     调 `ratio()`。

长度差阈值的依据：`ratio <= 2L/(2L+d)`（`L` 为短名长度、`d` 为长度差），
要求 `ratio >= 0.92` 就得到必要条件 `d <= L × 2(1-0.92)/0.92 ≈ 0.174L`，
默认取 `0.20L + 1` 留余量。该条件只会提前淘汰不可能命中的候选，不会误杀。

整体复杂度从 `O(n²)` 降到 `O(n log n + n·窗口)`。

## 4. 阈值默认值与适用规模

阈值都在 `InspectionOptions` 里，可被调用方覆盖，并随报告 `options` 字段输出：

| 参数 | 默认值 | 作用 | 默认值成立的前提 |
| --- | ---: | --- | --- |
| `duplicate_name_threshold` | 0.92 | 名称相似度达到该值才提示 | 名称归一后仍高度相似才算重复；低于 0.92 的「有点像」不猜 |
| `duplicate_name_min_length` | 6 | 短于该长度的名称不参与相似度猜测 | 两三个字的简称几乎必然彼此相似，报了也无法处理 |
| `duplicate_name_window` | 128 | 正序/倒序邻域各取多少个邻居 | 名称相似度高的主体在排序后相邻；窗口是最主要的召回/耗时旋钮（何时必须调见 §4.1） |
| `duplicate_name_length_ratio` | 0.20 | 长度差上限（相对短名长度） | 由 0.92 推出的必要条件约 0.174，0.20 留余量 |

**默认值在什么规模下还成立：**

- 合成数据（最坏情况：所有名称共享 5 字前缀 + 数字后缀）在 **10 万行 /
  2 万供应商**下实测 44.93 s、峰值 148.5 MB，默认值成立（合成、本机数字，
  仅内部参考，不对外、不外推，见 §2 上方口径）；
- 「成立」指耗时在分钟级且形近名称召回 ≥ 99.6%；供应商数超过 2 万后耗时
  近似线性增长（每增加 1 万供应商约 +20 秒），但**默认窗口的召回率不再有
  实测支撑**，必须按 §4.1 复核；
- 单次要跑几十万行时，优先按组织/编码区间分批，而不是只靠调小窗口换速度。

### 4.1 运维结论：什么时候必须调 `duplicate_name_window`

**① 那 0.4% 是什么。** 1 万行上形近名称（DUP-002）的证据行比逐对全比少
50 条（50 / 约 12,000 条 ≈ 0.4%），但**触发编码集合一条不少**，只是窗口外
的候选不再逐条列为证据。这是 `duplicate_name_window=128` 在「所有名称共享
5 字前缀 + 数字后缀」这一最坏构造下的召回折中，**不是 bug**；真实数据的
名称分布更散，实测占比通常低于此值。

**② 什么情况下必须调。**

| 条件 | 动作 |
| --- | --- |
| 供应商 ≤ 2 万（约 ≤ 10 万行），且接受 99.6% 召回 | 保持默认 128，无需调整 |
| 供应商 > 2 万，**或**本次输出要拿去跟供应商主档做 100% 对账 | 调成 256，跑一次复核 |
| 单次超过约 20 万行（约 4 万供应商） | 先按组织/编码前缀分批；仅调大窗口不足以解决规模问题 |

**③ 调成多少、会慢多少（实测）。**

- 256 在最坏构造上与逐对全比结果一致，即 **100% 召回**；10 万行下比 128
  多召回 **3,850 条** DUP-002 证据行，`findings` 总数（20,192）与峰值内存
  （148–150 MB）都不变；
- 耗时：同批次实测 10 万行 **128 = 50.4–58.0 s、256 = 88.5–94.6 s**，
  倍数 **1.63×–1.75×**；按安静环境 128 的 44.93 s 折算（同一合成数据、同机），即
  **10 万行从约 45 s 涨到约 73–81 s，容量规划按 ≤ 95 s 预留**；
- 复测时机器有并发负载（Load ≈ 23%），绝对值偏高，**倍数**才是可用的数。

**④ 怎么设、怎么确认生效。**

- 两条等价入口：CLI `--duplicate-name-window 256`，或
  `InspectionOptions(duplicate_name_window=256)`；报告 `options.duplicate_name_window`
  会回显实际值，用它确认配置已生效（不传时为默认 128）；
- 复核动作：先用默认值出结论，再只对「与供应商主档对账」的那一批用 256
  重跑，diff 多出来的证据行即可，不必全量重跑再人眼比对。

## 5. 可复现性与 CI 断言

同一输入两次运行，报告与降级清单的规范 JSON **逐字节相同**：

- 序列化固定为 `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(",", ":"))`；
- 规则输出本身已按 `(严重度, rule_id, 对象类型, 对象编码, 期间)` 排序，
  降级清单再按 `(主体类型, 主体编码, rule_id, 期间, 原因)` 排序；
- 修复后基线摘要（3.12.12）：
  - 1,000 行：`report_digest = d8921159d2de6bbcf082684a9f93be3df6d5d4e96b8ba9ad9071fe78d1e3629d`，
    `downgrade_digest = bf91621cc27152d4767c0bf587d4389fe71a37163875b7a5783d26101e8977df`
  - 10,000 行：`report_digest = d75ff736041fd20d74e96929d5b3dfd8dc403a4359b43f066bd62c5fab310fe9`，
    `downgrade_digest = 6f15e8c54ab7563a9e99758ca0e4eecb1a2f70c3b434ad99f99c3ec664fed232`
  - 100,000 行：`report_digest = 45443dce156e891d164fa3e9b38eabdec126587b650bbb5f06bf7e497a59fad7`，
    `downgrade_digest = 28b1eda68ff7a5b27e366eda2d92e76d975bca2c0b546484a01aa264c778f84a`
- `report_digest` 与上一版不同，是因为 `options` 新增了三个可配阈值；**差异条数
  与降级清单摘要（`downgrade_digest`）在三个量级上都没变**，下游影响面不变。

CI 断言（`tests/masterdata/test_masterdata_benchmark.py`）：

- 规模上限固定 **1 万行**，10 万行不进 CI（太慢）；
- 断言「1 万行体检 ≤ 30 秒」，且两次运行报告逐字节相同；
- 10 万行的数字只作为人工基准记录在本文件，并注明硬件与解释器版本。

## 6. 复跑方法

```powershell

```
